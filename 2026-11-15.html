Z 函式（Z-function）：線性掃描記錄每個位置與開頭的最長共同前綴

今天換一個完全沒教過的分類：Z 函式（Z-function）。給定字串 s（長度 n），Z 陣列定義 為 z[i] = s[i..n-1] 與 s[0..n-1] 的「最長共同前綴」長度（z[0] 通常直接定義為 0 或 n，依實作慣例而定，底下取 n）。換句話說，z[i] 回答的是：「從位置 i 開始看， 最多能往後抄多少個字元，跟開頭一模一樣？」這跟之前教過的 KMP failure function 問的是同一類問題的「鏡像版本」—— failure function 問「這個前綴的尾巴，最多能跟自己的開頭重疊多少」，Z 函式問「字串中每個位置，跟整體開頭最多重疊多少」。

暴力算法很直覺：對每個 i，從 s[i] 開始逐字元跟 s[0] 比對，比到不相等為止。這樣單個 i 最壞要花 O(n) 比較， n 個位置合計 O(n²)。Z 函式的關鍵洞察是：比對過程中產生的資訊不該被丟棄。演算法維護一個視窗 [l, r]， 代表「目前見過、延伸最靠右的一次匹配區間」（也就是某個 z[l] 的匹配延伸到了 r）。處理新的位置 i 時分兩種情況： 如果 i 還在視窗內（i ≤ r），表示 s[i..r] 其實已經知道等於 s[i-l..r-l]（因為整段 [l,r] 本身就是開頭的拷貝）， 所以可以直接借用 z[i-l] 當作初始猜測，不必從零比對；如果猜測值剛好頂到視窗邊界 r，才需要從 r+1 開始「手動」往後多比幾個字元確認有沒有更長。如果 i 已經超出視窗（i > r），就只能老實從頭手動比對，比完後更新 [l, r] 為新找到的這段。

Z-box　指演算法當下維護的區間 [l, r]：曾經確認過 s[l..r] 等於 s 的前綴 s[0..r-l]，是整個加速技巧的「已知情報快取」。

走一遍實例會比較有感覺。令 s = "aabxaabxcaabxaabxay"……其實不用這麼長，拿一個經典小例子 s = "aaabaab"（n=7）來看：z[0] 定義為 7（整串跟自己比對當然全等，實作上這個位置通常另外處理，不列入 「找最長 proper border」的候選）；z[1]：從 s[1]="aabaab" 比對開頭 "aaabaab"，第一個字元 a=a，第二個字元 a=a，第三個字元 b≠a，所以 z[1]=2；z[2]：從 "abaab" 比，a=a，b≠a，z[2]=1；z[3]（字元是 'b'，跟開頭 'a' 第一 個字元就不同）z[3]=0；z[4]：從 "aab" 比開頭 "aaabaab"，a=a、a=a、b≠a，z[4]=2；z[5]：從 "ab" 比，a=a， b≠a，z[5]=1；z[6]：從 "b" 比，b≠a，z[6]=0。整個 Z 陣列是 [7,2,1,0,2,1,0]。這組數字馬上告訴你 一個重要事實：位置 1 跟位置 4 都「局部長得像開頭」，長度分別是 2 跟 2——這正是後面講字串週期時會用到的線索。

Edge case 值得特別小心：如果整個字串每個字元都不同（例如 "abcde"），Z 陣列除了 z[0] 之外全部是 0，演算法 不會因此錯誤地「省略比較」，視窗 [l,r] 會一路維持退化（r 幾乎不往前推進），但這剛好印證了下面數學推導要證明 的攤還論證——視窗沒有進展時，演算法本來就只做常數次工作，不會變慢。另一個邊界是整個字串由同一個字元組成 （例如 "aaaaa"），這時 z[i] = n-i 對所有 i 成立（每個位置往後看都跟開頭重疊到字串結尾），視窗會一路擴張到底， 是「視窗推進量」被用滿的極端情況，也是驗證實作正確性時最容易踩雷的輸入（off-by-one 常在這種全同字元輸入下现形）。

border（邊界）　字串的 border 是「同時是它的 proper 前綴、又是它的 proper 後綴」的子字串（proper 指長度嚴格小於原字串）。KMP 的 failure function 和 Z-function 本質上都是在幫你快速找出所有 border。

複雜度比一比：暴力法對每個起點重新掃一次，最壞 O(n²)（例如整串同字元時每個起點都要掃到底）；如果是「多個 模式字串對同一個長文本做比對」，暴力更糟，變成 O(n·m) 甚至更高。Z 函式只需要一次線性掃描，時間 O(n)、額外空間 O(n)（存 Z 陣列本身），且是 one-pass、不需要像後綴自動機那樣先建出一個更重的資料結構，這也是它在演算法面試裡 討喜的原因——程式碼量跟 KMP failure function 差不多（都在 20 行內），但很多人覺得 Z 函式的「視窗推進」邏輯比 KMP 的「失敗後回退到哪裡」更直覺好記。

兩個最常見的變形模式：第一種是單模式字串比對——把 pattern + 分隔符 + text 接成一條新字串 （分隔符要選一個保證不會出現在 pattern 或 text 裡的字元，常用 # 或 \x00），對這條新 字串算一次 Z 陣列，只要某個落在 text 部分的位置 z 值剛好等於 pattern 長度，就代表那裡出現一次完整匹配，整體時間 仍是 O(n+m)，跟 KMP 做字串搜尋是同一個複雜度量級的替代方案。第二種是字串週期／循環節偵測：字串 s（長度 n） 存在長度為 d 的週期（也就是 s 可以看成某個長度 d 的子字串重複貼出來），條件是 z[d] == n-d；如果還要求 「剛好整除、完全由重複單元拼成」（不是只在尾端部分重疊），再加上 n % d == 0 這個額外條件即可。

sentinel 分隔符　在「pattern + 分隔符 + text」技巧裡插入的那個保證不會出現在原字串中的特殊字元，作用是切斷 Z 陣列的匹配，避免 pattern 的比對不小心「跨過邊界」延伸進 text 裡、或反過來，造成誤判。

面試官常見追問，建議心裡先有答案：「Z 函式跟 KMP 的 failure function 是不是同一個東西？」答案是：兩者都在 O(n) 時間內提取出字串的 border 結構，彼此可以互相推導（已知 Z 陣列可以 O(n) 轉成 failure 陣列，反過來也可以）， 但視角不同——failure function 是「每個前綴自己的最長 proper border」，Z 函式是「每個位置跟整體開頭的最長共同前綴」， 在單模式字串搜尋這個最常見的應用上效能完全等價，差異主要在工程習慣與哪種視窗邏輯比較好除錯。另一個常見追問是 「視窗 [l,r] 為什麼保證均攤 O(n)？」——這題的嚴謹論證放進下面的數學推導區塊；還有「如果要同時搜尋 k 個模式字串， Z 函式還夠用嗎？」——單純重複套用 k 次 O(n+mᵢ) 的技巧仍然可行但沒有共用資訊，這時更合適的工具是後綴自動機或 Aho-Corasick（字典樹 + failure link 的多模式版本），可以把資訊結構一次攤平共用，這也是這題如果追問到底，最終 會導向「你知道比 Z 函式更進階的字串資料結構嗎」的分水嶺問題。

宣稱 Z 函式是「攤還 O(n)」，核心論證在於視窗右端 r 在整個演算法執行過程中只會往右移動，不會往左退。 每次處理位置 i 時，演算法做的「真正逐字元比較」只發生在兩種情況：(1) i 超出目前視窗（i > r），这時從 r+1（也就是 i 本身）開始手動比對；(2) i 在視窗內但借用的猜測值剛好頂到視窗邊界，於是從 r+1 繼續往後多比幾個字元確認。這兩種 情況合起來看，每一次「手動比較」要麼立刻失敗（比較 1 次就結束，退出迴圈），要麼成功並讓 r 往右推進 1。 全程下來，「成功的手動比較次數」累計起來最多等於 r 總共推進的距離，而 r 的範圍被限制在 [0, n-1]，所以成功比較的 總次數 ≤ n；「失敗的手動比較」每次最多發生 1 次就立刻終止該輪的擴張，所以總共最多 n 次。兩者相加，整個演算法 的逐字元比較次數上界是 O(n)，而不是每個 i 都重新比對一次的 O(n²)——這跟滑動視窗、雙指標類演算法的攤還證明是 同一套「指標單調不回頭」的論證骨架。

Ch.4　4.2 Logic Design and the Hardware Control Language HCL

上一次（11/14）學完 4.1 的 Y86-64 指令集架構之後，今天進入 4.2 Logic Design and the Hardware Control Language HCL——邏輯設計與硬體控制語言 HCL。這一節的任務是「換心智模型」：4.1 讓你用寫組合語言程式的方式理解 Y86-64，4.2 要讓你學會用「搭電路」的方式思考同一組指令要怎麼被硬體真正執行，而 4.3 緊接著就會把這一節學到的元件 真正接線組成一台可以跑 Y86-64 程式的 SEQ（Sequential）處理器。換句話說，4.2 不是獨立的理論章節，而是 4.3 的 零件清單與電路圖語言。

整節的第一個觀念回顧：邏輯閘（AND、OR、NOT 等）是沒有狀態的物理電路，它們是純函式——輸出完全由當下輸入 決定，不記得任何歷史。這點看似理所當然，但是整個數位邏輯設計最重要的前提：之後你會看到，處理器裡「會記得東西」 的部分（程式計數器、暫存器、記憶體）必須被刻意、明確地跟這些「不會記得東西」的組合邏輯分開設計，兩者混在一起接線 是硬體 bug 的主要來源之一。CS:APP 第 4 章重點筆記裡對這個性質下了很精準的一句話：「組合邏輯不需要任何時序或 控制——只要輸入變化，值就通過邏輯閘傳播。」

組合邏輯（Combinational Logic）　由邏輯閘搭建、完全沒有內部狀態的電路：任何時刻的輸出都只是當下輸入的函式，沒有「記憶」，輸入一變，經過閘延遲之後輸出就自動跟著變。

HCL 的 Boolean 表達式語法就是把這種「純函式」電路，用類似 C 的語法寫下來：宣告一個 bool 型的 訊號，右邊用 &&（AND 閘）、||（OR 閘）、!（NOT 閘）、== （相等比較電路）組合其他訊號。比方說 Y86-64 要判斷「目前這個 icode 是不是屬於條件跳躍或條件搬移這一類」，HCL 會寫成類似 bool Bch = icode in { IJXX, ICMOVXX }; 這種形式——這正是下一段要講的 set membership 語法糖。每個 HCL 的 bool 表達式最終都會被拆解回一組邏輯閘的接線圖，所以 HCL 本身並不是一種「程式語言」，而是 「畫電路圖的文字描述法」，寫出來的每一行都對應一塊實際存在的硬體。

比 Boolean 訊號更進一步，4.2 引入字組層級（word-level）的組合邏輯：把一整束位元線（例如 64 條線） 當成一個「字」整體操作，最典型的元件是多工器（MUX）——根據一個或多個選擇訊號，從好幾個輸入字裡選出一個 當輸出。HCL 用 int 型訊號搭配 case 表達式來描述 MUX：case 裡列出一串 「條件 : 值」，依序往下求值，第一個條件為真的那一行決定輸出（不是所有符合條件的都生效，只取最先符合的）， 這個「優先權」語意直接對應硬體上用一串優先編碼邏輯接出來的多工器，而不是「同時」比較所有分支。這點是初學者最容易 誤解的地方——HCL 的 case 看起來像 C 的 switch，但 C 的 switch 預設會貫穿 到下一個 case（除非寫 break），HCL 的 case 則是「只取第一個為真的分支」，語意上更接近巢狀的 if-else if 鏈。

多工器（MUX, Multiplexer）　一種字組層級的組合邏輯元件：輸入好幾條等寬的資料線與一組選擇訊號，依照選擇訊號的值，把其中一條輸入線直接接通到輸出。Y86-64 處理器裡每個「這個數值從哪裡來」的分支，硬體上幾乎都是一顆 MUX。

Set membership 是 HCL 提供的語法糖：x in {v1, v2, v3} 這一個寫法，背後會被展開成 (x==v1) || (x==v2) || (x==v3)，純粹是為了讓「判斷某個訊號是不是屬於某一類值」這件事在 HCL 裡寫起來 更簡潔。這個語法在 Y86-64 的控制邏輯裡大量出現，原因是處理器經常要問「目前這個 icode，是屬於算術運算類、跳躍類、 還是堆疊操作類」，與其寫一長串 ||，不如直接列舉這一類包含哪些 icode 值，可讀性高很多，也更貼近 「這是在描述一種分類關係」的本意，而不只是硬體線路的細節。

最後一個子小節 Memory and Clocking，是整節真正的分水嶺——從「沒有狀態的組合邏輯」切換到「有狀態的 時序邏輯（sequential logic）」。CS:APP 的 SEQ 處理器裡，只有四個部件真正需要被明確的時脈訊號控制時序： 程式計數器（PC）、條件碼暫存器（CC）、資料記憶體、暫存器檔案（register file）； 除了這四個，處理器裡其他所有邏輯都是純組合邏輯，不需要時脈。筆記裡的原文描述得很精確：「這些單元通過一個時鐘 信號來控制，它觸發將新值轉載到暫存器，並將值寫到隨機存取記憶體。」更具體一點：程式計數器每個時鐘週期都會載入 新的指令位址；條件碼暫存器只有在執行整數運算指令時才會被更新；暫存器檔案只有在執行 rmmovq、 pushq、call 這類會寫暫存器的指令時才寫入。

正緣觸發（Edge-Triggered）　時序元件只在時鐘訊號由 0 跳到 1 的那一瞬間（上升緣）才真正把新值鎖存進去，週期內其餘時間即使輸入訊號一直在變，輸出也維持舊值不動，直到下一次上升緣才更新。

為什麼一定要「正緣觸發」而不是隨時更新？因為這是保證整台處理器行為可預測的關鍵約束：一個時鐘週期內，指令 讀取狀態時，讀到的永遠是「上一個週期結束時鎖存的舊值」，絕對不會讀到「本週期正在計算、還沒寫回去的新值」—— 如果沒有這條規則，電路裡一旦出現「輸出回頭影響自己輸入」的回授路徑，就可能永遠震盪、收斂不到穩定值，或是不同 元件之間因為微小的延遲差異，讀到彼此處於「寫一半」的中間狀態，產生無法重現的 race condition。這也解釋了為什麼 4.2 要先把「無狀態的組合邏輯」跟「有狀態、靠時脈更新的時序邏輯」切得這麼乾淨——4.3 之後要設計 SEQ 處理器的每一 個 stage（取指、解碼、執行、記憶體存取、寫回），本質上就是在這兩種元件之間接線，而「這條線到底是組合邏輯算出來 的瞬時值，還是時序元件鎖存著的穩定值」，是後面讀懂整張 SEQ 電路圖最重要的一條分界線。

面試或實務上常見的追問延伸到這一節：「為什麼數位電路設計要嚴格禁止組合邏輯裡出現回授迴路（feedback loop）？」——答案就是上一段講的震盪/不穩定風險，純組合邏輯被定義成必須是無迴圈的有向圖（DAG），一旦出現環， 就不再是「輸出是輸入的函式」這麼簡單的語意了。「同步電路跟非同步電路的差異是什麼？」——同步電路（像這裡的 SEQ） 所有狀態更新都綁在同一顆全域時鐘上，非同步電路沒有全域時鐘，靠訊號本身的到達順序觸發，設計更自由但也更難驗證 正確性，是許多真實晶片抓蟲的重災區。CS:APP 刻意先用 HCL 把「組合邏輯 vs 時序邏輯」這條線畫得清清楚楚，正是為了 讓後面 4.3～4.5 一路推進到 pipeline 處理器時，你能一眼看出每個訊號屬於哪一種性質。

🔢 數學推導

4.2.5 Memory and Clocking 雖然沒有給出具體公式，但它隱含了一個所有真實硬體時序設計都要面對的數字限制： 時鐘週期 Tc 不能無限縮小，必須滿足 Tc ≥ t_pd + t_setup——其中 t_pd 是 這一段組合邏輯從輸入變化到輸出穩定所需的最長傳播延遲（propagation delay，取決於串接了多少層邏輯閘）， t_setup 是時序元件（暫存器）要求「新值必須提前穩定多久，才能保證下一次上升緣能正確鎖存」的 setup time。如果時鐘週期短於這個下限，暫存器可能鎖存到還在變化、尚未穩定的中間值，造成不可預期的錯誤狀態 （這在真實晶片設計裡稱為 setup-time violation）。這正是為什麼 4.2 要先讓讀者認識「組合邏輯有延遲、時序元件有 穩定時間需求」這兩個前提——4.4～4.5 之後要把 SEQ 拆成多個 pipeline stage 來提升時脈頻率，本質上就是把一條很長 的 t_pd（跨整個指令執行路徑）切成好幾段較短的 t_pd，讓每一段都能單獨滿足上面這個不等 式、把 Tc 壓得更小，整台處理器的輸出總帶寬（throughput）才能因此提升，即使單一指令從頭到尾所需的 總延遲（latency）並沒有變短，甚至因為加入暫存器而略微增加。

§01
Linux 核心的 /dev/mem 裝置：把實體記憶體位址空間直接攤開成一個可 mmap 的檔案

Linux 延續「進度表 Week 13」這一週的記憶體管理主題，11/08 教過 POSIX Shared Memory、11/14 教過更全景的 System V shm／POSIX shm／memfd_create／dma_buf 比較，今天接著 Week 13 清單上緊接在這兩者後面的下一個項目： /dev/mem 裝置。如果說前兩天在講「使用者空間程式之間怎麼合法地共享一段記憶體」，今天要講的是更底層、更 赤裸的東西——「使用者空間程式要怎麼繞過所有抽象，直接摸到實體記憶體位址空間本身」。/dev/mem 把整個系統的實體 位址空間，直接攤開成一個可以被 open／read／write／mmap 的字元裝置檔案，從 Linux 最早期的版本（v0.01）就存在，是 UNIX「everything is a file」這句話被實踐到最極端的 案例之一。

先把它跟一般的記憶體存取路徑對比一下：平常一個行程讀寫記憶體，是透過 CPU 的 MMU 把虛擬位址翻譯成 實體位址，這整層翻譯（page table）被核心嚴密控制，使用者完全看不到、也碰不到實體位址本身——這正是 CS:APP 第 9 章「虛擬記憶體」花了一整章要建立的抽象：每個行程活在自己私有的位址空間裡，彼此看不到對方，也看不到 實體記憶體真正的樣子。/dev/mem 是這層抽象刻意開的一個後門：只要有權限（通常要 root），就可以指定一段實體 位址，直接要求核心把它映射進自己的虛擬位址空間，徹底跳過「這段記憶體原本屬於哪個行程」這個問題。

實體位址 vs 虛擬位址　虛擬位址是 CPU 執行指令時看到的位址，要經過 MMU／page table 翻譯才能對應到真正的記憶體晶片位置；實體位址才是硬體匯流排上真正拿去定址 DRAM／MMIO 裝置的那個號碼。/dev/mem 操作的是後者。

實際使用方式很直接：open("/dev/mem", O_RDWR) 拿到檔案描述子後，呼叫 mmap(addr, length, prot, flags, fd, offset)，這裡的 offset（第六個參數）不是檔案裡的偏移量，而是你想映射 的那段實體記憶體的起始位址本身；呼叫成功後，回傳的虛擬位址範圍，讀寫起來就等同直接讀寫那段實體記憶體—— 不管它是真正的 DRAM，還是某張 PCI 裝置映射進位址空間的暫存器（MMIO），/dev/mem 一視同仁。也可以直接對 /dev/mem 用 read／write 搭配 lseek 存取，但那樣每次都要經過核心內部的 緩衝區複製一次，效能遠不如 mmap 把那段實體記憶體直接映射進使用者空間後反覆存取。

jserv 課程筆記裡示範了幾個很具體的真實案例，很值得拿來建立直覺：其一是搭配開機參數 mem=11G 限制核心只管理前 11GB 記憶體（讓核心完全不替超過這個範圍的記憶體建立映射與保留），之後透過 mmap(0, 0x1000, ..., fd, 0x2C0000000) 把核心「看不到」的那段實體記憶體直接摸出來用；其二是 master.c／slave.c 這組範例，分別映射實體位址 0x34000000 與 0x34004000，讓兩個互不相關、原本沒有親緣關係的行程透過同一段實體記憶體交換資料，等於用 /dev/mem 自己手刻一個最原始版本的共享記憶體；其三則示範了更危險的用法：找出某個行程的虛擬位址對應的實體 位址後，透過 /dev/mem 直接竄改那段記憶體內容，甚至反組譯核心函式 devmem_is_allowed 之後，直接 用 /dev/mem 改寫它的機器碼，讓它永遠回傳「允許」。

這也直接帶到安全性考量：操作 /dev/mem 需要足夠權限（一般要求 root），但光有 root 權限還不夠，核心本身還有 一層守門機制——devmem_is_allowed() 這個函式，會呼叫 region_intersects() 與 iomem_is_exclusive() 判斷你想存取的那段實體位址，是不是被標記成一般系統記憶體（System RAM）且 已經被某個驅動程式獨占使用；如果是，預設就拒絕讓 /dev/mem 碰它。現代核心的 CONFIG_STRICT_DEVMEM（以及更進一步的 CONFIG_IO_STRICT_DEVMEM）選項，就是把這道守門 機制收得更緊：開啟之後，/dev/mem 預設拒絕存取一般 RAM、甚至拒絕存取已經配給其他驅動的 MMIO 區段，只放行少數 已知安全的例外——例如 x86 上即使開了 STRICT_DEVMEM，低於 1MB 的 System RAM 仍然允許被 mmap，這是為了相容某些 需要讀取開機時 BIOS 資料區的傳統使用情境而保留下來的例外。另外有一個相關但不同層次的保護是 mmap_min_addr（可透過 /proc/sys/vm/mmap_min_addr 查看／調整）：它限制誰能映射靠近 位址 0 附近的區域，主要是為了防堵「核心端 NULL 指標解參考」配合使用者端刻意映射位址 0 的提權攻擊手法。

devmem_is_allowed() 守門函式　核心裡決定「這段實體位址到底准不准被 /dev/mem 存取」的檢查函式，依靠 region_intersects／iomem_is_exclusive 判斷該段是否是被其他驅動獨占的一般系統記憶體；CONFIG_STRICT_DEVMEM 開啟後，它會拒絕絕大多數對一般 RAM 的存取請求。

把 /dev/mem 放進整個「記憶體相關檔案家族」裡比較會更清楚它的定位：/proc/iomem 是「地圖」， 列出整個實體位址空間目前被誰、用來做什麼（哪一段是 System RAM、哪一段是某張裝置的 MMIO、哪一段是保留區）， 一般使用者跟 root 看到的詳細程度不同（root 能看到完整的位址範圍，一般使用者只能看到被模糊化的資訊）； /dev/kmem 概念上是 /dev/mem 的「虛擬位址版本」——透過核心自己的虛擬位址而不是實體位址存取記憶體， 但因為風險更高、實用價值又低，已經在多數現代主線核心裡被移除；vmcore（kdump 機制產生）則是 「崩潰當下那一刻」的靜態記憶體快照，拍完照之後內容就不會再變，跟 /dev/mem 這種「運行中系統的即時動態映像」 在時間軸上完全是兩種東西。

這個主題跟 CS:APP 的對照其實非常直接：CS:APP 第 9 章用整整一章建立「虛擬位址空間」這個抽象，告訴你作業系統 怎麼用 page table 把每個行程的位址翻譯藏起來，讓每個行程以為自己獨佔一整塊連續記憶體；/dev/mem 則是這整套抽象 故意被打開的一個後門，讓你繞過翻譯這一層，直接用實體位址操作記憶體——理解了 /dev/mem，其實也等於從反方向驗證了 一次「虛擬記憶體這層抽象到底在隔離什麼」。實務上，/dev/mem（或包著它的工具如 devmem2）在嵌入式 開發、裝置驅動偵錯裡很常見，用來直接戳某個周邊裝置的 MMIO 暫存器做快速驗證；但在一般伺服器或雲端環境裡， /dev/mem 幾乎被視為頭號資安風險面——它等於繞過了核心所有的存取控制與行程隔離，所以是 kernel lockdown （安全開機模式）第一個要擋下的攻擊面之一，也是許多雲端供應商直接在 kconfig 編譯時就關掉它的原因。

🔢 數學推導

jserv 筆記裡那些看起來隨意挑選的實體位址，其實都暗藏一條硬性規則：mmap() 系統呼叫規定 offset 參數必須是系統分頁大小（絕大多數平台是 4KB = 0x1000）的整數倍，否則呼叫會回傳 EINVAL。原因在於 MMU 的分頁機制一次只能映射「整頁」，無法從某一頁中間開始映射——分頁是硬體位址 翻譯的最小單位，硬體壓根沒有「半頁映射」這種操作。驗證一下筆記裡出現的數字：0x2C0000000 換算成 二進位，最低 12 個位元（對應 4KB = 2¹² 的頁內偏移）全部是 0，確實是 4KB 整數倍，合法；0x34000000 與 0x34004000 同樣低 12 位全 0，也合法，而兩者差值 0x4000 換算成十進位是 16384 bytes，剛好是 4KB 的 4 倍（4 個分頁），這代表 master.c／slave.c 範例裡的兩段映射之間，剛好留了 4 個分頁的距離， 不會互相重疊。這也是為什麼在真實情境裡，透過 /proc/iomem 或 /proc/kallsyms 找到的「想要存取的位址」，使用前 通常得先手動對齊到最近的頁邊界（addr & ~(PAGE_SIZE-1)），再用頁內偏移量去修正最終要讀寫的 位置，否則 mmap 這一步會直接失敗。
