差分陣列 Difference Array，區間加值的 O(1) 攤還技巧（全新分類）

今天要介紹的是「差分陣列」（Difference Array），處理的問題家族是：給一個長度為 n 的陣列，接下來有一大堆「把區間 [l, r] 內每個元素都加上 val」的操作，最後才一次性詢問整個陣列或某幾個位置的值。LeetCode 370、1109、1854、2251 是這個家族由基礎到進階的四個代表：370（Range Addition）是最純粹的教科書版本、1109（Corporate Flight Bookings）把情境換成航班座位、1854（Maximum Population Year）把「區間」換成人的出生到死亡年、2251（Number of Flowers in Full Bloom）則把座標範圍一路放大到逼近差分陣列技巧失效的邊界，正好用來示範這招什麼時候該退場。

先看暴力解法的代價：如果每次「區間加值」都真的走訪 [l, r] 裡的每一格去加 val，q 次操作、每次最多碰到 n 個格子，總時間是 O(n·q)；370、1109 的 n、q 都可以到 10^4 量級，O(n·q) 會到 10^8，單次測資通常還能擠過去，但如果 q 再大一個量級（例如 1109 的真實測資把 bookings 數放到 2×10^4、flights 放到 2×10^4），就會逼近超時邊界，而這正是差分陣列存在的理由。

差分陣列的核心想法是：不要在「操作發生的當下」就去修改整段區間，而是只在區間的兩個端點留下記號，把真正的加總計算延後到最後一次性處理。具體做法是另開一個輔助陣列 diff，對每個「把 [l, r] 加上 val」的操作，只做兩件事：diff[l] += val、diff[r+1] -= val（如果 r+1 超出陣列範圍就直接省略這一步）。每次操作都是 O(1)，q 次操作總共 O(q)。等所有操作做完後，對 diff 陣列做一次前綴和（diff[i] += diff[i-1]），得到的 diff[i] 就正好是原陣列在位置 i 累積加總後的值——這一步是 O(n)。

差分陣列與前綴和是一對逆運算　前綴和陣列是原陣列「相鄰元素兩兩相減」得到的；差分陣列的設計恰好相反：你直接在差分陣列上動手（只改兩個端點），再對差分陣列做前綴和，就「還原」出被整段修改過的原陣列。可以把它想成：前綴和負責「展開」，差分負責「編碼」，兩者互為反函數，這也是為什麼差分陣列有時候也被稱為「前綴和的逆運算」。

這招可以自然延伸到二維：給一個矩陣，操作是「把某個子矩形區域全部加上 val」，最後要還原整個矩陣。做法是在二維差分陣列上，對每個操作只動四個角：diff[r1][c1] += val、diff[r2+1][c1] -= val、diff[r1][c2+1] -= val、diff[r2+1][c2+1] += val，最後對整個矩陣做二維前綴和還原。這個「四角加減」的推導跟一維版本同構，只是從一次相減變成二次（容斥）相減，常見於 LeetCode 2536、2132 這類矩形區域更新題。

差分陣列有一個關鍵的適用邊界：座標範圍必須小到可以直接開一個長度等於座標上限的陣列。370 跟 1109 的座標（陣列索引、航班編號）本身就是連續小範圍整數，直接套用沒問題；1854 的「年份」雖然語意上是日期，但題目限定在 1950–2050 之間，範圍只有 101，一樣可以直接開陣列硬做差分。但 2251 的「天數」可以到 10^9 這個量級，如果還硬開一個長度 10^9 的差分陣列，記憶體直接爆掉——這時必須先做座標離散化，只保留真正出現過的那些開始/結束時間點，把一大堆「事件」排序後掃過去（也就是把差分陣列的精神換成排序＋掃描線，或是先排序後對每個查詢做二分搜尋），這正是 2251 官方解法採用「排序 start/end 陣列 + 二分搜尋」而不是真正開一個差分陣列的原因。

座標壓縮（Coordinate Compression）　當資料的「座標值」範圍遠大於資料「個數」時（例如座標到 10^9 但只有 10^4 個事件點），直接開對應大小的陣列不可行；座標壓縮把所有真正出現過的座標值排序、去重，重新編號成 0, 1, 2, ...，之後所有運算都在這組編號後的小範圍裡進行，再在輸出時換算回原始座標。差分陣列、線段樹、樹狀陣列遇到座標範圍過大時，幾乎都要先做這一步才能用。

常見的邊界陷阱是端點位置算錯一格：「把 [l, r] 加 val」對應的是 diff[l] += val、diff[r+1] -= val，很多人會寫成 diff[r] -= val，少了那個 +1，相當於把 r 這個位置本身也被減掉、效果變成只加到 [l, r-1]；另外要記得判斷 r+1 是否超出陣列邊界，超出就整個跳過那一行，不要真的去寫入不存在的格子。

這類「大量區間更新、最後統一結算」的模式在實務上非常常見：像是訂房系統統計每天有多少房間被佔用（1109 的原型）、CDN 或 API gateway 統計每個時間片的併發連線數、或是排班系統統計每個時段有多少人上班——這些場景的共同特徵是「更新頻繁、但查詢可以延後到批次結算」，正好對應差分陣列「犧牲即時查詢換取 O(1) 更新」的設計取捨，也是面試官喜歡拿來追問系統設計取捨的切入點。

370 Range Addition
差分陣列最純粹的教科書版本：給 updates = [[l, r, val], ...]，求所有操作套用後的最終陣列。時間 O(n+q)，空間 O(n)。
1109 Corporate Flight Bookings
370 的應用版：bookings[i] = [first, last, seats]，座標（航班編號）範圍小且連續，直接套用一維差分陣列，時間 O(n+q)。
1854 Maximum Population Year
出生年 +1、死亡年當天 -1（死亡年不計入人口），年份範圍題目限定在 1950–2050（僅 101 個值），差分＋前綴和後找最大值對應的最早年份，時間 O(n+range)。
2251 Number of Flowers in Full Bloom
座標（天數）範圍可達 10^9，無法直接開差分陣列，改用排序 start/end 時間點 + 對每個查詢做二分搜尋（或等價的事件掃描線），時間 O((n+m) log n)。
🔢 數學推導

設陣列長度為 n，共有 q 次「區間加值」操作。暴力解法每次操作要走訪整段區間，最壞情況下每次碰到 O(n) 個格子，總時間 O(n·q)；差分陣列把每次操作的代價壓到 O(1)（只動兩個端點），q 次操作共 O(q)，最後再花一次 O(n) 做前綴和還原，整體時間降為 O(n + q)。當 n、q 都是 10^4～10^5 等級時，O(n·q) 可能來到 10^8～10^10，而 O(n+q) 只有 10^4～10^5，差距是數量級的，這就是為什麼題目一旦出現「大量區間更新＋最後才查詢」的字樣，就要優先想到差分陣列而不是逐格修改。

差分陣列「正確還原」的證明可以用telescoping（逐項相消）解釋：對差分陣列做前綴和後，位置 i 的值等於 Σ_{k=0}^{i} diff[k]。每個操作 (l, r, val) 貢獻給這個總和的部分是：若 i < l，兩筆記號都還沒被加總進來，貢獻 0；若 l ≤ i ≤ r，只有 diff[l] += val 這筆被加總進來（diff[r+1] -= val 還在 i 之後，尚未加總），貢獻恰好是 val；若 i > r，兩筆記號都已經被加總進來，+val 與 -val 互相抵消，貢獻變回 0。這正好符合「只有 [l, r] 範圍內的位置被加上 val、範圍外不受影響」的語意，而且這個論證對任意多筆疊加的操作都線性成立（總和的線性性），所以可以放心把所有操作的 diff 貢獻直接疊加再一次性前綴和，不需要分別處理每筆操作的影響範圍。

NOTE · 補充

面試官常見追問：

  • 「如果操作跟查詢是交錯進行的（不是全部更新完才查），差分陣列還能用嗎？」——不能直接用，因為差分陣列的「前綴和還原」要等所有更新都做完才有意義。這時要換成支援「區間更新、單點查詢」或「區間更新、區間查詢」的樹狀陣列（Fenwick Tree）／線段樹 + Lazy Propagation（本頻道 09-09、10-03 教過），用 O(log n) 的更新/查詢換取即時性，犧牲一點時間複雜度換取線上處理能力。
  • 「如果區間加的不是固定值，而是『等差數列』（例如每個位置加的值依位置遞增）怎麼辦？」——這是差分陣列的進階變形「二階差分」：對差分陣列再做一次差分，可以用 O(1) 處理「區間內每個位置加上一個以 l 為起點、固定公差遞增的等差數列」這種更複雜的更新，還原時需要連續做兩次前綴和。
  • 「座標範圍太大時，除了座標壓縮，還有什麼思路？」——如果操作本身具有某種單調性（例如本例的「人口」隨時間只會因為一次出生、一次死亡而改變），也可以直接用事件排序＋掃描線（Sweep Line，本頻道 10-05 教過）而不產生中間陣列，這跟差分陣列骨子裡是同一種「只在關鍵點記錄變化量」的思想，只是省掉了陣列這個中間表示。

變形模式整理：(1) 區間更新＋最終一次性查詢 → 一維/二維差分陣列；(2) 區間更新＋交錯的即時查詢 → 樹狀陣列/線段樹；(3) 座標範圍過大 → 座標壓縮或排序＋掃描線／二分搜尋。

Ch.4　4.5.3 Rearranging and Relabeling Signals

11/18 教的 4.5.1（SEQ+）只是把 SEQ 的邏輯順序重新排列、不改變行為；11/19 教的 4.5.2 動手插入了 F、D、E、M、W 五個管線暫存器，把一條長組合邏輯路徑切成五段，但得到的 PIPE- 還只是「機械式插入暫存器」的半成品。4.5.3 接著處理一個在 PIPE- 裡才真正浮現的新問題：同一時刻管線裡同時有五條指令在跑，於是像 icode、valA、dstE 這類在 SEQ 裡「全域只有一份」的訊號，到了 PIPE 裡會同時存在五份不同的版本——分別屬於正在 Fetch、Decode、Execute、Memory、Write-back 的那五條指令。如果繼續用同一個裸名字 icode 來稱呼這五個不同的物理訊號，整張硬體圖跟後續的 HCL 程式碼會完全無法分辨「現在講的是哪一條指令的 icode」。

4.5.3 解決這個歧義的方法，是引入一套系統化的訊號命名慣例：凡是直接從某個管線暫存器輸出的訊號，用那個暫存器的「大寫字母」當字首，例如 D_icode 表示「D 暫存器裡存著的 icode」（也就是上一個週期 Fetch 階段算出來、現在交給 Decode 階段使用的那個 icode）、E_valC 表示「E 暫存器裡存著的 valC」。凡是在某個階段內部由組合邏輯重新計算出來的訊號，則用那個階段的「小寫字母」當字首，例如 d_srcA 表示「Decode 階段依據 D_icode、D_rA 等暫存器輸出，用組合邏輯算出來的 srcA」、e_valE 表示「Execute 階段的 ALU 算出來的 valE」。這套字首規則貫穿整本書後面所有 PIPE 相關的硬體圖與 HCL 程式碼，一看字首就知道這個訊號是「某暫存器鎖住的舊值」還是「這個階段剛算出來的新值」。

大寫字首 vs 小寫字首　X_signal（大寫）＝直接讀自管線暫存器 X 的輸出，是「已經鎖存、本週期不會再變」的穩定值；x_signal（小寫）＝階段 x 內部組合邏輯剛算出的「本週期新鮮出爐」的值，下一個時脈上升緣才會被某個暫存器收進去變成下一階段的 X_signal。同一個邏輯訊號（例如 valA）會隨著指令往下游移動，依序被稱為 d_valA → D_valA（搬進下個階段前）→ 在下一階段若被原樣往下傳，又會變成 e_valA 或直接沿用 E_valA，每往前一階就換一次字首。

除了重新命名，4.5.3 也配合這套命名規則微調了一些訊號在哪個階段被計算：有些在 PIPE- 草稿裡暫時放在「不自然」階段的邏輯，會被挪到更合理的階段，目的是讓每個階段的組合邏輯深度更平均（呼應昨天提到的「希望 T_PIPE 由最慢的那一階段決定，所以要盡量把各階段延遲拉平」），也讓命名時「這個訊號屬於哪個階段」更直觀、不會出現「D 階段卻在算一個聽起來像 E 階段才該做的事」的違和感。

一個貫穿多個階段、很適合用來說明這套命名法的例子是 valP（predicted PC，Fetch 階段預測的下一條指令位址）。像 call 指令需要把 valP（也就是 call 之後緊接著的那條指令位址，當成返回位址）寫進記憶體的堆疊，而「寫進記憶體」是 Memory 階段才做的事——這代表 valP 必須原封不動地從 Fetch 一路「搭便車」經過 Decode、Execute，才能在 Memory 階段被用到。沿途它會依序被稱為 f_valP（Fetch 階段算出）、鎖進 F register 後變成要傳給 Decode 的輸入、在 Decode 階段內部可能被稱為 d_valP（但這裡通常原樣直接傳遞，沒有額外運算）、鎖進 D register 變成 D_valP，以此類推一路到 M_valP 才真正被存入記憶體。這種「值不變、但要跟著指令一路被重新命名、一路佔用每個管線暫存器的一塊空間」的現象，正是 4.5.2 提到「暫存器要夠寬」的具體範例，也是 4.5.3 命名法存在的必要性：沒有這套字首規則，你完全沒辦法在 HCL 或硬體圖上分辨「現在這個 valP 是哪個階段的」。

valP（Predicted PC）　Fetch 階段依據目前抓到的指令型態「猜」出來的下一條指令位址（大多數情況就是 PC + 指令長度；對 call／jmp 則猜測跳轉目標）。它不只是「下一個 PC」，call 指令還需要用它當作返回位址寫進堆疊，所以它必須被完整地搭便車帶到 Memory 階段，是後面 4.5.4（Next PC Prediction）要深入檢討「猜錯了怎麼辦」的鋪墊訊號。

這套命名規則表面上只是排版/文件上的方便，但它直接服務於後面幾節要解決的真正難題：4.5.4 的下一個 PC 預測、4.5.5 的管線危障，都需要精確指出「我要比較的是 e_dstE 這個剛算出來、還沒鎖進暫存器的值，還是 M_dstM 這個已經在 Memory 階段、確定不會再變的值」——資料前送（forwarding）邏輯的正確性完全建立在「能精確分辨每個訊號屬於哪個階段、是舊值還是新值」這個基礎之上，而這正是 4.5.3 要先立好的規矩。對準備系統設計／電腦架構面試的人來說，這套命名習慣也是閱讀真實 CPU 驗證文件、閱讀教科書對應的 HCL 原始碼（pipe-stages.hcl）時最先需要「破譯」的慣例，不先弄懂它，後面看管線前送的邏輯公式會完全不知道每個變數指的是哪個時間點的值。

Linux 核心的裝置驅動程式介面與模型（Driver Model）：struct device／device_driver／bus_type 與 probe 配對流程

成大 Linux 核心課程進度表 Week 13 在教完「C 語言的 Stream I/O、EOF 判斷與例外處理」「CS:APP 第 10 章重點提示：Unix I/O」（11/18、11/19 已教過）之後，緊接著的下一個條目是「Linux: 裝置驅動程式介面和模型」。這個主題把視角從「核心怎麼對使用者空間呈現 I/O」（Unix I/O、fd）往下拉一層，看核心內部怎麼統一管理成千上萬種異質裝置（PCI 卡、USB 裝置、I2C 感測器、platform device……）——如果每種匯流排都各自發明一套裝置／驅動程式配對邏輯，核心會充滿重複又互不相容的程式碼，這正是 Linux Driver Model 要解決的問題：提供一套跨匯流排共用的資料模型與介面。

這套模型的三個核心結構是 struct device、struct device_driver、struct bus_type。struct device 代表「一個裝置實體」，通常不會單獨配置，而是被內嵌進各匯流排專屬的結構裡（例如 struct pci_dev 內嵌一個 struct device dev），核心官方文件特別強調這個內嵌是靜態配置、「只在裝置被發現時配置一次」，而且一般裝置驅動程式不該直接碰這個內嵈欄位，應該透過 bus 提供的介面存取，避免跨層亂轉型。struct device_driver 代表「一整個驅動程式」（不是某一個裝置實體），必須至少初始化 name 與 bus 兩個欄位，並提供 probe、remove、suspend、resume 等回呼函式；它也維護一份 devices 清單，記錄目前有哪些裝置已經綁定到這支驅動程式上。struct bus_type 則代表一種匯流排（PCI、USB……），必須初始化 name，並可選擇性提供 match 回呼——這個 match 正是「怎麼判斷某個驅動程式支不支援某個裝置」的關鍵掛鉤。

三者的配對流程是：匯流排驅動程式初始化時呼叫 bus_register() 把自己登記進全域的匯流排清單；裝置驅動程式透過匯流排專屬的註冊函式（例如 pci_driver_register()）向對應的 bus 登記；這時 bus 會走訪自己維護的裝置清單，對每一個「目前還沒配對到驅動程式」的裝置呼叫自己的 match() 回呼，拿驅動程式宣告的裝置 ID 表（例如 PCI 的 vendor/device ID）跟裝置實際回報的 ID 比對；一旦比對成功，driver core 就呼叫這支驅動程式的 probe()，把裝置與驅動程式正式綁定起來。整個過程中，裝置 ID 的格式與比對語意刻意設計成「完全匯流排專屬」——因為 PCI 用 vendor/device ID、USB 用 vendor/product ID、platform bus 用名稱字串或 device tree 的 compatible 屬性，彼此格式天差地別，統一模型的做法不是硬把這些格式塞進同一種表示，而是把「比對」這個動作抽象成一個可替換的回呼，讓每種 bus 自己決定怎麼比對，同時仍共用同一套 device／driver／probe 生命週期管理。

probe() 的執行環境　官方文件明確指出 probe() 是在 process context（而非中斷環境）被呼叫，且呼叫時這個 bus 的 rwsem 鎖已經被持有、驅動程式與裝置處於「部分綁定」狀態。驅動程式通常會用 container_of() 把傳入的 struct device *dev 轉型回匯流排專屬的型別（例如 struct pci_dev）以取得資源資訊，完成硬體初始化後用 dev_set_drvdata() 把自己配置的狀態結構掛回 dev，成功回傳 0、失敗回傳負的 errno 並釋放已配置的資源。

一個 probe 階段特別值得深入的機制是 EPROBE_DEFER（延後探測）：如果驅動程式在 probe() 裡發現自己依賴的資源（例如某個 GPIO、clock、regulator）還沒就緒——通常是因為提供那個資源的另一支驅動程式還沒 probe 完——可以回傳 -EPROBE_DEFER，driver core 會把這個裝置放進一份「延後清單」，等之後有新的驅動程式成功 probe（代表依賴關係可能已經解開）時再重新嘗試。這個機制解決了「驅動程式初始化順序無法在編譯期完全確定」的問題：核心不需要事先知道正確的依賴拓樸順序，而是靠「失敗就先跳過、之後再重試」這種樂觀重試策略逐步收斂。但官方文件也特別警告一個陷阱：如果 probe() 已經建立了子裝置（child device）才回傳 -EPROBE_DEFER，下次重試時那些子裝置可能會被重複建立，導致無窮迴圈——這對應到今天主線提到的「系統化規則」主題的另一面：規則本身很系統化，但使用規則的人（驅動程式作者）還是要留意規則背後沒說清楚的操作順序陷阱。

這整套 device／driver／bus 的階層關係，也完整反映在 sysfs 上：每當一個裝置被插入樹狀結構，核心就會在 /sys 下幫它建立一個目錄；全域層會自動加上 name、power 這類通用檔案，bus 層（例如 PCI）會加上 irq、resource 這類匯流排專屬檔案，裝置驅動程式自己還可以再加上裝置特有的屬性檔案。同時每個 bus 在 /sys/bus// 底下都有自己的 devices、drivers 兩個目錄，devices 裡放的是指向實際裝置目錄的符號連結，drivers 則列出目前登記在這個 bus 下的所有驅動程式——這也是為什麼在真實系統上執行 ls /sys/bus/pci/drivers/ 可以直接看到目前載入的 PCI 驅動程式清單，這是 driver model 的設計直接外顯成使用者可觀察的檔案系統介面，不需要額外工具就能偵錯「這個裝置到底被哪支驅動程式接管」。

再往底層看一層，struct device、struct device_driver、struct bus_type 這些結構之所以都能「自動」在 sysfs 底下有一個目錄、都有 reference count，背後共用的基礎設施是 kobject／kset：每個 kobject 對應 sysfs 裡的一個目錄節點，並透過內嵌的 kref 做參照計數管理生命週期；kset 則是一組 kobject 的容器，通常對應 sysfs 裡的一層目錄結構。driver model 的 device、driver、bus 三個結構內部都內嵌了 kobject，等於是在這層通用的「目錄樹 + 參照計數」基礎設施之上，再疊加一層「裝置／驅動程式／匯流排」專屬語意——這跟昨天 CS:APP 4.5.3 用「字首命名規則」在底層硬體訊號之上疊加一層可讀語意，是同一種「先有通用基礎設施、再疊加領域專屬規則」的分層手法。

理解 driver model 是後續除錯「裝置沒被正確接管」（dmesg 看不到 probe 成功訊息、驅動程式有載入但裝置節點沒出現）的起點，也是成大課程表接下來幾個主題（「如何避免在嵌入式 Linux 上自己寫驅動程式」「用 GDB 偵錯嵌入式裝置」「Device Tree」）的共同基礎：Device Tree 的 compatible 屬性，說穿了就是 platform bus 的 match() 用來比對裝置與驅動程式的其中一種具體實作方式。這也是系統設計與韌體相關面試裡常被追問的題目：「為什麼有時候改了 Device Tree 卻發現驅動程式還是沒 probe 成功？」答案往往就藏在 compatible 字串比對失敗、或是依賴的資源驅動程式還沒就位卻沒有正確回傳 -EPROBE_DEFER 這類細節裡。

struct bus_type {
	const char		*name;
	const char		*dev_name;
	const struct attribute_group *const *bus_groups;
	const struct attribute_group *const *dev_groups;
	const struct attribute_group *const *drv_groups;

	int (*match)(struct device *dev, const struct device_driver *drv);
	int (*uevent)(const struct device *dev, struct kobj_uevent_env *env);
	int (*probe)(struct device *dev);
	void (*sync_state)(struct device *dev);
	void (*remove)(struct device *dev);
	void (*shutdown)(struct device *dev);
	const struct cpumask *(*irq_get_affinity)(struct device *dev,
			unsigned int irq_vec);

	int (*online)(struct device *dev);
	int (*offline)(struct device *dev);

	int (*suspend)(struct device *dev, pm_message_t state);
	int (*resume)(struct device *dev);

	int (*num_vf)(struct device *dev);

	int (*dma_configure)(struct device *dev);
	void (*dma_cleanup)(struct device *dev);

	const struct dev_pm_ops *pm;

	bool driver_override;
};
