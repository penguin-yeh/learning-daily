Aho-Corasick 自動機：多模式字串匹配

今天跳出最近 14 天內反覆出現的分類（Trie 進階、Reservoir Sampling、Tree DP、Sliding Window、加權區間排程、Z-function、LFU Cache、歐拉路徑），改教一個全新但跟上週（11/04）Trie 進階應用一脈相承的主題：Aho-Corasick 自動機（AC automaton），用來解決多模式字串匹配（multi-pattern matching）問題——給定一段文本與一整組模式字串（可能有成千上萬個），要在一次掃描裡找出文本中所有出現過的模式。這類問題在實務上非常常見：敏感詞／關鍵字過濾系統、防毒軟體的病毒碼比對、IDS/IPS 的封包特徵比對、DNA 序列裡同時搜尋多段已知基因片段，都是同一個問題的變形。

先回顧已知工具：對單一模式字串，我們教過 KMP（09/12、09/15）跟 Z-function（11/15），都能在 O(n+m) 內完成比對，核心技巧是用一個「失配函式」避免比對失敗時整個從頭重來。但如果有 k 個模式字串，直覺做法是把每個模式各自跑一次 KMP，總時間變成 O(n·k + M)（M 為所有模式長度總和）——當 k 很大（例如上萬條敏感詞）時，n·k 這個因子會直接讓系統撐不住。Aho-Corasick 自動機的目標，就是把「對 k 個模式各跑一次」壓成「對整組模式只掃一次文本」，關鍵是把 11/04 教過的 Trie 拿來當骨架。

建構第一步：把所有模式字串塞進一棵 Trie。每個模式字串對應 Trie 上從根到某節點的一條路徑，共享前綴的模式會共用路徑上的節點。這一步跟 11/04 教的 Trie 進階應用完全一樣，差別在於 AC automaton 不只用 Trie 做「有沒有這個前綴」的查詢，還要替每個節點額外接上一條失配指標（fail link）——這正是把 KMP 的 failure function，從「一條字串」推廣到「一整棵 Trie」。節點 v 的 fail(v) 定義為：Trie 上「代表字串是 v 所代表字串的最長『真後綴』」的節點。

Failure Function（失配函式）　KMP 裡失配函式 fail[i] 回答「比對失敗時，最長能沿用的已匹配前綴是多長」；AC automaton 把同一個概念從一維陣列推廣到整棵 Trie：每個節點的 fail 指標回答「這個節點代表的字串，最長的『同時也是某個模式的前綴』的真後綴，對應到 Trie 上哪個節點」。兩者的本質完全相同，只是後者要處理分支。

fail 指標要怎麼算？用 BFS 按 Trie 的深度一層層算：根節點與深度 1 節點的 fail 指標直接指回根；對深度 ≥2 的節點 v（父節點 p，邊上字元 c），先看 fail(p) 是否有字元 c 的出邊——若有就指過去，若沒有就繼續沿著 fail(fail(p)) 一路往上找，直到找到有 c 出邊的節點或退回根為止。這跟 KMP 建 failure function 時「比對失敗就退回 fail[j-1] 再試一次」的遞迴結構完全一致，只是在 Trie 上做。這一步做完後，整個自動機就變成一個完整的有限狀態機（DFA）：對任何字元，每個節點都有唯一的下一個狀態（原生邊或沿 fail 指標補齊的邊）。

Dictionary Suffix Link（輸出連結）　一個節點可能同時是好幾個模式字串的結尾（例如模式 "she" 與 "he" 共享結尾），而且一個節點的 fail 鏈往上追，可能會經過「別的模式的結尾節點」。AC automaton 額外維護一條「輸出連結」（有時直接複用 fail 指標），在到達某個節點時，要沿這條鏈把所有「掛在這條鏈上」的模式都視為命中，不能只看當前節點本身是不是某個模式的結尾。

比對階段才是這個自動機真正省時間的地方：掃描文本時，若當前字元在目前節點沒有對應的子節點，就沿 fail 指標往上退，退到某個有該字元出邊的節點（或根）為止，再往下走一步——這跟 KMP 比對失敗時的退回動作是同一招。為什麼整體還是攤銷 O(n)？因為可以定義一個「位能」φ=目前自動機狀態的深度：每吃進一個字元、成功往下走一步，φ 最多 +1；每沿 fail 指標退一步，φ 至少 -1。φ 的總增加量被文本長度 n 卡住（每個字元最多貢獻一次 +1），所以沿 fail 指標的退回次數總和也被 n 卡住——詳細算式見下方數學推導。

攤銷分析（Amortized Analysis／位能法）　位能法（potential method）是攤銷分析的標準工具：挑一個隨資料結構狀態變化的「位能函式」φ，若每次操作的實際代價，有一部分可以用「φ 的下降量」去抵銷，就能證明總代價被總的 φ 上升量卡住。這裡的 φ=自動機狀態深度，是同一套論證在 KMP 攤銷分析（09/12 教過）裡就用過的技巧，AC automaton 只是原封不動搬過來用。

Edge case：(a) 字母集很大（例如 Unicode）時，每個節點用固定大小陣列存邊會爆記憶體，改用 hashmap 存邊，攤銷複雜度不變但常數變大；(b) 模式字串之間互為子字串（如 "he" 是 "she" 的子字串）時，一定要靠上面的輸出連結正確收集，否則會漏掉命中；(c) 模式字串重複或為空字串，建構時要先去重、空字串通常直接排除（否則每個位置都會「命中」）；(d) 文本是極端重複字元（如 "aaaa...a"）時雖然 fail 鏈可能很深，但攤銷論證保證退回總次數仍是 O(n)，這是最容易被誤判成「退化成 O(n²)」的地方，必須靠位能法才能說清楚為什麼不會退化。

複雜度比較：brute force／對每個模式各跑一次 KMP 是 O(n·k + M)；Aho-Corasick 建構 O(M)（或用陣列轉移表是 O(M·Σ)，Σ 為字母集大小）加上比對 O(n + z)（z 為命中次數），總計 O(M + n + z)——完全不含 k 這個因子，這正是當模式數量很多時的決定性差異。詳細推導見下方。

常見變形模式至少兩種要記住：①串流版（Online）——LeetCode 1032. Stream of Characters 就是反過來用：先用所有模式建好 AC automaton，資料不是一次給全部文本，而是一個字元一個字元陸續進來，每進來一個字元就在自動機上走一步，用「目前狀態是否落在某個模式的結尾（或其輸出鏈上）」判斷「目前為止收到的字元，是否以某個模式作結尾」——不需要重新掃描歷史資料；②索引收集版——1065. 面試官常見追問：「為什麼不直接對每個模式跑一次 KMP？」——答案就是上面 O(n·k) 那個 k 因子，當 k 很大時完全不可行；「fail 指標跟 KMP 的 failure function 本質上是同一個東西嗎？」——是，AC automaton 可以理解成「把 KMP 的 failure function 從一條字串推廣到一整棵 Trie」；「如果模式會動態增減怎麼辦？」——AC automaton 本質是離線結構，模式變動通常需要重建整棵自動機（或用更複雜的動態資料結構），這也是為什麼 1032 題的解法是「先建好自動機、資料流只對文本方向增量」而不是反過來；「空間複雜度能不能再壓？」——用 hashmap 取代固定陣列存邊，或把 Trie 節點池改成更緊湊的表示（如 double-array trie）。

🔢 數學推導

Brute force 的時間複雜度：設文本長度為 n，共有 k 個模式字串，長度分別是 m₁,…,m_k，總長度 M=Σmᵢ。對每個模式各跑一次 KMP（建 failure function O(mᵢ) + 掃描 O(n+mᵢ)），單個模式花 O(n+mᵢ)，k 個模式總共 O(Σ(n+mᵢ)) = O(k·n + M)。當 k 很大（例如 k~10⁴ 個敏感詞、n~10⁶ 的長文本）時，k·n 這一項是真正的瓶頸，M 相對很小。

Aho-Corasick 的時間複雜度：建構 Trie 本身是 O(M)；用 BFS 建 fail 指標時，表面上每個節點要「沿 fail 鏈往上找」，但可以證明：對固定深度 d 的節點，它往上追的鏈長總和被攤銷到 O(1) 每節點（跟 KMP 建表的攤銷論證同構），所以整棵 fail 指標的建構也是 O(M)（若用陣列轉移表則要乘上字母集大小 Σ，變成 O(M·Σ)，這是空間換時間的常見取捨）。比對階段用位能法 φ=目前狀態深度：n 個字元總共最多讓 φ 增加 n 次（每個字元恰好一次「往下走」的機會），而每一次沿 fail 指標退回都讓 φ 嚴格減少至少 1，所以「退回」這個動作的總次數 ≤ φ 的總增加量 ≤ n，因此比對階段是 O(n) 再加上「報告命中」的 O(z)（z 為實際命中次數，可能遠小於 n²）。總結：Aho-Corasick 總時間 O(M + n + z)，少掉了 brute force 裡的 k·n 這一項——這正是模式數量 k 越多、AC automaton 相對優勢越大的根本原因。

Ch.4　4.5.1 SEQ+: Rearranging the Stages of SEQ

昨天（11/17）教完 §4.4 General Principles of Pipelining，把「流水線化」這件事講成一般原理：把一個長的組合邏輯電路切成多段，每段之間插暫存器，讓不同指令可以同時停在不同階段，藉此提高吞吐量。今天正式進入 §4.5 Pipelined Y86-64 Implementations，從它的第一個子節 4.5.1 SEQ+: Rearranging the Stages of SEQ 開始。這一步的重點是：它本身完全不是流水線化，而是在真正插暫存器之前，先對 §4.3 教過的 SEQ（單週期順序實作）做一次純邏輯上的「重新安排」，把電路改造成「容易被切」的形狀。

先回顧 SEQ 的時序行為：SEQ 把一條指令的執行拆成 Fetch、Decode、Execute、Memory、Write back 五個邏輯階段，外加一個 PC update——在每個時鐘週期裡，前五個階段用「這個週期開始時 PC 暫存器裡的值」去抓指令、算出結果，而 PC update 則是在本週期尾端，根據本週期 fetch／decode 出來的資訊（icode、valC、valP、分支是否成立的 Cnd 等）算出「下一個週期要用的新 PC」，再把它存回 PC 暫存器。這裡藏著一個跨週期的資料相依：下個週期一開始的 Fetch，要用到的新 PC，是上個週期最後才算完的值。

Critical Path（關鍵路徑）　單週期實作（SEQ）的時鐘週期長度，必須至少等於「從本週期 PC 值出發，一路算到下個週期新 PC 值」這條邏輯路徑上，所有邏輯閘延遲加總的最大值——這條最長路徑就叫 critical path。SEQ 的 critical path 要橫跨全部五個邏輯階段加上 PC update 邏輯，所以 SEQ 的時脈週期必然很長，這正是 §4.4 一般原理裡「為什麼要流水線化」的具體動機。

SEQ+ 的改造動作：把「算出新 PC」這段邏輯，從「本週期尾端」整個挪到「下個週期開頭」——也就是說，不是在本週期結束前就把下一個 PC 算好存進暫存器，而是在下個週期一開始，直接用上個週期留下來的那組訊號（icode、ifun、valC、valM、Cnd……）現場算出「現在該 fetch 哪個位址」。這個改動最直接的結果，是書裡講得很白的一句話：SEQ+ 沒有一個獨立、顯式存在的 PC 暫存器——「現在的 PC 是多少」這件事，變成一段用「上一輪留下的訊號組合」即時算出來的值，而不是一個真正被寫入、讀出的暫存器內容。

為什麼這樣重排不會改變任何邏輯行為？這是數位電路設計裡一個標準的手法，叫電路重定時（retiming）——只要不改變邏輯閘之間「誰依賴誰」的資料相依關係，只是把暫存器（狀態邊界）在時序圖上的位置往前或往後挪，整個電路對外表現出來的輸出序列是完全一樣的。SEQ 裡「本週期尾端算新 PC」跟 SEQ+ 裡「下週期開頭算現在的 PC」，算的是同一段組合邏輯、吃的是同一組輸入訊號，只是「這段計算被歸在哪個時鐘週期裡」不同——這跟軟體工程裡把一段運算從函式 A 的尾端搬到函式 B 的開頭（只要輸入不變）不會改變結果，是同一個道理。

更具象地說，SEQ+ 真正改變的是「狀態」這件事的定義。SEQ 的跨週期狀態只有一個：PC 這個暫存器的值。SEQ+ 把這個單一狀態，換成了一整組訊號：icode、ifun、valC、valA、valB、dstE、dstM、valE、valM、Cnd 等——這些原本只是「在 SEQ 一個時鐘週期裡暫時流動」的中間訊號，現在變成「必須真的被記住、留到下個週期」的狀態。這一步非常關鍵：它等於先把「要在哪裡切開」想清楚、把切開後兩邊各自需要哪些資訊列清楚，而 4.5.2（插入管線暫存器）要做的事，其實就是把這組訊號實際放進一顆真正的暫存器裡——4.5.1 是設計決策，4.5.2 才是真正動手實作。

這種「先重新安排計算順序、決定狀態要放在哪裡，才動手真正拆開」的思路，不只是硬體設計的事。軟體工程裡把一個同步函式改寫成可以分段執行的 state machine、coroutine，或是把一個長流程拆成多個非同步階段（pipeline-as-a-service），本質上都在做同一件事：先想清楚「哪些資料要在階段之間被保留下來（狀態）」，再決定要不要、以及在哪裡真正切開執行。改變的永遠是「狀態放在哪裡、什麼時候被讀寫」，不是底層邏輯本身要算什麼。

常見誤解：很多人看到 SEQ+ 這個名字，會誤以為它已經是流水線化（pipelined）的實作。課本特別強調：SEQ+ 仍然是單週期、順序執行的硬體——它每個時鐘週期仍然完整跑完一條指令的所有邏輯，沒有任何兩條指令同時「停」在不同階段，時脈週期長度（critical path）跟 SEQ 基本相同（甚至可能因為訊號重新繞線而略增）。SEQ+ 唯一改變的是「訊號被重新排列、PC 不再是獨立暫存器」，真正的平行處理要等 4.5.2 插入管線暫存器、之後處理冒險（hazard，4.5.5）才算完成。

面試官常見追問：「為什麼流水線化之前要先做這個看似沒用的 SEQ→SEQ+ 轉換？」——因為管線暫存器只能插在兩段組合邏輯之間，如果不先把訊號重新排列，PC 更新邏輯會橫跨在理想的暫存器邊界兩側，變成一段邏輯上「同時屬於兩個不同階段」的訊號，不方便切割；先做 SEQ+ 等於先把邊界畫好。「SEQ+ 跟 SEQ 的時脈週期時間有差嗎？」——理論上差不多，因為 retiming 不改變邏輯閘總深度，只改變這些邏輯被歸進哪個時鐘週期，差異通常只來自訊號繞線距離的微小變化。

🔢 數學推導

§4.4 已經教過一般原理，這裡把它套進今天的情境做一次具體的公式化。設 SEQ 的時脈週期長度為 T_seq，它必須覆蓋從「本週期 PC 值」一路算到「下週期新 PC 值」這條 critical path 上所有邏輯閘延遲的總和，即 T_seq ≥ T_fetch + T_decode + T_execute + T_memory + T_writeback + T_pcupdate（各階段邏輯延遲相加，因為 SEQ 每週期只做一條指令、全部邏輯一次算完，中間沒有暫存器打斷）。吞吐量＝每秒能完成的指令數＝1/T_seq（CPI=1，但 T_seq 很長）。

若把這六段邏輯平均切成 k 個管線階段（理想情況下每段延遲約 T_seq/k），插入管線暫存器後，新的時脈週期T_pipe = max₍階段i₎(Tᵢ) + t_reg（t_reg 為暫存器本身的延遲與時序裕度），理想均分下 T_pipe ≈ T_seq/k + t_reg。穩定狀態下（管線填滿後）吞吐量提升到約 1/T_pipe ≈ k/(T_seq + k·t_reg)——當 k 不太大、t_reg 相對 T_seq/k 很小時，吞吐量近似提升 k 倍。但實務上很難把六段邏輯「切得剛好一樣長」，T_pipe 其實取決於最慢的那一段（max 項），這也是 §4.5 後面（4.5.7、4.5.9）要花篇幅討論「怎麼安排各階段內容、讓它們延遲盡量平衡」的原因——SEQ+ 這一步，正是為了讓「怎麼切」這個問題有一個乾淨的起點：先確定每個邊界上要傳遞哪些訊號，才能談如何讓每段邏輯深度盡量相近。

§01
C 語言的 Stream I/O、EOF 判斷與例外處理

接續 11/16 的「C 語言物件導向程式設計」與 11/17 的「Method Dispatch 與 Data Inheritance」，今天依照成大 Linux 核心課程 Week 13 進度表，進入下一個主題：C 語言的 Stream I/O、EOF 判斷與例外處理（對應 jserv 講義《你所不知道的 C 語言：Stream I/O, EOF 和例外處理篇》）。這個主題把「使用者層的 C 標準函式庫（glibc stdio）」跟「核心如何把硬體例外轉譯成訊號（signal）」兩條線串起來，是銜接 CS:APP 第八章 Exceptional Control Flow 概念與真實系統行為的好例子。

為什麼 getchar() 回傳 int 而不是 char？一個位元組（byte）只有 256 種可能值（0–255），但 getchar() 除了要回傳讀到的資料位元組，還要能回傳一個「讀到檔尾」的特殊訊號 EOF，這個訊號必須跟所有合法資料值都不一樣——具體需要多少位元才夠，見下方數學推導。這直接導致一個真實、平台相依的陷阱：若用 char c = getchar(); 接收，在 x86-64（char 預設有號）上，資料位元組 0xFF 經符號延伸會變成 -1，剛好跟 EOF（glibc 定義為 -1）撞在一起，導致迴圈把合法資料誤判成檔尾、提早結束；在 arm64（ABI 預設 char 為無號）上同一段程式碼反而永遠偵測不到 EOF，變成無窮迴圈。這種「在 x86 測試正常、搬到 ARM 裝置就壞掉」的 bug 在真實專案裡並不少見。

EOF 是一種「狀態」，不是一個「字元」。stdio 把「讀到檔尾」跟「讀取發生錯誤」兩種完全不同的情況，都用同一個回傳值 EOF 表示，必須另外呼叫 feof()／ferror() 才能分辨。一個經典誤用是 while (!feof(fp))：feof() 只有在「已經嘗試讀取過、而且確實碰到檔尾」之後才會變真，永遠慢一步，結果迴圈會多跑一輪、用到上一次讀取失敗產生的垃圾資料；正確做法是直接檢查讀取函式（fgets／fread／scanf 的回傳值）本身。

Sticky EOF　glibc 2.28 之後，stream 一旦進入 EOF 狀態就會「卡住」：即使之後檔案被截斷恢復、或底層檔案描述子又有新資料，stream 仍然會持續回報 EOF，必須明確呼叫 clearerr() 清除旗標才會恢復正常讀取。這跟早期部分實作「每次呼叫讀取都重新判斷」的行為不同，是一個會讓舊程式碼在新版 glibc 上行為改變的細節。

Unix I/O 與 stdio 的分工：底層的 read()／write() 系統呼叫允許short count——你要求讀 4096 bytes，系統可能只給 37 bytes 就回來了（常見於管線、終端機、網路 socket，也可能是訊號打斷造成），這不是錯誤，呼叫者必須自己用迴圈補滿（jserv 筆記裡的 readn 就是這種補齊迴圈）。stdio 的使用者層緩衝區，正是把這些瑣碎的短讀短寫包裝起來，用「多緩衝、少呼叫 syscall」換效能——這也解釋了為什麼 stdout 接到終端機時是行緩衝、接到檔案或管線時變成全緩衝：後者不需要讓人立刻看到輸出，可以攢更多資料再一次性 write()。

處理器例外如何變成 signal：x86-64 上整數除以零，CPU 會丟出一個 divide error fault，核心的 trap handler（如 arch/x86/kernel/traps.c）接到這個硬體例外後，轉譯成 SIGFPE 送給該行程；浮點例外則預設不會觸發任何訊號（IEEE 754 預設是靜默產生 NaN／Inf），除非程式主動呼叫 feenableexcept() 開啟特定浮點例外的 trap。這條「硬體 trap/fault → 核心 handler → 轉成 signal → 送到使用者層 handler」的鏈路，正是 CS:APP 第八章 Exceptional Control Flow 教的內容在真實系統上的落地，也解釋了為什麼同一段 C 程式碼（例如整數除以零）在 x86-64 跟 arm64 上可能有完全不同的行為——這不是 C 語言規格定義的，而是底層硬體 trap 行為加上核心轉譯規則共同決定的。

Trap / Fault / Abort 三種處理器例外　CS:APP 把處理器例外分成同步（synchronous，由目前執行的指令直接造成，如除以零、分頁錯誤）與非同步（asynchronous，跟目前指令無關，如外部中斷）兩大類；同步例外裡又再分 trap（故意觸發，如系統呼叫）、fault（可被核心修復後重新執行該指令，如 page fault）、abort（無法恢復的致命錯誤，如硬體記憶體錯誤）。整數除以零屬於 fault 類別裡的特例：核心無法「修復」它，只能把它轉譯成 SIGFPE 交給使用者層決定怎麼辦。
Async-signal-safe　signal handler 隨時可能在程式執行到任何一行時被插進來打斷，所以 handler 裡只能呼叫一組被標記為「async-signal-safe」的函式（例如 write()），絕對不能呼叫 malloc()、printf() 這類內部維護全域狀態、非 reentrant 的函式，否則可能跟主程式正在進行的呼叫互相破壞內部資料結構。安全做法通常是 handler 裡只設定一個 volatile sig_atomic_t 旗標，真正的處理邏輯留給主迴圈檢查這個旗標時再做。

signal() 本身的語意，依編譯時的 feature test macro 而不同：glibc 在-std=gnu11（GNU 模式）下提供 BSD 語意——handler 安裝後持續有效、被打斷的系統呼叫會自動重啟（即設定 SA_RESTART）；但在 -std=c11 等「嚴格標準」模式下，改用System V 語意——handler 觸發一次後會自動恢復成 SIG_DFL、且不設定 SA_RESTART，被打斷的系統呼叫會直接回傳 -1 並把 errno 設成 EINTR。下方原始碼框裡的 __sysv_signal() 就是這個 System V 語意的實際實作：可以看到它把 sa_flags 設成 SA_ONESHOT | SA_NOMASK | SA_INTERRUPT 後，又明確用 &= ~SA_RESTART 把 SA_RESTART 清掉——這一行就是「被打斷的系統呼叫不會自動重啟」這個行為的根源。

fork() 與緩衝區重複輸出：stdio 的使用者層緩衝區是每個 FILE* 各自在程序記憶體裡的一塊內容，fork() 會把父行程的整個記憶體（包含尚未 flush 的緩衝區內容）複製一份給子行程。如果 fork() 之前緩衝區裡還有沒寫出去的資料，父子行程各自之後再各自 flush 一次，同一段輸出就會被印兩次——這正是為什麼很多框架在 fork() 前會呼叫 fflush(NULL)，或乾脆把關鍵輸出改成行緩衝／無緩衝模式的真正原因。這整個主題把「C 語言規格」「glibc 實作選擇」「核心的例外轉譯」三層串起來，是系統程式設計面試裡常考的題型：不只問 API 怎麼用，還會追問「為什麼」在不同平台上行為會不一樣。

🔢 數學推導

一個 unsigned char 能表示 0–255 共 256 個不同值（2⁸ = 256）。getchar() 除了要能回傳這 256 種資料值，還要能回傳一個「讀到檔尾／發生錯誤」的特殊訊號，兩者必須可區分——也就是整個回傳型別至少要能表示 256 + 1 = 257 種不同狀態。由於 2⁸ = 256 < 257，8 bits 不夠用，至少需要能表示 2⁹ = 512 ≥ 257 種狀態的寬度，也就是至少 9 bits。C 標準的基本型別裡沒有恰好 9 bits 的整數型別，而 int 在幾乎所有平台至少有 16 bits（現代主流平台普遍是 32 bits），遠超過 9 bits 的下限，自然成為最直接的選擇；另一個理由是 int 是函式呼叫慣例裡的「自然」寬度（System V AMD64 ABI 的整數回傳值走的是通用暫存器，int 只看低 32 bits），不需要額外的截斷或符號延伸處理，效能上沒有壞處。

再看 EOF 這個值為什麼挑 -1（glibc 在 libio/stdio.h 定義 EOF (-1)）而不是其他數字：-1 在二補數表示法下，所有位元都是 1（32-bit 下是 0xFFFFFFFF）。只要呼叫端老實把 getchar() 的回傳值放在 int 裡比較（不要先截斷成 char 再比較），任何合法的 0–255 位元組值被「零延伸」成 int 後，範圍都落在 0x00000000–0x000000FF，永遠不會跟 0xFFFFFFFF 混淆——這正是上面第二段提到的那個真實 bug 的根源：bug 不是出在 EOF 的定義本身，而是出在呼叫端把回傳值先截斷成 char，讓「零延伸」在有號平台上變成「符號延伸」，0xFF 被延伸成 0xFFFFFFFF，才會跟 EOF 的位元模式撞在一起。

glibc glibc-2.39 · sysdeps/posix/sysv_signal.c#L36-L56
__sighandler_t
__sysv_signal (int sig, __sighandler_t handler)
{
  struct sigaction act, oact;

  /* Check signal extents to protect __sigismember.  */
  if (handler == SIG_ERR || sig < 1 || sig >= NSIG)
    {
      __set_errno (EINVAL);
      return SIG_ERR;
    }

  act.sa_handler = handler;
  __sigemptyset (&act.sa_mask);
  act.sa_flags = SA_ONESHOT | SA_NOMASK | SA_INTERRUPT;
  act.sa_flags &= ~SA_RESTART;
  if (__sigaction (sig, &act, &oact) < 0)
    return SIG_ERR;

  return oact.sa_handler;
}
