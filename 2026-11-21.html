Morris Traversal：借用樹本身的空指標達成 O(1) 空間走訪，全新分類

二元樹走訪聽起來像是「背得起來就會寫」的題目，但如果面試官追問一句「可以不要用遞迴、也不要用任何額外的 Stack 嗎？」，大部分人就卡住了。遞迴走訪其實是把呼叫堆疊當成隱性的資料結構在用，用顯式 Stack 模擬一樣要付出 O(h) 的額外空間（h 是樹高，最差情況退化成 O(n)）。Morris Traversal 的洞見是：二元樹裡有大量「浪費」掉的 null 指標——在中序走訪（inorder）裡，除了最右邊那個節點以外，每個節點都存在一個明確的前驅（predecessor），也就是它左子樹裡最右邊的那個節點；而這個前驅節點的 right 指標，在正常建樹時通常是 null。Morris Traversal 就暫時「借用」這個 null 指標，讓它指回目前節點，形成一條臨時的線（有些書稱為「線索二元樹／threaded binary tree」的概念延伸），走訪經過時就能順著這條線走回來，完全不需要額外的堆疊或遞迴。

前驅（Predecessor）　中序走訪順序下，目前節點「前一個」會被訪問到的節點；對任何有左子樹的節點來說，前驅就是它左子樹中一路往右走到底的那個節點（因為中序是「左、中、右」，左子樹裡最後被訪問的一定是最右邊那個）。

運作步驟如下：維持一個指標 cur 從 root 開始走。(1) 若 cur.left 是 null，代表左邊沒有東西可借用，直接訪問 cur，然後 cur = cur.right。(2) 若 cur.left 不是 null，就去找 cur 左子樹裡最右邊的節點 pred：若 pred.right 是 null，表示這條線還沒建立過，就把 pred.right 指回 cur（建立 thread），然後 cur = cur.left 往左子樹深入；若 pred.right == cur，表示這條線之前已經建立過、現在剛好繞回來了，代表左子樹已經走完，這時要把線拆掉（pred.right = null，還原樹的原狀），訪問 cur，再 cur = cur.right。整個迴圈直到 cur 變成 null 結束。

舉一個具體例子：樹根是 1，1 的左子是 2，2 的左子是 4，2 沒有右子，1 的右子是 3。走訪流程：cur=1，有左子樹，找到 1 左子樹最右節點是 2（因為 2 沒有右子），pred=2，pred.right 是 null，建立 thread：2.right=1，cur=2。接著 cur=2 有左子樹，找到 2 左子樹最右節點是 4，pred=4，建立 thread：4.right=2，cur=4。cur=4 沒有左子樹，訪問 4（輸出：4），cur=4.right=2。cur=2 這次左子樹的 pred 仍是 4，發現 4.right==2==cur，表示線已經建立過，拆線（4.right=null），訪問 2（輸出：4,2），cur=2.right=null……實際上因為 2.right 剛剛被 thread 指回 1，所以這裡 cur 會變成 1，不是 null。接著同理拆掉 2.right=1 這條線，訪問 1（輸出：4,2,1），cur=1.right=3，3 沒有左子樹，訪問 3（輸出：4,2,1,3）結束，剛好就是正確的中序結果。

Edge case 需要特別小心：空樹直接回傳空結果；只有左子樹／只有右子樹的退化鏈結串列情況下，整棵樹其實變成一條線，每個節點的「左子樹最右節點」搜尋都是 O(1)（因為沒有分支），整體仍維持 O(n)；最容易寫錯的地方是判斷順序——一定要先判斷 pred.right == cur（代表線已存在要拆），再判斷 pred.right == null（代表線不存在要建），如果順序寫反，會把本來該拆除的線誤判成要再建一次，導致無窮迴圈或樹被永久破壞。

複雜度比較：遞迴走訪是 O(n) 時間、O(h) 額外空間（最差 O(n)）；顯式 Stack 模擬同樣是 O(n)/O(h)；Morris Traversal 是 O(n) 時間、O(1) 額外空間，代價是時間常數略高一些，因為每個有左子樹的節點，它左子樹裡的最右節點會被「訪問」兩次：一次是建立 thread 時順便找到它，一次是之後繞回來拆線時再次確認。這個「看起來好像要花 O(n²)」的疑慮，會在下方數學推導區塊用攤銷分析證明仍然是 O(n)。

攤銷分析（Amortized Analysis）　不是看「單一操作」最差要花多少時間，而是看一連串操作「平均下來」每次花多少時間；即使某幾步看起來要重複做某件事，只要能證明重複的總次數有一個全域上限，平均分攤到每個節點後仍然是常數時間。

常見變形至少兩種：第一種是 Morris Preorder——輸出的時機點不同：中序是在「第二次經過、要拆線時」才輸出，preorder 則改成「第一次經過、thread 還沒建立時」就先輸出，順序變成先中後左再右的建線邏輯要跟著調整；第二種是把 Morris 技巧直接拿去解 LeetCode 114（Flatten Binary Tree to Linked List）：不是建一條「指回自己」用來導航的線，而是直接把目前節點的左子樹接到右子樹的位置（把左子樹裡最右節點的 right 指向原來的右子樹），等於用 Morris 的指標操作「順手」把整棵樹重新接線成一條右傾的鏈結串列，同樣是 O(1) 額外空間。

面試官常見追問：(1) 為什麼不會造成無窮迴圈？因為每一條建立的 thread，一定會在之後明確的某一步被拆除，拆除的判斷條件 pred.right==cur 保證每條 thread 只會被「利用」一次來導航，用完就恢復原狀。(2) 走訪過程中樹被其他執行緒同時讀取會發生什麼事？因為 Morris Traversal 會暫時修改樹的實際指標結構，它不是執行緒安全的，這也是正式系統裡很少把它用在「唯讀」走訪場景的原因，必須確保走訪過程中沒有其他讀者。(3) 能不能用 Morris 技巧做後序走訪（postorder）？可以，但做法是先建一個虛擬 dummy root 當作樹根，把整棵樹「左右互換」視角去做 Morris preorder，拿到結果後再整體反轉，複雜度仍是 O(n)/O(1)，但實作細節多很多，多數公司面試只要求講出原理、不一定要求當場寫出完整程式碼。

關鍵數字是「總走訪步數仍是 O(n)」，而不是看起來的 O(n²)。證明方式是把「尋找前驅」這個內層迴圈的步數，重新記到樹的邊（edge）上而不是記到節點上：對每一條邊 (parent, left-child)，它只會在兩種情況下被「走過」——一次是從 cur 往左子樹裡尋找最右節點、順著右指標一路往下走去建立 thread 時經過；另一次是之後繞回來、要拆掉這條 thread 時再經過一次確認。也就是說，每一條邊最多被經過 2 次。一棵有 n 個節點的二元樹恰好有 n−1 條邊，所以尋找前驅這個內層迴圈的總步數上限是 2(n−1) = O(n)，加上外層 cur 本身從根走到結束最多移動 O(n) 次，兩者相加仍是 O(n)。這就是為什麼「看起來每個節點的內層迴圈都要花到 O(h)」，攤銷下來整體仍然維持線性時間，而不是退化成 O(n·h) 或 O(n²)。

Ch.4　4.5.4 Next PC Prediction

延續前兩天教的 SEQ+（把訊號計算搬到暫存器輸出端）與插入 Pipeline Register（把 SEQ+ 切成 Fetch／Decode／Execute／Memory／Write-back 五級），今天要處理一個五級管線一旦真正並行運作，馬上會撞到的根本問題：Fetch 階段必須在還不知道「下一條指令到底是誰」的情況下，就先決定要去抓哪個位址的指令。如果管線每一級都要等前一級徹底確定完才能動作，那管線化根本沒有意義——五個階段會變成排隊依序執行，跟完全不分階段的單週期處理器沒有差別。PIPE 的解法是在 Fetch 階段新增一個訊號 predPC，由一組規則「猜」出下一個該抓的位址，等真正結果出來後再驗證、必要時修正。

控制相依（Control Dependency）　下一條該執行的指令，依賴於「這條指令的執行結果」才能確定（例如條件跳躍要看 condition code、ret 要看堆疊裡的返回位址）。這種相依關係如果不先想辦法處理，管線就只能乾等，這也是本節要解決的核心問題。

predPC 的三種規則：(1) 一般指令（不是 jmp／call／ret）：predPC 直接設成這條指令之後的位址，也就是 Fetch 階段本來就會算出的 valP（因為指令編碼長度固定，解碼出 icode/ifun 就知道整條指令多長），因為程式預設就是順序執行，這不算真正的「猜」，是可以直接確定的事實。(2) call 與無條件 jmp：predPC 設成指令裡編碼出來的目的位址 valC，因為這兩種指令一定會跳到那裡，同樣是確定而非猜測。(3) 條件跳躍 jXX：這時還不知道條件是否成立——要等到 Execute 階段，ALU 算出減法結果並設好 condition code 之後才能確定——但 Fetch 階段不能停下來等，PIPE 的設計選擇是永遠預測「會跳躍」，所以 predPC = valC。只有 ret 完全沒辦法用這套規則預測，因為返回位址藏在堆疊裡的記憶體內容中，Fetch 階段根本看不到，只能等這條 ret 指令本身真正執行到 Write-back 階段，才能從管線暫存器裡拿到正確的返回位址。

具體例子：考慮一段簡單迴圈組語，迴圈尾端是 cmpl 設定旗標、接著 jg loop 跳回迴圈開頭。每個 cycle，Fetch 階段都會立刻用 predPC 去抓下一條指令：第一次遇到 jg，因為規則 (3) 永遠預測跳躍，predPC 直接設成 loop 的位址，於是下一個 cycle 馬上去抓迴圈開頭那條指令，而不是等 jg 走到 Execute 階段才動作；等到 jg 真正走到 Execute 階段、condition code 算出來後，才確認這次預測對不對——如果迴圈還要繼續跑，預測就是對的，完全沒有損失；只有迴圈最後一次要跳出時，預測才會錯。

Edge case：如果一個基本區塊裡連續出現兩個條件跳躍（例如先 jle 再緊接著 jmp），predPC 要一路鏈式往下猜——每個 cycle 都只根據「目前正在 Fetch 的這條指令」猜一次，不會提前去看更後面的指令；遞迴函式呼叫則是另一個棘手的邊界情況：每次 call 都會把返回位址推進堆疊，但 Fetch 階段完全看不到堆疊內容，所以每個 ret 的下一個 predPC 都無法套用規則 (1)(2)(3) 中的任何一條去猜，只能先讓 Fetch 暫時卡住（插入泡沫），直到真正的返回位址從 Write-back 階段浮現為止。

這其實就是現代處理器裡「分支預測器（Branch Predictor）」最原始、最簡化的版本：Y86 PIPE 用的是最簡單的靜態規則（永遠預測 taken），而真實 x86 處理器用的是會根據執行歷史動態調整的預測器（例如 two-level predictor、perceptron predictor，甚至專門處理 ret 的 Return Address Stack）。面試中常被追問的問題是：為什麼「永遠預測跳躍會發生」這個簡單規則，統計上反而經常是對的？原因是大部分條件跳躍出現在迴圈尾端，用來「跳回迴圈開頭」，一個跑了 N 次的迴圈裡，這條跳躍指令會有 N−1 次預測正確（繼續跑迴圈）、只有最後一次要離開迴圈時才預測錯誤，N 越大，命中率就越接近 100%。

常見變形：(1) 把預測策略從「永遠預測 taken」換成「永遠預測 not-taken」，或是更精細的「往回跳就預測 taken、往前跳就預測 not-taken」（教科書稱為 BTFNT，backward-taken/forward-not-taken），是許多課程常出的練習題，背後假設是迴圈的跳躍多數是往回跳、if 分支的跳躍多數是往前跳。(2) 針對 ret 完全無法預測這件事，更進階的處理器會加一個小型硬體堆疊，在 call 執行時就把「預期的返回位址」先推進這個硬體堆疊，等真正遇到 ret 時直接彈出使用，而不是什麼都不猜、乾等到 Write-back。

面試官常見追問：(1) 一般指令用 valP 來決定下一步，為什麼不算是「猜」？因為那本來就是解碼直接算出的事實，只有當前面出現跳躍指令改變了實際流向，才需要在之後修正，而這個修正動作本身屬於「控制相依」要處理的範疇，不是 valP 本身不準。(2) 如果條件跳躍預測錯誤，要怎麼恢復？下一節 4.5.5 會詳細處理：已經被誤抓進管線、跟著錯誤路徑往下跑的那幾條指令，必須被「清空（squash）」成等效於 nop，而清空動作本身要花掉幾個 cycle 的代價，要等到那裡才會精確算出數字。(3) Y86 PIPE 為什麼不索性做跟真實 CPU 一樣的動態分支預測？因為 Y86 PIPE 是教學用、結構固定的簡化管線，動態預測需要額外的歷史紀錄表與訓練邏輯，會讓整個管線控制邏輯複雜很多，教科書選擇先用最簡單的靜態規則，把「為什麼一定需要預測」這個概念講清楚，動態預測留給處理器結構的後續課程或進階讀物。

🔢 數學推導

量化一下「不預測」要付出的代價：如果完全不做任何預測，最保守的作法是每條指令都要等到自己真正走完 Execute 階段、算出下一個 PC 之後，才讓下一條指令開始進入 Fetch——也就是每條指令要獨占管線 F→D→E 這 3 個 cycle 之後，才能讓下一條指令進場，等於 5 級管線的 CPI（每指令週期數）從理想的 1 退化到至少 3。如果像 ret 這種真的要等到最後一刻（Write-back 階段）才能確定下一個 PC，CPI 甚至會退化到 5，等於完全沒有管線化的好處，跟單週期處理器一樣慢。這就是為什麼一定要有 predPC：用「猜」把 CPI 重新拉回接近 1，代價只是猜錯時要花額外幾個 cycle 清空重做——下一節會把這個清空代價精確量化成具體的泡沫數。

如何避免為嵌入式 Linux 撰寫裝置驅動程式：Userspace I/O（UIO）

昨天教的 Driver Model（struct device／device_driver／bus_type）解決的是「核心內部」要怎麼用一致的方式管理千奇百怪的裝置；今天要問一個更前面、更根本的問題——有沒有辦法完全不寫符合這套模型的核心驅動程式？Chris Simmonds 在 Embedded Linux Conference 的這場演講〈How to Avoid Writing Device Drivers for Embedded Linux〉，介紹了幾種把驅動邏輯「搬到使用者空間」執行的機制，其中最具代表性的就是 UIO（Userspace I/O）。

UIO（Userspace I/O）　Linux 核心提供的一套基礎設施，讓裝置驅動的大部分邏輯可以寫在使用者空間，核心端只保留一個「最小」的 kernel module 負責登記裝置資源與轉送中斷事件。

UIO 的設計把一個裝置驅動拆成兩半：核心端只留下一塊很薄的 kernel module，負責向核心登記這個裝置的記憶體區域（I/O memory）與中斷號，並把它透過 /dev/uioN 這個字元裝置節點、以及 /sys/class/uio/uioN/ 底下的 sysfs 屬性曝露給使用者空間；使用者空間的程式再用 open("/dev/uioN") 配合 mmap()，把裝置的暫存器／記憶體直接映射進自己的位址空間，之後就能像操作一般記憶體一樣直接讀寫暫存器，完全不需要走 ioctl() 或 read()/write() 這類系統呼叫介面去間接存取。

中斷的處理方式也同樣被簡化成使用者空間熟悉的介面：UIO 把「中斷發生」這件事轉成使用者空間可以用 read() 或 select()/poll() 等待的一個簡單事件——核心端最小的中斷處理程式只做最基本的確認（例如清除中斷狀態暫存器、遮罩住這顆裝置的中斷源，避免同一個中斷不斷重複觸發），然後喚醒正在等待的 read()；實際上要對裝置做什麼動作，全部留給使用者空間決定。等於把「上半部（硬中斷處理）」留在核心，把幾乎所有「下半部」的實際邏輯都搬到使用者空間執行。

下方原始碼區塊引用的是 kernel.org 官方 UIO HOWTO 裡 uio_pci_generic 的範例程式：使用者空間程式先 open("/dev/uio0") 拿到中斷事件的檔案描述字，再透過 sysfs 的 .../device/config 節點直接讀寫 PCI config space 來清除與重新啟用中斷遮罩位元，接著用一個無窮迴圈呼叫 read(uiofd, &icount, 4) 卡住等待下一次中斷，拿到中斷計數後印出除錯訊息。整段驅動邏輯完全在使用者空間完成，核心只提供「記憶體映射」與「中斷事件通知」這兩項最基礎的設施。

Edge case／限制：UIO HOWTO 明確指出它不是萬用的驅動介面。如果裝置需要用到 DMA（直接記憶體存取）、需要精確的中斷延遲保證、或邏輯已經能很乾淨地對應到某個既有核心子系統（像網路裝置或區塊裝置），用 UIO 硬做反而會失去那個子系統原本提供的一致介面與效能最佳化；Simmonds 的演講也特別強調，UIO／使用者空間驅動最適合的場景是「這顆裝置很客製化、很少見、沒有對應的標準核心子系統」，而不是拿來取代所有驅動程式。

VFIO（Virtual Function I/O）　UIO 的更安全版本，額外整合了 IOMMU 保護，讓使用者空間程式無法透過 DMA 寫到任意實體記憶體位址，常用在虛擬機直通裝置（PCI passthrough）的場景。

與實務／面試的關聯：這個題材直接對應到真實世界的工程取捨——在嵌入式系統開發，把驅動邏輯放到使用者空間可以大幅縮短開發週期（不用重新編譯核心、不用擔心核心模組的 GPL 授權邊界、程式 crash 只會弄死一個使用者行程而不會讓整台機器 panic），但代價是失去核心排程保證的即時性，也失去核心內建的鎖、電源管理等基礎設施整合；這正是 DPDK（高效能封包處理框架）、SPDK（高效能儲存框架）等使用者空間驅動框架選擇走 UIO／VFIO 這條路的根本原因——它們追求的是繞開核心網路／儲存堆疊的額外開銷，換取極致的吞吐量。

常見變形：除了前面提到的 VFIO，還有一個更極端的案例是 GPIO 這類最簡單的裝置——核心甚至不需要使用者寫任何一行驅動程式碼，透過舊式的 /sys/class/gpio 介面，或新版建議改用的 libgpiod 字元裝置介面，就能直接從 shell 指令稿或函式庫操作腳位，是比 UIO「完全不用寫程式碼」更進一步的做法。把昨天的 Driver Model、今天的 UIO／VFIO、以及 GPIO 的 sysfs/libgpiod 介面三者放在一起看，才是「要不要讓核心插手裝置控制邏輯」這個光譜的完整全貌：從核心完全掌控，到核心只搭一層最薄的橋，到核心完全不插手。

🔢 數學推導

範例程式裡呼叫 mmap() 映射裝置記憶體時，官方文件特別強調：若一顆裝置有多個獨立的記憶體映射區域（mapping），要用 offset = N * getpagesize() 來指定第 N 個映射區域，不能直接用任意的位元組數去區分。原因可以追回 CS:APP 虛擬記憶體章節會教到的分頁機制：mmap() 底層依賴 MMU 以「完整頁」為單位做映射，x86-64 常見的分頁大小是 4096 bytes（也就是 2^12），任何映射的起始位址與長度都必須是頁大小的整數倍；UIO 因此選擇把「第幾個映射區域」直接編碼成「第幾個分頁」的 offset（N=0 用 offset 0，N=1 用 offset 4096，以此類推），而不是用裝置內部記憶體的真實位元組位移，這樣才能保證換算出來的 offset 永遠滿足 MMU 分頁對齊的硬性限制。

uiofd = open("/dev/uio0", O_RDONLY);
if (uiofd < 0) {
    perror("uio open:");
    return errno;
}
configfd = open("/sys/class/uio/uio0/device/config", O_RDWR);
if (configfd < 0) {
    perror("config open:");
    return errno;
}

/* Read and cache command value */
err = pread(configfd, &command_high, 1, 5);
if (err != 1) {
    perror("command config read:");
    return errno;
}
command_high &= ~0x4;

for(i = 0;; ++i) {
    /* Re-enable interrupts. */
    err = pwrite(configfd, &command_high, 1, 5);
    if (err != 1) {
        perror("config write:");
        break;
    }

    /* Wait for next interrupt. */
    err = read(uiofd, &icount, 4);
    if (err != 4) {
        perror("uio read:");
        break;
    }
}
