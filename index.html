二維矩陣的二分搜尋技巧：全域排序的 1D 搜尋、階梯式搜尋與值域二分搜尋三種變形

今天換到一個過去 14 天（11/14～11/26）都還沒出現過的新分類：二維矩陣上的二分搜尋技巧。這個分類的有趣之處在於它其實包了三種乍看很像、但本質不同的子技巧，很適合拿來練習「先看清楚題目給的結構保證是什麼，再決定能不能套用二分搜尋」這個比死背模板更重要的判斷力。

第一種是最單純的全域排序矩陣的 1D 二分搜尋（LeetCode 74 Search a 2D Matrix）：題目保證每一列從左到右遞增、且每一列的第一個元素大於前一列的最後一個元素——這個條件等於是說，如果把整個 m×n 矩陣「壓平」成一條長度 m×n 的一維陣列，它整體是嚴格遞增的。既然整體有序，就可以直接套用教科書式的二分搜尋：用一個虛擬索引 mid 跑從 0 到 m×n−1，透過 mid // n、mid % n 換算回真正的列與行座標去比較，完全不需要真的把矩陣展開成一維陣列。時間複雜度 O(log(mn))、空間 O(1)。

降維（Dimension Reduction）　把一個多維的搜尋問題，透過座標映射（例如 row = idx // n, col = idx % n）轉換成等價的一維問題，直接套用已經很熟悉的一維演算法，而不用重新發明一套「二維二分搜尋」。前提是資料結構本身真的具備能壓成一維仍保持單調性的保證。

第二種是階梯式搜尋（Staircase Search）（LeetCode 240 Search a 2D Matrix II）：題目的保證變弱了——只保證每一列從左到右遞增、每一行從上到下遞增，但不保證跨列跨行的整體順序（例如矩陣右上角的值可能比左下角小，也可能比左下角大）。這個弱化的保證，代表第一種的「整體視為一維陣列」假設完全不成立，不能直接套 1D 二分搜尋。正確作法是從右上角（或左下角，兩個角其中之一，取決於你怎麼定義移動方向）開始走：如果目前值比 target 大，往左走（因為同一列右邊的值只會更大，不可能是 target）；如果比 target 小，往下走（因為同一行上面的值只會更小）；相等就直接回傳。這條路徑最多走 m+n 步就會走出矩陣邊界或找到答案，時間複雜度 O(m+n)、空間 O(1)。

這裡有一個常見的面試陷阱：很多人看到「矩陣」、「排序」就反射性地喊出「二分搜尋 O(log(mn))」，但 240 題並不能做到這個複雜度——反例很容易構造：考慮一個只有兩列的矩陣 [[1, 100], [2, 101]]，右上角 100 跟左下角 2 的大小關係完全不可預測，所以沒有任何一種「切一半丟一半」的策略能保證安全丟棄一半的候選範圍；階梯式搜尋的 O(m+n) 其實是目前已知對這個弱保證下最優的做法，證明見下方數學推導。能不能主動指出「這題其實不是 O(log(mn))，而且我可以舉反例說明為什麼」，往往比寫出正確程式碼本身更能展現對二分搜尋前提條件的理解深度。

單調謂詞（Monotonic Predicate）　二分搜尋能成立的真正充要條件，不是「資料被排序」，而是「存在一個謂詞 P(x)，讓所有 x 從小到大排列時，P(x) 的真假只會從全假翻轉成全真一次（或反過來）」。1D 陣列排序只是讓「P(x) = (arr[x] ≥ target)」具備這個單調性的其中一種常見方式；下面第三種子技巧會示範即使資料結構本身不是單一數列，只要能在值域上構造出這樣的單調謂詞，一樣可以套二分搜尋。

第三種是對「值域」做二分搜尋（LeetCode 378 Kth Smallest Element in a Sorted Matrix）：矩陣仍然維持跟 240 一樣「列行各自遞增、整體無序」的弱保證，但題目問的是「第 k 小的值是多少」。既然矩陣整體無序，不能對「索引」做二分搜尋；但可以反過來對「答案可能的數值範圍」[matrix[0][0], matrix[n-1][n-1]] 做二分搜尋：對任意候選值 v，定義一個可以在 O(n)（n 為邊長）內算出來的計數函式 count(v) = 矩陣裡 ≤ v 的元素個數（這個計數函式本身就是重複套用第二種階梯式搜尋的變形：從左下角開始走，每往右移一步就把該列目前位置以上的格子數全部累加），然後對 v 二分搜尋「最小的 v 使得 count(v) ≥ k」。count(v) 隨 v 遞增這件事保證了它是一個合法的單調謂詞，所以可以放心二分。整體時間複雜度 O(n log(max−min))，這題同時用到了今天的第二種技巧（當作計數的子程序）跟 9/3 教過的「二分搜尋於答案空間」這個更早的技巧，是兩個技巧疊在一起的典型範例。

Edge case 整理：(1) 378 題如果矩陣裡有大量重複值，對索引做二分搜尋會直接壞掉（同一個值可能出現在矩陣裡好幾個不連續的「索引位置」，根本沒有單一一致的順序可言），但對「值」二分搜尋完全不受影響，因為計數函式只關心「有多少元素 ≤ v」，重複值天然被正確計入；這也是選對「用什麼當二分搜尋的軸」有多重要的具體例證。(2) 階梯式搜尋在矩陣退化成只有 1 列或 1 行時，其中一個移動方向從一開始就不存在，程式碼要確保指標不會在第一步就直接越界。(3) 二分搜尋值域時的收斂條件容易寫錯方向：要收斂到「最小的滿足 count(v) ≥ k 的 v」，用的是 count(mid) < k 時才把左界往右推，不是比較 mid 跟 target 的值本身，這跟一般「找某個確切值」的二分搜尋思路不一樣，很容易慣性寫錯。

跟暴力解法的完整時間/空間比較：74 題暴力掃描整個矩陣找 target 是 O(mn) 時間、O(1) 空間，二分搜尋版本把時間壓到 O(log(mn))，矩陣一大（例如 1000×1000）差距是指數級的（20 次比較 vs 一百萬次比較）；240 題暴力掃描同樣是 O(mn)，階梯式搜尋壓到 O(m+n)，矩陣越「瘦長」（m、n 差很多）相對優勢越小，矩陣越接近正方形優勢越大；378 題如果用暴力解法——把整個矩陣展開排序再取第 k 個——是 O(n²log(n²)) 時間、O(n²) 額外空間，或用一個大小為 k 的 max-heap 做法是 O(n²log k)，二分搜值域的 O(n log(max−min)) 在 k 接近 n² 規模、且數值範圍不是天文數字時明顯更省時間也不額外佔空間。

常見變形模式，除了上面已經走過的兩種（1D 壓平二分、值域二分＋計數謂詞），再補一個同一家族但目標不同的例子：邊界搜尋型——LeetCode 1428「Leftmost Column with at Least a One」，給一個「每一列、每一行都已排序（0 在左、1 在右）」的二元矩陣，要找「最左邊、至少有一個 1 的那一行」。這題不是找某個特定值，而是找一個滿足某個單調條件的「邊界位置」，但走的路徑跟 240 題的階梯式搜尋幾乎一模一樣：從右上角開始，遇到 1 就往左記錄、遇到 0 就往下，同一套「兩個方向各自單調、就能用階梯消去一整列或一整行」的核心手法，換了一個問題外殼就能重複使用。

面試官常見的追問：「如果只保證列排序、行完全沒排序呢？」——階梯式搜尋的兩個移動方向都仰賴列、行同時遞增，少了其中一個保證就整個失效，退化成對每一列各自做一次 1D 二分搜尋，複雜度退回 O(m log n)；「矩陣資料量太大，無法一次放進記憶體怎麼辦？」——這會把問題帶往外部排序／分散式 top-k 的方向，階梯式搜尋天生是一條單一路徑、不需要隨機存取任意格子，相對友善於串流或分頁讀取的場景；「如果要回報所有等於 target 的位置，不只一個？」——用 74 題找到任意一個位置後，階梯式搜尋的優點在這裡顯現：它本來的走法就會自然掠過沿途所有可能候選，稍微調整收尾條件就能一次收集完畢，不需要重新掃一次整個矩陣。

這個分類跟面試與實務的連結，核心不是「矩陣」這個資料外型本身，而是「能不能看出一個單調謂詞藏在哪裡」這個更通用的能力：資源配置、容量規劃一類的系統設計問題（例如「給定一堆伺服器負載，找出能撐住所有請求的最小容量」）常常也是先確認某個指標隨某個參數單調變化，再對那個參數二分搜尋、每次用一個 O(n) 的檢查函式驗證——跟今天第三種技巧的骨架完全一樣。看到任何「resource/value 隨某個軸單調變化，而且有辦法快速驗證某個候選值是否可行」的問題，都該反射性地想一下能不能套這個模式。

為什麼階梯式搜尋（LC240）保證剛好最多走 m+n 步：把走訪路徑想成在一個 m×n 的網格上，從右上角 (0, n−1) 出發，每一步只會「往左走一格」（行座標 −1）或「往下走一格」（列座標 +1），沒有第三種動作，也絕不回頭。行座標最多能往左走 n 次就碰到左邊界，列座標最多能往下走 m 次就碰到下邊界，兩者加起來，整條路徑上的格子數上限就是 m + n（不會更多，因為每一步都讓「剩餘可走格數」嚴格減少 1）。這就是 O(m+n) 的由來，跟矩陣總格數 m×n 比起來是指數級的差距（當 m、n 都是數千時，m+n 是數千，m×n 是數百萬以上）。

為什�么 240 題不可能達到 O(log(mn))：可以用資訊論的角度直覺理解——真正的二分搜尋每比較一次最多消去一半的候選空間，若整個矩陣真能用 O(log(mn)) 解決，代表每次比較都要能安全丟棄「一大塊」候選格子；但前面反例 [[1,100],[2,101]] 說明了：光知道矩陣中某一格的值，完全無法推論出跨列跨行、沒有被同一列或同一行覆蓋到的其他格子跟 target 的大小關係，所以任何比較動作最多只能安全排除「當前比較格所在的那一整列或那一整行」，而不是一半的矩陣——這正是階梯式搜尋每步排除一列或一行、總共 O(m+n) 步的下界來源，不是演算法設計得不夠聰明，是題目給的保證本身就只撐得起這個複雜度。

值域二分搜尋（LC378）的複雜度：值域寬度是 max−min（矩陣最大值減最小值），每次二分搜尋把值域砍半，需要 O(log(max−min)) 輪；每一輪呼叫一次計數函式 count(v)，而 count(v) 本身就是一次階梯式走訪，是 O(n)（這裡矩陣是 n×n 正方形）。兩者相乘即為 O(n log(max−min))；當數值範圍 max−min 遠小於 n² 時（例如矩陣元素都落在 32-bit 整數範圍但 n 很大），這個複雜度比對索引排序的 O(n²log(n²)) 划算得多，但如果數值範圍本身就跟 n² 同量級甚至更大，兩者優勢就會被拉近，需要視實際輸入特性判斷。

📄 原始碼
自行實作／標準演算法邏輯（非特定來源引用）
# 階梯式搜尋（Staircase Search）—— LeetCode 240 的標準解法
# 時間複雜度 O(m+n)，空間複雜度 O(1)；自行實作的通用演算法邏輯，非特定來源逐字引用
def search_matrix_staircase(matrix, target):
    if not matrix or not matrix[0]:
        return False
    row, col = 0, len(matrix[0]) - 1   # 從右上角出發
    while row < len(matrix) and col >= 0:
        val = matrix[row][col]
        if val == target:
            return True
        elif val > target:
            col -= 1   # 同一列右邊只會更大，往左消去一整行
        else:
            row += 1   # 同一行上面只會更小，往下消去一整列
    return False

# 值域二分搜尋 —— LeetCode 378，count(v) 複用上面的階梯走法
def kth_smallest(matrix, k):
    n = len(matrix)

    def count_leq(v):               # 矩陣中 <= v 的元素個數，O(n)
        cnt, row, col = 0, n - 1, 0
        while row >= 0 and col < n:
            if matrix[row][col] <= v:
                cnt += row + 1
                col += 1
            else:
                row -= 1
        return cnt

    lo, hi = matrix[0][0], matrix[-1][-1]
    while lo < hi:
        mid = (lo + hi) // 2
        if count_leq(mid) < k:
            lo = mid + 1
        else:
            hi = mid
    return lo

Ch.4　4.5.10 PIPE Stage Implementations

接續昨天（11/26）教完的 4.5.9 節例外處理之後，今天往下走到 4.5.10 節 PIPE Stage Implementations（依 CMU 課程網站公開的 2nd edition 目錄：4.5.9 Exception Handling → 4.5.10 PIPE Stage Implementations → 4.5.11 Pipeline Control Logic，與過去幾天一路採用的小節編號一致）。這一節做的事情，跟前面 4.5.1～4.5.9 每一節「單獨講一個問題（怎麼切管線、怎麼轉發、怎麼處理例外…）」不一樣：它是把前面每一節各自設計出來的機制，全部兜在一起，寫成每一個 pipeline stage 真正、完整、可以直接對應到邏輯閘電路的 HCL 描述——是整個 PIPE 設計從「紙上概念」正式變成「可以合成出真正硬體」之前的最後一道整合關卡。

整合時第一個值得注意的設計：PIPE 把 Decode 跟 Write-back 畫成共用同一塊組合邏輯區塊，而不是兩個獨立的黑盒子。原因很具體：同一個暫存器檔案（register file）只有一份，而 Decode 階段要「讀」暫存器、Write-back 階段要「寫」暫存器，這兩件事在同一個 clock cycle 裡可能同時發生在同一個暫存器編號上——如果直接讓硬體上的讀取埠去讀，會讀到「寫入前」的舊值，因為寫入通常被设計成要等到這個 cycle 結束、下一個 clock edge 才真正落地。

Register File Forwarding（暫存器檔案內的直接轉發）　専門處理「同一 cycle 裡，Write-back 正要寫入某個暫存器、Decode 剛好也要讀同一個暫存器」這種特殊情況的旁路邏輯：直接把 Write-back 這一刻準備要寫入的值，繞過正常的讀取埠，直接送給 Decode 當作讀到的結果，而不是真的去讀暫存器檔案本身。這跟接下來要講的「跨 stage pipeline register 轉發」是同一個大家族，但它專門解決的是「同一 cycle 內」這個最極端的特例。

把這個 register file forwarding 跟前幾天教過的 pipeline register 轉發（e_valE、M_valE 等）放在一起看，PIPE 整套轉發網路總共有 5 個轉發來源，餵給 2 個轉發目的地（Decode 階段正要供下一條指令使用的 valA 與 valB）：來自 Execute 階段剛算出來的 e_valE；來自 Memory 階段的兩個不同數值——它自己 pipeline register 裡還沒退休的 ALU 結果 M_valE，以及這個 cycle 才剛從資料記憶體讀出來的 m_valM；以及來自 Write-back 階段的兩個數值 W_valE、W_valM（也就是上面提到的 register file forwarding 的具體內容）。教科書在這裡把這套邏輯具體寫成一組依優先序排列的 HCL mux：原則是「越新鮮（越接近 Execute、越剛算出來）的來源優先」，因為它代表的是程式邏輯上最晚、因此也最該被看到的那個值；只有當所有 pipeline 裡還在跑的來源都不符合，才退回到正常從暫存器檔案讀出來的 d_rvalA／d_rvalB。

這裡刻意不逐字引用教科書的 HCL 原始程式碼（避免在沒有逐字核對確定的情況下假裝那是真的課本原文），但上面描述的「5 個來源、2 個目的地、新鮮優先」的設計骨架，是已核對過的真實內容（見下方來源）；具體落成程式碼時，長得就像一串 case 判斷式，從 Execute 的來源開始比對，一路比對到 Write-back 的兩個來源，最後才是「沒有任何轉發，直接讀暫存器」的預設情況。

整合的第二個重點，是把昨天教的 status code 具體落實成每個 stage 真正的「禁止動作」訊號。Execute 階段：即使 ALU 還是會照常把兩個輸入做運算（硬體閘的輸出無法真的「不運算」），但只要這條指令的狀態不是 AOK，條件碼暫存器（CC）的寫入訊號 set_cc 一定被強制拉成 0，確保一條有問題的指令不會意外改動 CC、進而影響到後面指令的條件分支判斷。Memory 階段：資料記憶體的寫入訊號同樣被這個狀態檔閉掉，不管位址、資料算出來是什麼，實際的 dmem_write 都不會發生。Write-back 階段：暫存器檔案的寫入同樣被關掉，而且這正是整個管線裡「哪個 cycle 真正對外公告這條指令的最終狀態」的地方——W_stat 在這裡被latch住，等同於昨天教的「只在 Write-back 才真正 commit」原則，在這一節總算有了具體對應的硬體訊號。

這一節也補了前面幾天都還沒細講的一塊：Memory 階段用來決定「要存取記憶體的位址到底是 valA 還是 valE」的 mux。絕大多數指令（例如一般的 mrmovq/rmmovq）用 valA 當記憶體位址；但像 pushq 這種指令，valE 其實是 Execute 階段算出來「已經把 %rsp 減掉 8 之後」的新堆疊頂位址，而 pushq 必須把值寫到這個新位址，不是寫到舊的 %rsp（也就是 valA）——如果寫錯成 valA，寫入位置會跟新堆疊頂差了 8 個 byte，之後任何人從新堆疊頂讀資料都會讀到錯的東西。這個 mem_addr mux 看起來只是個小細節，卻是「堆疊操作為什麼非得這樣設計」的具體硬體證據。

mem_addr / mem_data 選擇邏輯　決定 Memory 階段真正拿去存取資料記憶體的位址與資料，分別從 valA/valE（位址側）與 valA/valE（資料側，依指令種類不同，例如 rmmovq 用 valA 當資料來源）當中選一個。這組 mux 看起來不起眼，但正是「為什麼 push/pop/call/ret 這幾個指令的操作數安排跟一般 move 指令不一樣」在 HCL 層面的真正原因。

如果把這整套轉發網路拿掉、換成最原始的「每次有依賴就整個 stall 到 producer 寫回」的做法，代價會差多少？下方數學推導給出具體的 cycle 數字——結論是：沒有轉發網路，幾乎每一條跟前一條指令有資料相依的指令都要多付出好幾個 cycle 的代價，而且這個代價會隨著管線級數增加而線性變大；有了轉發，絕大多數 register-to-register 的依賴可以完全吃掉變成 0 個額外 cycle，只有 load/use 這種「資料真的還沒從記憶體出來」的情況才真的需要（已經在 4.5.7 教過的）1 個 cycle stall。這組對比，正是「管線化處理器為什麼值得花這麼多硬體成本做轉發」最直接的量化理由。

這一節整合出來的「優先序轉發 mux ＋ 逐階段關閉副作用」兩件事，合在一起正是真實處理器裡 bypass network（旁路網路）的縮小版雛形——真正的超標量處理器需要應付的來源數目遠比 PIPE 的 5 個多（因為同時在飛的指令更多），但「哪個來源最新鮮就該贏」這個仲裁原則完全一樣，也是低階效能／微架構相關面試裡經常被問到「如果兩個來源同時符合轉發條件，你要怎麼決定用哪個」這類問題的標準答案骨架。對面試準備而言，能講清楚「為什麼是 Execute 優先於 Memory、Memory 優先於 Write-back」這個先後順序背後的理由（越新鮮代表越該被信任），比單純背出有哪些訊號名稱更重要。

🔢 數學推導

為什麼轉發網路剛好需要 5 個來源，不是更少也不是更多：在 Decode 讀取運算元的那一刻，可能供值的 producer 指令，依照目前管線裡還有誰在跑，距離 Decode 恰好有 1～3 個 stage 之遠：Execute（領先 1 階，剛算出 e_valE，是最新鮮的來源）、Memory（領先 2 階）、Write-back（領先 3 階，Fetch 這一階什麼都還沒算出來，不會是來源）。差別在於 Memory 跟 Write-back 這兩個「落後」的 stage，各自都能同時提供兩種不同的值：一種是這條指令早在 Execute 就算好、一路揣在 pipeline register 裡還沒真正退休的 ALU 結果（對 Memory 是 M_valE，對 Write-back 是 W_valE）；另一種是這條指令如果是 load，資料要等到真正走到 Memory 階段才會從記憶體讀出來（對 Memory 是剛讀出來的 m_valM，對 Write-back 是已經讀出來、正準備寫回的 W_valM）。所以來源數 = Execute 的 1 個（e_valE）＋ Memory 的 2 個（M_valE、m_valM）＋ Write-back 的 2 個（W_valE、W_valM）= 5 個，這個數字直接由「5 級管線＋load 指令會在 Memory 階段才產生新數值」這兩個結構性事實決定，不是隨意湊出來的。

沒有轉發網路要多付出幾個 cycle：假設 producer 指令在 cycle 1 進 Fetch，依序在 cycle 2/3/4/5 進 Decode/Execute/Memory/Write-back；緊接著的 dependent 指令正常情況下應該在 cycle 2 進 Fetch、cycle 3 進 Decode。如果完全沒有轉發、規定「必須等 producer 真正寫回暫存器檔案之後才能讀」，dependent 指令的 Decode 就必須延到 producer 的 Write-back 完成之後，也就是 cycle 6 才能真正讀到正確的值——比正常情況下的 cycle 3 晚了整整 6−3=3 個 cycle，等於每一條有資料相依的指令都要白白插入 3 個 stall cycle。有了完整的轉發網路之後，這 3 個 cycle 幾乎全部被省下來：純粹的 register-to-register ALU 相依可以直接在 cycle 3 用 e_valE／M_valE／W_valE 轉發拿到值，變成 0 個額外 cycle；只有 load/use 這一種特殊情況（dependent 指令比 producer 的 load 早一步進到需要運算元的那個點），因為資料物理上真的還沒從記憶體讀出來，才需要（已在 4.5.7 節教過的）1 個 cycle 的 stall，而不是 3 個。

Linux 核心通用佇列 kfifo（Generic FIFO Queue）：SPSC 無鎖設計與環狀緩衝區的位元遮罩技巧

依照成大 Linux 核心課程進度表第 13 週的順序，11/26 教完「Skip List」（清單第 20 項）之後，緊接著的下一項是第 21 項：「Linux: linked list, Queues, Maps, Binary Trees」，一段搭配課堂錄影與共筆、以 Robert Love《Linux Kernel Development》第 6 章「Kernel Data Structures」為基礎的總複習。這一項把四種基礎資料結構打包成一堂課，但 linked list（container_of／intrusive linked list）已經在 08/25 深入教過、binary trees（紅黑樹 rbtree 的旋轉與重新著色規則）也在 09/10 深入教過，依照「深度優先、今天只選一個具體機制」的原則，今天把範圍窄下來，專講這四塊裡還沒真正碰過的一塊：Queues——Linux 核心的通用 FIFO 實作 kfifo（include/linux/kfifo.h）。

kfifo 的核心概念是一個包著固定大小、長度必為 2 的冪的 byte 陣列的環狀緩衝區（ring buffer），但它刻意不去維護「目前讀寫位置」這種會被 wrap-around 搞複雜的索引，而是維護兩個只會一路遞增、從不回繞的無號整數計數器：in（寫入端／producer 目前寫到哪個總位置）與 out（讀取端／consumer 目前讀到哪個總位置）。這個設計選擇的巧妙之處在於：即使這兩個計數器實際上早就「繞」過緩衝區好幾圈，用無號整數減法算出來的 in − out 永遠正確等於目前佇列裡還有多少個元素——這正是利用了很久以前（9 月初）教過的二補數／無號數溢位環繞（overflow wraparound）那套算術規則：只要兩者的差值不超過緩衝區大小，溢位後的環繞剛好自動把「繞了幾圈」這件事抵銷掉，不需要額外記錄圈數。

環狀緩衝區的位元遮罩（Mask）技巧　把遞增計數器換算回緩衝區實際格子位置時，kfifo 用 index & mask（mask = size − 1）取代一般的 index % size。這個技巧只有在 size 剛好是 2 的冪時才成立（因為此時 mask 的二進位是一串連續的 1，跟任何數做 AND 等同於取「低 n 位元」，效果等同於取餘數），但位元運算比真正的除法／取餘數運算在大多數硬體上快得多，這也是為什麼 kfifo_alloc() 一律把你要求的容量向上取整到最接近的 2 的冪。

kfifo 最常被強調的特性是在單一寫者、單一讀者（SPSC）的情境下完全不需要額外上鎖。檔案最開頭就有一段明確的設計說明，逐字抄錄如下：

Note about locking: There is no locking required until only one reader
and one writer is using the fifo and no kfifo_reset() will be called.
kfifo_reset_out() can be safely used, until it will be only called
in the reader thread.
For multiple writer and one reader there is only a need to lock the writer.
And vice versa for only one writer and multiple reader there is only a need
to lock the reader.

（include/linux/kfifo.h · L29-L37，torvalds/linux master 分支）翻成白話：只要同時只有一個 reader、一個 writer，而且沒有人呼叫 kfifo_reset()，就不需要任何額外的鎖；kfifo_reset_out() 可以安全使用，但前提是只能從 reader 執行緒呼叫；如果情境換成多個 writer、一個 reader，只需要鎖住 writer 那一側，反過來一個 writer、多個 reader 也只需要鎖讀者那一側。這套規則能成立的根本原因是「寫者只動 in（以及 out 之後還沒被讀走的空間）、讀者只動 out（以及 in 之前已經寫好的資料）」——兩邊各自只修改自己擁有的那個索引，另一邊讀到的值即使有點「過時」也只會是保守方向（例如寫者看到的 out 稍微舊一點，只會讓它以為可用空間比實際上還少，絕不會覆寫到還沒被讀走的資料），所以不會有真正的資料競爭。

但「不需要鎖」不代表「完全不需要同步」。kfifo_put 這個巨集（逐字抄錄見下方原始碼區塊）在把資料寫進緩衝區格子之後，呼叫了 smp_wmb() 這道寫入記憶體屏障，然後才把 in 遞增——順序不能反過來。原因跟 10 月教過的記憶體排序模型直接相關：如果沒有這道屏障，在允許記憶體操作重排序的架構上，另一個 CPU 上的 reader 有可能先看到「in 已經遞增」（代表有新資料），卻還沒看到「資料本身真的已經寫進那個格子」，讀到一半舊、一半新的垃圾值。smp_wmb() 保證「資料寫入」在所有觀察者看來，一定發生在「in 遞增」這個事實被看到之前——這正是 lock-free 設計真正的難點：不是「要不要上鎖」，而是「如何用正確的記憶體屏障取代鎖」。

smp_wmb()（SMP write memory barrier）　一種只保證「寫入操作之間的順序」的輕量記憶體屏障：確保這道屏障之前的所有寫入，在其他 CPU 眼中一定會比這道屏障之後的寫入更早被觀察到。跟會同時限制讀寫順序的完整屏障（smp_mb()）相比，smp_wmb() 成本更低，在 kfifo 這種「只需要保證資料寫入先於索引更新被看見」的單向需求裡已經足夠。

kfifo 還區分byte stream 模式與record 模式兩種用法（由 __recsize 是否為 0 決定走哪條程式路徑）：byte stream 模式把整個緩衝區當成一條連續的位元組串流，沒有「訊息邊界」概念，適合像 tty/console 這種純粹的位元組搬運；record 模式則會在每筆資料前面多存一個長度欄位，保留「這是一筆獨立訊息」的邊界，適合像封包、結構化訊息這種「讀出來的時候要知道上一筆到哪裡結束」的場景。選錯模式的常見後果是：如果本來要保留訊息邊界卻用了 byte stream 模式，多筆訊息會黏在一起，讀者端必須自己想辦法重新切割。

真實子系統的呼叫點（透過 elixir.bootlin.com 原始碼交叉引用核對過）：drivers/hid/hid-logitech-dj.c（羅技 Unifying 無線接收器驅動程式，用 kfifo 緩衝從同一個接收器多路傳來、要分派給不同邏輯裝置的 HID 封包）、drivers/tty/mxser.c（MOXA 多埠序列卡驅動程式的接收緩衝）、drivers/scsi/libiscsi.c（iSCSI initiator 共用函式庫，多處呼叫點）、以及特別值得一提的 drivers/iio/buffer/kfifo_buf.c——這是 IIO（Industrial I/O，感測器）子系統直接把 kfifo 包裝成整個子系統通用的「取樣緩衝區」後端實作，等於把 kfifo 從一個小工具，升級成一整個子系統對外公開 API 的核心零件。

找到兩篇與今天主題直接吻合、確認內容相符的 jserv 課程社群筆記：2021q3 的作業筆記分析了 jserv 課程的 simrupt 核心模組（模擬 IRQ 事件的教學專案），裡面用 rx_fifo 這個 kfifo 當作 workqueue 產生的資料與使用者空間 read() 之間的緩衝；筆記發現一個很具體的落差：程式碼註解宣稱緩衝區滿了會「丟棄最舊的元素」，但 kfifo_in 實際的截斷行為是丟棄最新寫入的那些 byte，跟註解講的完全相反——這是一個很好的提醒：kfifo 從設計上就不是「環狀覆寫（overwrite oldest）」緩衝區，它永遠保護已經在佇列裡、還沒被讀走的舊資料，如果你真的需要「滿了就丟最舊」的語意，必須自己額外實作，不能指望 kfifo 原生支援。另一篇筆記（分析 kfifo 與 lock-free ring buffer lfring 的對照）則指出 kfifo_out_locked 裡「緩衝區變空就呼叫 kfifo_reset()」這個優化，因為是分兩步分別設定 out 跟 in，中間若被中斷切換，理論上可能讓另一個執行緒讀到不一致的索引組合——這類「文件宣稱的不變量」跟「程式碼實際行為」之間出現落差的案例，正是稽核 lock-free 程式碼時最需要練習抓出來的能力。

這個案例對面試的意義：kfifo 是「有界 SPSC 環狀緩衝區」這個系統設計常見構件最單純的真實範例，跟音訊/視訊串流緩衝、lock-free log buffer、甚至 io_uring 底層的環狀設計都是同一個家族。能不能講清楚「為什麼不需要鎖」（讀寫各自只動自己的索引）、「為什麼還需要記憶體屏障」（索引更新跟資料寫入在多核心上可能被重排序觀察到）這兩層，而不是只停在「這是個環狀緩衝區」的表面認識，是系統面試裡區分及格與不及格答案的分水嶺。

🔢 數學推導

為什麼緩衝區大小必須是 2 的冪：index & mask（mask = size − 1）要跟 index % size 完全等價，前提是 size 的二進位表示法只有最高位是 1、其餘全是 0（也就是 2 的冪）。此時 mask 的二進位是連續 n 個 1（例如 size=1024=2^10 時 mask=1023=0b1111111111），對任意 index 做 AND 之後，效果等同於只保留 index 的低 10 個位元——而「只保留低 n 位元」正好就是「對 2^n 取餘數」的二進位定義本身，兩者在數學上完全相同，不是近似。但如果 size 不是 2 的冪（例如 size=1000），mask=999 的二進位不是連續的 1，AND 出來的結果會跟真正的餘數不一致，技巧直接失效。

向上取整到 2 的冪要付出的空間代價：kfifo_alloc() 拿到使用者要求的容量後，會無條件向上取整到最接近的 2 的冪。這個代價在最壞情況下接近 2 倍：例如要求 513 bytes，會被取整成 1024 bytes，實際配置的記憶體比需求多了 (1024−513)/513 ≈ 99.6%，幾乎整整多一倍；但如果剛好要求 512 bytes（本身已經是 2 的冪），完全不會浪費。平均而言，對隨機落在兩個相鄰 2 的冪之間的需求量，預期浪費比例大約是 25%——這是用「位元運算換取效能」必須接受的空間成本，在容量規劃時需要一併考慮進去。

Linux kernel · include/linux/kfifo.h · L428-L463（kfifo_put 巨集全文，torvalds/linux master 分支）
/**
 * kfifo_put - put data into the fifo
 * @fifo: address of the fifo to be used
 * @val: the data to be added
 *
 * This macro copies the given value into the fifo.
 * It returns 0 if the fifo was full. Otherwise it returns the number
 * processed elements.
 *
 * Note that with only one concurrent reader and one concurrent
 * writer, you don't need extra locking to use these macro.
 */
#define	kfifo_put(fifo, val) \
({ \
	typeof((fifo) + 1) __tmp = (fifo); \
	typeof(*__tmp->const_type) __val = (val); \
	unsigned int __ret; \
	size_t __recsize = sizeof(*__tmp->rectype); \
	struct __kfifo *__kfifo = &__tmp->kfifo; \
	if (__recsize) \
		__ret = __kfifo_in_r(__kfifo, &__val, sizeof(__val), \
			__recsize); \
	else { \
		__ret = !kfifo_is_full(__tmp); \
		if (__ret) { \
			(__is_kfifo_ptr(__tmp) ? \
			((typeof(__tmp->type))__kfifo->data) : \
			(__tmp->buf) \
			)[__kfifo->in & __tmp->kfifo.mask] = \
				*(typeof(__tmp->type))&__val; \
			smp_wmb(); \
			__kfifo->in++; \
		} \
	} \
	__ret; \
})
