矩陣快速幂（Matrix Exponentiation）加速線性遞迴：費波那契、泰波那契與磁磚鋪法

今天換到一個過去這段時間都還沒碰過的分類：矩陣快速幂（Matrix Exponentiation）加速線性遞迴。核心想法很單純：如果一個數列的第 n 項可以寫成「前 k 項的固定線性組合」（也就是係數不隨 n 改變的線性遞迴），那麼這個遞迴關係就可以整個包進一個 k×k 的常數矩陣裡——算第 n 項，等價於把這個矩陣「連乘 n 次」，而矩陣的幂可以用跟整數快速幂（fast power / binary exponentiation）一模一樣的「平方再合併」技巧，在 O(log n) 次矩陣乘法內算出來，不需要真的迴圈跑 n 次。

以費波那契數列為例，令狀態向量 v(n) = [F(n+1), F(n)]^T，可以驗證 v(n) = M^n · v(0)，其中 M = [[1,1],[1,0]]，v(0) = [F(1), F(0)]^T = [1, 0]^T。這個等式成立的原因很直接：把矩陣乘法展開，M · [F(k+1), F(k)]^T = [F(k+1)+F(k), F(k+1)]^T = [F(k+2), F(k+1)]^T，正好是把狀態往前推進一步，跟遞迴定義 F(k+2) = F(k+1) + F(k) 完全對應。只要狀態維度 k 足夠大、能把「決定下一項所需要的全部資訊」都塞進向量裡，任何常係數線性遞迴都可以用這個套路改寫成矩陣形式——泰波那契數列（Tribonacci，每項是前三項之和）就是把狀態擴成 3 維、轉移矩陣變成 3×3。

矩陣乘法結合律（Associativity）　矩陣乘法滿足 (AB)C = A(BC)，這是整套技巧能成立的前提：它保證不管用什麼順序把 n 個 M 相乘，結果都一樣，所以可以用「先算 M^2，再用 M^2 算出 M^4，再合併出 M^n」這種跳躍式的分組方式，而不必乖乖按照 1、2、3…的順序逐步相乘。矩陣乘法不滿足交換律（AB ≠ BA 一般情況下），但快速幂只需要結合律，不需要交換律，所以完全不受影響。

具體作法跟整數的 binpow(a, n, mod) 幾乎是逐行對照：把 n 寫成二進位展開，從最低位往高位掃，維護一個「目前幂」矩陣（每輪自己跟自己相乘，相當於把幂次翻倍）跟一個「累積結果」矩陣（只在該位元是 1 時，把目前幂乘進結果裡）。因為 Fibonacci／Tribonacci 這類題目的數值會呈指數成長，必須在每一次矩陣乘法、每一個元素相加後都立刻對 10^9+7 取模，否則在第二十幾項就已經超出 64-bit 整數範圍；取模的時機不能拖到最後才做一次，因為中間值本身就會先溢位。

Edge case 上有幾個地方特別容易出錯：(1) n=0、n=1、n=2 這類最小的 base case 建議直接查表回傳，不要硬塞進矩陣幂公式，因為 M^0 是單位矩陣，指標處理容易跟遞迴定義的下標對不齊而差一位；(2) 矩陣乘法的相乘順序（左乘還是右乘狀態向量）要跟一開始定義狀態向量的順序保持一致，寫錯順序在 2×2 這種小矩陣可能剛好算出一樣的答案（因為部分元素對稱），但換到不對稱的轉移矩陣就會錯；(3) 語言層面：C++/Java 用 long long/long 存取模後的中間值仍可能在兩個接近 10^9 的數相乘時溢位 64-bit，視數值範圍可能需要先轉型或用 __int128／模乘法技巧。

跟暴力解法的時間/空間完整比較：最原始的遞迴（沒有 memo）是 O(φ^n)（φ 是黃金比例，約 1.618），n 一大就直接爆炸；加上 memo 或改寫成迴圈的標準 DP 是 O(n) 時間、只要保留最後 k 項所以是 O(k) 空間；矩陣快速幂是 O(k^3 log n) 時間、O(k^2) 空間（詳見下方數學推導）。重點是：當題目給的 n 落在 10^5 以內（LeetCode 這幾題的實際限制就是如此），O(n) 的簡單 DP 反而比矩陣快速幂更快、程式碼也更短，矩陣快速幂的優勢只有在 n 真的大到 10^9 以上（例如改成 n ≤ 10^18 的進階版本）才會顯現出來——這也是這題在實務上常被問的「什麼時候該用哪個解法」考點。

常見變形模式，至少有兩種值得記住：第一種是「單一數列計數型」，像 Fibonacci、Tribonacci、以及今天題目之一的鋪磁磚問題——鋪磁磚的遞迴式本身需要自己先推導出來（例如 2×n 的板子用 1×2 骨牌與 L 型三格磚鋪滿的方法數，遞迴式長得比 Fibonacci 複雜，狀態也不只 1 維），推對遞迴式之後套用的矩陣幂技巧完全一樣。第二種是「圖上路徑計數型」：把一張有向圖的相鄰矩陣 A 取 n 次幂，A^n 的第 i 列第 j 行就是「從節點 i 走恰好 n 步到節點 j 的路徑數」——這跟遞迴數列的差別只在於狀態維度從幾個數字變成整張圖的節點數，原理完全相同，LeetCode 上「固定步數後走到某個狀態」類型的題目（例如限定天數內的轉移計數問題）就是這個變形的具體應用。

增廣矩陣（Augmented Matrix）處理仿射遞迴　如果遞迴式帶有常數項，例如 a(n) = c1·a(n-1) + c2·a(n-2) + b（多了一個固定常數 b，不是純線性組合），可以在狀態向量裡多塞一個「永遠是 1」的分量，轉移矩陣對應多一列把這個常數 b 加進去，這樣整個遞迴仍然能寫成「矩陣乘上狀態向量」的純線性形式，繼續套用快速幂——這個技巧叫增廣矩陣，在線性代數與控制理論裡處理仿射（affine）變換時也是同樣的手法。

面試官常見的追問：「如果 n 大到 long long 都快存不下怎麼辦？」——這時通常會引導到 Fibonacci mod m 具有週期性（稱為 Pisano Period），可以先把 n 對週期取餘數再算，徹底避開矩陣快速幂；「如果遞迴係數不是常數、而是跟 n 本身有關呢？」——矩陣快速幂的前提是「轉移矩陣固定不變」，係數隨 n 變化就不能直接套用，需要別的工具（例如生成函數、或者分段處理每個係數固定不變的區間）；「能不能順便求出前 n 項的總和？」——把「目前項的總和」也納入狀態向量的一個分量，讓轉移矩陣同時描述「下一項怎麼算」跟「總和怎麼累加」，一次矩陣幂就能連帶把總和也算出來，不需要另外跑一次迴圈。這類追問考的不是會不會寫矩陣乘法，而是有沒有真正理解「狀態向量要包含哪些資訊才夠」這個設計核心。

這個技巧在面試與實務上的連結不只在矩陣這一個題型：模幂運算（RSA 等公開金鑰密碼學的核心操作）用的就是同一套「平方再合併」的二進位展開技巧，只是物件從矩陣換成一般整數；Markov Chain 的穩態分布計算、PageRank 類演算法在某些加速版本裡，也會用矩陣快速幂去跳過大量次的迭代步驟直接逼近極限狀態。認識這個模式之後，看到任何「狀態轉移是固定規則、但要重複套用非常多次」的問題，都可以反射性地想一下：這能不能用快速幂跳過去？

時間複雜度推導：設狀態維度（矩陣邊長）為 k。兩個 k×k 矩陣相乘，用最直接的三層迴圈做法，需要 k^3 次乘加運算（結果矩陣有 k^2 個元素，每個元素是長度 k 的內積）。把整數快速幂的二進位展開套用到矩陣上：要算 M^n，把 n 寫成二進位，長度是 ⌊log₂ n⌋ + 1 位，演算法對每一個位元最多做 1 次「平方」（更新目前幂）跟最多 1 次「合併進結果」的矩陣乘法，所以總矩陣乘法次數是 O(log n)（精確地說最多 2⌊log₂ n⌋ 次，跟一般的 binpow 完全對應）。兩者相乘，總時間複雜度就是 O(k^3 log n)；額外需要保留目前幂與結果兩個 k×k 矩陣，空間是 O(k^2)。

拿這個式子跟樸素 DP 的 O(n)（狀態只需要保留最後 k 項，空間 O(k)）比較：矩陣快速幂勝出的條件是 k^3 log n < n。以 Fibonacci（k=2）為例，k^3=8，只要 8·log₂ n < n，在 n 大約超過 100 之後就已經成立且差距隨 n 指數拉開；但以狀態數比較多的題目（例如今天題目之一、狀態維度到 k=6 的 552 題）為例，k^3=216，需要 n 大到數千以上才真正划算——這解釋了為什麼 LeetCode 上這幾題官方給的 n 上限通常只到幾萬或十萬量級時，標準 O(n) DP 反而是更實際的選擇，矩陣快速幂的價值要等到題目把 n 的上限拉到 10^9 甚至 10^18 才會真正體現。

Ch.4　4.5.9 Exception Handling

接續昨天（11/25）教完的 4.5.8 節 control hazard 之後，今天進到 PIPE 要面對的第三種、也是性質最不同的狀況：exception（例外）。前兩天的 hazard（data hazard、control hazard）都是「管線化這個設計手法本身必然帶來的暫時性問題」，解法是插入 bubble 或 forwarding，指令本身並沒有錯；exception 則是「這條指令本身就不應該被正常執行完」。Y86-64 定義了會打斷正常執行的三種狀況：halt 指令本身、指令位元組無法解讀成合法指令（invalid instruction／功能碼非法），以及指令抓取或資料存取的位址超出模擬器配置的合法記憶體範圍（invalid memory reference）。

為了讓這三種狀況跟「一切正常」都能用同一套邏輯在管線裡傳遞，Y86-64 定義了一個 4 值的 status code（狀態碼）：AOK（=1，正常執行）、HLT（=2，遇到 halt）、ADR（=3，位址非法）、INS（=4，指令非法）。這四個數值不是隨意編的順序——數值大小本身就是一種「優先權排序」，當同一個檢查點同時可能符合不止一種狀況時，用數值較大者（視為較「嚴重」或檢查順序較優先）決定要回報的狀態，這跟硬體上常見的「優先權編碼器（priority encoder）」是同一種思路，只是用在軟體/HCL 的條件判斷順序上。

Status Code（狀態碼）　貫穿整條管線、附掛在每一條指令身上的一個小整數標籤，用來記錄「這條指令目前為止有沒有遇到需要中斷執行的狀況」。跟資料本身（valA、valE 等）不同，status code 不參與運算，純粹是控制邏輯用來決定「要不要真的讓這條指令完成」的旗標。

Fetch 階段決定 f_stat 的檢查順序，具體反映了上面「數值大者優先」的設計：先看 instruction memory 存取本身是不是有 imem_error（抓指令用的位址就不合法）→ 給 ADR；若位址沒問題，再看抓回來的位元組能不能解讀成合法的 Y86-64 指令（!instr_valid）→ 給 INS；若指令合法，再看這條指令的 icode 是不是 IHALT → 給 HLT；上述都不成立才給 AOK。這個「依序排除」的檢查邏輯，等同於一個多工的 case 判斷，從最該優先回報的狀況開始檢查，跟硬體上用數值比較做優先權仲裁的做法殊途同歸。

Status code 沿著管線暫存器一路往下傳：d_stat 接 Fetch 給的 f_stat、e_stat 接 d_stat、m_stat 接 e_stat，最後進 Write-back 的 W 暫存器變成 W_stat。絕大部分階段只是把狀態原封不動往後傳，但 Memory 階段是整條管線裡唯一一個「狀態可能中途惡化」的地方：如果一條原本是 AOK 的指令，到了 Memory 階段才發現它要存取的資料位址是 dmem_error（位址非法），這時會把狀態由 AOK 改寫成 ADR——這是合理的，因為「資料位址到底合不合法」這件事，物理上就是要等真正發出記憶體存取時才能被偵測到，沒辦法提前在 Fetch 階段就知道。

整節最關鍵的設計決策：PIPE 刻意把「偵測到例外」跟「真正處理例外」這兩個時間點分開——只有當這條指令本身走到 Write-back 階段，它的狀態才會被真正檢查並觸發例外處理流程，中途任何階段偵測到的非 AOK 狀態都只是先標記起來、繼續往後流動。原因跟「程式順序」直接相關：管線裡任一時刻最多同時有 5 條指令在跑，而真正該被服務的例外，一定是程式順序上最早出問題的那一條——即使某條在管線裡位置較後面（例如停在 Decode）的指令，物理上比某條位置較前面（例如停在 Memory）的指令更早被判定出狀態異常，也不能因為「先偵測到」就先處理，否則會違反程式邏輯上的順序。

Precise Exception（精確例外）　處理器對外必須維持的語意保證：當某條指令觸發例外時，「它之前的所有指令」都已經完整、正確地執行完畢並寫回了所有結果，而「它之後的所有指令」則完全不該留下任何已執行的痕跡。PIPE 用「只在 Write-back 才真正 commit 例外處理」的方式，在管線化、多條指令同時在飛的情況下，硬是模擬出這種看起來像循序執行一樣的精確順序。

跟昨天教的分支預測失敗交互影響：mispredicted branch 猜錯時，Fetch 多抓的那兩條指令會被轉成 bubble、效果整個抹除。這兩條 bubble 指令的位元組本來就是從錯誤位址抓來的垃圾資料，很可能剛好被解讀成一條不合法的指令、帶著 INS 狀態繼續往下流——但因為它們一開始就被明確標記為 bubble（不是真正該被執行的指令），PIPE 的硬體設計確保這種「假例外」永遠不會在 Write-back 被真正承認，等同於 bubble 的狀態碼從一開始就被排除在「有效指令」的判定之外。

跟 load/use hazard 的交互也是同一個防護機制的另一次體現：4.5.7 節教過，load/use hazard 會讓控制邏輯在 Execute 階段插入一個 stall bubble。這個 bubble 同樣不帶有任何真正的指令語意，不會、也不該觸發例外。把這點跟上一段放在一起看會發現一個一致的規律：凡是因為管線控制邏輯主動插入的 bubble，一律被當成「沒有發生過」，不能產生任何副作用，自然也不能產生例外——這跟昨天教的「代價跟資訊出現的 stage 位置成正比」是另一個橫跨好幾節課、貫穿整個 4.5 節的共同設計邏輯。

避免副作用（side effect）的具體硬體作法：一旦某個階段看到的狀態是 HLT／ADR／INS（非 AOK），硬體會直接 disable 掉這條指令接下來所有可能改變處理器可見狀態的動作——Execute 階段不更新 condition code（即使 ALU 照常運算，結果也不會寫回 CC 暫存器）、Memory 階段不執行資料記憶體寫入、Write-back 階段不把結果寫進暫存器檔。這確保一條「有問題」的指令，哪怕已經流過半條管線、算出了一堆中間結果，最終也完全不會留下任何可觀察的痕跡，直到 Write-back 才統一決定：是讓它正常 commit，還是真正進入例外處理流程。

這套「狀態一路跟著走、只在最終階段才真正 commit」的設計，本質上就是真實處理器必須支援的 precise exception 語意——作業系統要能在處理完 page fault、除以零、系統呼叫等例外之後正確地恢復執行，前提就是處理器必須保證「看起來好像這條指令之前的所有指令都完整執行完了，之後的完全沒執行」，這跟後面 Ch.8 要教的 Unix/Linux trap、signal、系統呼叫進入點的語意完全呼應（也跟 11/19 教過的 Unix I/O、以及更早教過的 Exceptional Control Flow 彼此銜接）。對面試來說，這類「管線裡平行跑、但對外必須看起來像循序 commit」的設計思路，正是現代 Out-of-Order 處理器裡 Reorder Buffer（ROB）要解決的核心問題，只是 Y86-64 的 PIPE 簡化到剛好可以用 5 個 stage 暫存器加上幾個 disable 訊號硬解決，不需要真正的 ROB 硬體。

🔢 數學推導

把「例外從被偵測到、到真正在 Write-back 被 commit，中間要等幾個 cycle」整理成數字，會發現跟昨天（4.5.8 節）教的 mispredicted branch（代價 2 cycle）、以及前天（4.5.7 節）教的 load/use hazard（代價 1 cycle）是同一條規律的延伸：PIPE 是 5 級管線（Fetch、Decode、Execute、Memory、Write-back），一個在第 s 級被偵測到的狀態，要再經過 5 − s 個 cycle 才會走到 Write-back（第 5 級）被真正處理。Fetch 階段（s=1）偵測到的 ADR／INS／HLT，要等 5−1=4 個 cycle 才 commit；Memory 階段（s=4）才偵測到的 dmem_error 轉成的 ADR，只要再等 5−4=1 個 cycle。

這跟昨天教的 hazard 代價公式本質上是同一個「管線深度 × 資訊出現位置」的規律，只是昨天算的是「需要 stall／squash 幾個 cycle 才能讓後續指令拿到正確的值或正確的下一個 PC」，今天算的是「需要讓一條帶著異常狀態的指令，在管線裡多流幾個 cycle 才能被妥善 commit」——兩者的共同點是：資訊（或狀態）離 Fetch 的那個起點越遠，要等待、要讓管線裡其他東西陪著一起流動的 cycle 數就越多，這是 5 級管線設計裡反覆出現的同一條底層規律。

C · Linux Kernel
§01
Skip List（跳躍串列）與機率平衡資料結構：Linux 核心 Btrfs extent_map 的 skiplist 實作案例

接續 11/25 教完 per-CPU counter 的 sloppy counter 技巧後，今天依照成大 Linux 核心課程進度表 Week 13 清單往下走到「Cache-Oblivious Data Structures」這組條目裡提到的 Skip List（跳躍串列）。這是一種用「隨機化」取代「嚴格平衡規則」的有序資料結構：最底層（第 0 層）是一條完整的有序鏈結串列，每個節點各自以固定機率 p（通常取 0.5）被「晉升」進入上一層，上一層的節點再以同樣機率晉升進更上一層，一路往上，層數越高節點越稀疏。

查詢（search）的走法是從最頂層開始：在同一層一路往右走，直到「下一個節點的 key 已經比目標大」才停下來、往下一層繼續走，重複這個過程一路降到第 0 層才確定找到或沒找到。這本質上是在拿「多層次、稀疏程度遞減」的結構做一種分散式的二分搜尋——跟平衡樹用「結構上嚴格維持的高度平衡」保證效率不同，skip list 靠的是「機率上大多數時候層數分布得剛好」，沒有任何時刻強制要求重新調整整體結構。

RCU（Read-Copy-Update）　Linux 核心裡讓「讀者完全不用上鎖」的同步機制：讀者直接走訪資料結構，寫者更新時先準備好新版本、再用一次原子的指標替換把舊版本「切換掉」，舊版本等所有正在讀的人離開（經過一個 grace period）才真正釋放。Skip list 因為每個節點的指標修改相對局部，天生比較容易套上 RCU 讓讀者無鎖通行。

跟 9/10 教過的紅黑樹（rbtree）旋轉重新著色規則放在一起比較，本質差異會很清楚：rbtree 的 insert/delete 之後常常需要做旋轉＋重新著色，這個操作會動到樹的結構本身，而且旋轉牽涉到的節點範圍有可能波及到跟插入點有一段距離的祖先節點——如果要支援多執行緒同時 insert/delete，必須對一大塊範圍上鎖，否則某個執行緒的旋轉會破壞另一個執行緒正在走訪的路徑。Skip list 的 insert/delete 理論上只需要修改「被插入／刪除的節點」本身所在的那幾層指標，影響範圍侵入性小得多，理論上更適合做 fine-grained lock 甚至配合 RCU 做到讀者完全無鎖。

Linux 核心確實有一個真實的歷史案例：2013 年，Btrfs 檔案系統的主要開發者 Chris Mason 推動用 skip list 取代 Btrfs extent_map 原本用的 rbtree，動機是 RAID5/6 的 parity log 等場景需要更高的併發 insert／lookup 吞吐量。開發者 Liu Bo 以 Con Kolivas 既有的 skip list 實作為起點，加入 RCU 支援，寫成兩篇 LWN 文章：第一篇講設計（sl_list／sl_node／sl_leaf／sl_slot 的分層結構，每個 sl_leaf 用一個大小為 32 的 key 陣列管理一批 key，避免每次搜尋都要讀整個節點），第二篇公布實際的 API（skiplist_preload／skiplist_insert／skiplist_delete／skiplist_lookup／skiplist_lookup_rcu）跟效能測試結果。

效能測試的具體數字很值得細看（完整數字放在下方數學推導區塊）：在單執行緒、循序存取的情境下，rbtree 反而比 skiplist-rcu 快；但在四執行緒併發、以及 IOMMU 隨機讀寫這類高併發場景下，skiplist 大幅勝出 rbtree，差距甚至到幾十倍。這個結果跟前面分析的理論完全吻合：skiplist 的優勢從來不是「單執行緒原始速度比較快」，而是「併發修改時不需要大範圍上鎖」。

後續發展值得記住：儘管效能數字亮眼，根據目前查到的公開資料，這個 skip list 實作最終並沒有被整併成 Linux mainline lib/ 底下的通用資料結構（在目前的 Linux 原始碼樹裡找不到 lib/skiplist.c 這個檔案），Btrfs 的 extent_map 至今仍然是用 rbtree。這是一個很好的提醒：效能測試數字漂亮不代表一定會被合併進核心，還要考慮維護成本、API 是否穩定、跟既有除錯工具（第二篇 LWN 文章結尾提到，當時 skiplist 的鎖定方式還沒有讓 lockdep 能夠理解並檢查）的相容性——核心社群對「新增一個通用資料結構」的門檻一向設得很高。

__builtin_ffs／__builtin_clz　GCC／Clang 提供的內建函式，分別對應 x86 的 bsf（找出最低位的 1 在哪一位）與 bsr／lzcnt（找出最高位的 1、或計算前導 0 的個數）之類的硬體指令，一個 cycle 內完成，遠比逐 bit 寫迴圈去數快得多，常用於需要「找某個 bit pattern 裡第幾位是 1」的場合。

2023 年 sysprog 課程留下的一份延伸筆記（見下方 sources）重新檢視了這組 skip list 程式碼，做了兩個具體優化：第一，決定晉升層數的 random_level 原本用逐 bit 迴圈去算「隨機數從哪一位開始變成 0」，改用 __builtin_ffs(random_seed ^ -1) - 1 一次算出結果，作者實測 perf 顯示指令數減少約 9%、cycles 減少約 18%；第二，依照 key 值範圍的 log 值去限制最大層數（用 __builtin_clz 實作 log2_32），避免層數「長太高」造成無意義的多層走訪——這兩個優化都是「用硬體內建的 bit 操作指令取代軟體迴圈」這個熟悉模式的具體案例，跟很多天前（8/26）教過的位元反轉／位元計數技巧是同一個思路的延伸應用。

這個案例很適合拿來回答面試裡「什麼時候該選 linked list、rbtree，還是 skip list」這類問題：答案不是背公式說 skip list 永遠比較好，而是要講清楚取捨——skip list 犧牲了「保證的最壞情況時間上界」，換取「insert/delete 是局部操作、併發控制簡單很多」，適合讀寫都多、對最壞情況沒有硬性要求的場景；rbtree 犧牲了併發友善性，換取「任何情況下都保證 O(log n)」的硬性上界，這在需要可預測延遲的場景（例如 CFS 排程器用 rbtree 管理 runqueue，絕對不能容忍某次操作突然退化成 O(n)）更重要。能不能講出這種取捨，往往比會不會默寫演算法本身更能反映真正的理解深度。

🔢 數學推導

期望高度的推導：n 個元素、晉升機率 p，第 i 層預期剩下的元素數是 n·p^i。當這個數字降到 1 左右，往上再晉升就沒有意義了，所以層數上限 L 大約滿足 n·p^L ≈ 1，兩邊取對數解出 L ≈ log(1/p)(n)；取 p=0.5 時就是 L ≈ log₂ n。每一層內平均要走訪的節點數是常數（跟 1/p 有關，p=0.5 時平均約 2 步），所以總的期望查詢／插入／刪除時間是「層數 × 每層步數」= O((1/p)·log(1/p) n)，p 視為常數時就是 O(log n)——跟平衡樹同一個量級，差別只在這是機率上的期望值，不是每一次操作都保證的硬上界（高機率仍可能出現某次操作退化成 O(n) 的極端情況，只是機率隨 n 增加而迅速趨近於 0）。

LWN 文章實際量測的數字：RAM 測試（10 萬個項目）裡，單執行緒平均操作時間 rbtree 是 0.752 秒，skiplist-rcu 反而要 2.615 秒（作者認為主要是 spin_lock 本身的額外開銷）；但換到 4 執行緒併發，skiplist 平均時間降到約 3.161 秒，rbtree 卻要 6.660 秒，優劣完全反轉。IOMMU 測試裡差距更戲劇化：循序寫入兩者相差不大（skiplist 1,715MB/s、rbtree 1,659MB/s），但隨機寫入 skiplist 有 1,649MB/s、rbtree 只剩 33MB/s（差了 50 倍），隨機讀取 skiplist 2,484MB/s、rbtree 只有 99MB/s（差了 25 倍）。這組數字清楚印證：rbtree 在隨機存取模式下，旋轉與上鎖造成的競爭成本會被放大到不成比例，而 skip list 因為修改範圍局部、鎖競爭小得多，在這種工作負載下的優勢遠超過理論上「兩者都是 O(log n)」這個表面上的平手結論。
