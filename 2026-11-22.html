Suffix Array（後缀陣列）：倍增法建構 + LCP 陣列，字串演算法的終極共用資料結構，全新分類

過去這幾週我們陸續教過 KMP、Z-function、Manacher's Algorithm、Rolling Hash、Aho-Corasick，這些都是「只解一種特定字串問題」的專用工具：KMP 只管單一模式字串比對、Manacher 只管回文、Aho-Corasick 只管多模式同時比對。今天要教的 Suffix Array（後缀陣列）走的是完全不同的路線——它先花一次 O(n log n) 把一個字串「所有後缀的排序關係」整理成一個通用結構，之後不管面試官追問哪一種關於子字串的問題（最長重複子字串、相異子字串數量、兩個字串的最長共同子字串、字典序第幾大的後缀……），幾乎都能用同一份結構回答，不用重新設計演算法。這正是它被稱為字串領域「終極共用資料結構」的原因。

核心定義很直觀：給定一個長度 n 的字串 s，它有 n 個後缀（suffix）——從每個位置 i 開始一路到字串結尾的子字串 s[i..n-1]。把這 n 個後缀依字典順序排序，Suffix Array（記作 SA[]）就是排序後「每個後缀原本起始位置」組成的陣列。以字串 banana 為例，6 個後缀分別是：0:banana、1:anana、2:nana、3:ana、4:na、5:a。依字典序排列會是 a(5) < ana(3) < anana(1) < banana(0) < na(4) < nana(2)，所以 SA = [5,3,1,0,4,2]——這個陣列本身不是答案，而是後面所有查詢賴以建立的基礎結構。

後缀（Suffix）　字串中從某個位置開始、一路延伸到結尾的子字串；長度 n 的字串恰好有 n 個後缀（包含空字串以前，通常不含空字串本身）。

最直覺的建構方式是「暴力排序」：直接把這 n 個後缀丟給一般的字串排序函式。問題在於，排序過程中每比較兩個後缀，最差情況下要逐字元比較到 O(n) 長度才能分出大小，而排序本身需要 O(n log n) 次比較，兩者相乘得到 O(n² log n)——這就是我們要打敗的暴力解法基準。對 LeetCode 常見的字串長度（n ~ 10&sup4;~10&sup5;）來說，O(n² log n) 幾乎必定超時。

真正可行的建構法是倍增法（Doubling / Prefix Doubling）：核心想法是不要一次比較整個後缀，而是先比較「長度 1 的前綴」排出初始名次 rank[i]（也就是單一字元的字母順序），再用這個名次去比較「長度 2 的前綴」——因為長度 2 的前綴可以拆成兩個長度 1 的片段 (s[i..i], s[i+1..i+1])，用上一輪算好的 rank 直接比較這兩個 rank 組成的 pair 就等價於比較長度 2 的前綴，完全不需要重新逐字元比較。接著用長度 2 的 rank 去推長度 4、再推長度 8……每一輪比較的「有效長度」都倍增，直到長度 ≥ n 為止，此時的名次就等於完整後缀的真正排序。因為每輪只需要排序這些 (rank[i], rank[i+k]) 的 pair（O(n log n) 用一般排序，或用基數排序壓到 O(n)），總共需要 ⌈log&sub2; n⌉ 輪，整體複雜度壓到 O(n log² n)（一般排序）或 O(n log n)（基數排序）。

光有 Suffix Array 本身還不夠，大部分查詢真正要用的是LCP 陣列（Longest Common Prefix Array）：LCP[i] 定義成「排序後相鄰的兩個後缀 SA[i-1] 與 SA[i]」共享的最長共同前綴長度。這個陣列可以用 Kasai's Algorithm 在 O(n) 時間內算出來，關鍵的攤銷論證是：當我們依照「原始字串順序」（不是排序後順序）去計算每個後缀的 LCP 時，這個值每往下一個位置最多只會減少 1，但可以一次增加很多——所以把所有「增加」的量加總起來，會被「總共最多減少 n 次、每次減 1」這個事實限制住，整體增減次數攤銷下來是 O(n)，不是看起來的 O(n²)。

LCP（Longest Common Prefix）　兩個字串（這裡特指排序後相鄰的兩個後缀）從頭開始逐字元比對，第一個不相同的位置之前、共同擁有的前綴長度。

拿 banana 延續剛剛排好的 SA=[5,3,1,0,4,2] 來看 LCP：SA[0]=a(5) 與 SA[1]=ana(3) 共同前綴是 "a"，LCP=1；SA[1]=ana(3) 與 SA[2]=anana(1) 共同前綴是 "ana"，LCP=3；SA[2]=anana(1) 與 SA[3]=banana(0) 沒有共同前綴（a vs b），LCP=0；SA[3]=banana(0) 與 SA[4]=na(4) 共同前綴 0；SA[4]=na(4) 與 SA[5]=nana(2) 共同前綴是 "na"，LCP=2。整個 LCP 陣列是 [_,1,3,0,0,2]（第 0 格沒有左邊相鄰項，通常填 0 或省略）。這裡 LCP 陣列裡的最大值 3，出現在 SA[1]=3（ana）與 SA[2]=1（anana）之間——代表字串裡最長的重複子字串是 "ana"，長度 3，而且馬上可以同時找回它出現在原始字串的哪兩個起始位置（1 跟 3）。這就是「最長重複子字串」問題幾乎零額外計算就能從 LCP 陣列讀出來的原因：答案永遠出現在 LCP 陣列的某個相鄰最大值，因為任何兩個共享長前綴的後缀，排序後一定會被排在彼此附近。

Edge case 需要特別注意：如果字串裡有大量重複字元（例如 "aaaaa"），後缀排序會高度退化——較短的後缀永遠是較長後缀的前綴，這時候比較兩個後缀「誰先結束」就必須視為「結束的那個比較小」，實作上常見作法是在字串尾端加上一個保證比任何合法字元都小的哨兵字元（sentinel，例如 '\0' 或字典序最小的符號），確保每個後缀的長度都不同、不會出現「其中一個後缀正好是另一個的前綴」造成比較歧義。此外要注意 Suffix Array 本身對大小寫、多位元組字元（如中文 UTF-8）一視同仁地當成位元組序列比較，跟真正符合使用者語言習慣的字典順序（collation）是兩件不同的事，這點在 LeetCode 題目裡通常不需要處理，但在真實系統（搜尋引擎、資料庫索引）裡是常見陷阱。

複雜度總表：暴力法（枚舉所有子字串再兩兩比較）通常落在 O(n³) 甚至更差；我們 10/28 教過的 Rolling Hash + 二分搜尋答案長度，可以把「最長重複子字串」做到期望 O(n log n)，但依賴雜湊函式、存在雜湊碰撞風險（需要用雙雜湊或大質數模數降低碰撞機率，正確性不是 100% 嚴格保證）；Suffix Array + LCP 則是 O(n log n)（或 O(n log² n)）確定性達成同樣效果，不依賴隨機性，而且額外附帶「建一次可以回答很多種查詢」的優勢；再進一步，Suffix Automaton（後缀自動機）可以把建構壓到 O(n)，是處理子字串計數類問題最強的結構，但實作複雜度明顯更高，今天先不展開，留在未來深度不足以展開時再教。

至少兩種常見變形模式：第一種是把題目從「單一字串找重複」擴展成「兩個字串的最長共同子字串」——做法是把兩個字串用一個保證不會出現在原字串裡的分隔符號接起來（例如 s1 + "#" + s2），對接起來的整個字串建一次 Suffix Array 和 LCP 陣列，掃過 LCP 陣列時只考慮「排序後相鄰、但分別來自 s1 與 s2 兩側」的那些配對，取其中 LCP 最大值即為兩字串的最長共同子字串長度。第二種是「計算字串中相異子字串總數」：觀察到每個後缀 SA[i] 本身貢獻了 (n - SA[i]) 個子字串（它自己所有的前綴），但其中跟「排序後前一個後缀」共享的前 LCP[i] 個前綴已經被算過了，所以每個後缀真正新增的相異子字串數量是 (n - SA[i] - LCP[i])，把這 n 項加總就是答案，完全不需要用集合（Set）去重，也不用擔心雜湊碰撞。

面試官常見追問：(1) 為什麼倍增法比較 (rank[i], rank[i+k]) 的 pair，就一定等價於比較長度 2k 的前綴？因為前 k 個字元的大小關係已經完整濃縮在 rank[i] 裡（rank 相同代表前 k 個字元完全相同），所以只要 rank[i] 一樣，真正決定勝負的就落在後 k 個字元，也就是 rank[i+k]，這是一個嚴謹的字典序比較的歸納論證。(2) 如果題目要「查詢任意兩個後缀的 LCP 長度」（不只是相鄰的），要怎麼在 O(log n) 內回答？利用一個經典結論：排序後兩個後缀 SA[i]、SA[j]（i<j）的 LCP 長度，等於 LCP 陣列裡 LCP[i+1..j] 這段區間的最小值——因為中間任何一個相鄰對的共同前綴比較短，就會把整段的共同前綴長度拉低，所以只要對 LCP 陣列建一個 Sparse Table 做區間最小值查詢（RMQ），預處理 O(n log n)，之後每次查詢就是 O(1) 或 O(log n)。(3) 這套結構在真實系統裡有什麼對應？Burrows-Wheeler Transform（bzip2 壓縮演算法的核心）就是直接從 Suffix Array 推導出來的；基因序列比對、全文檢索引擎的 FM-index，背後也都是 Suffix Array／Suffix Automaton 家族的延伸——這類「大量不變文字、要支援快速子字串查詢」的場景，正是 Google 這類公司系統設計面試裡偏好的追問方向。

倍增法為什麼是 O(n log n)（或 O(n log² n)）：因為比較的「有效前綴長度」每輪倍增（1 → 2 → 4 → 8 → …），要讓長度覆蓋整個字串（長度 n），最多需要 ⌈log&sub2; n⌉ 輪——這就是輪數的來源。每一輪要做的事情是：把 n 個 (rank[i], rank[i+k]) 的 pair 重新排出新的名次。如果用一般的比較排序，一輪要花 O(n log n)；乘上 O(log n) 輪，總共 O(n log² n)。如果注意到每輪的 rank 值永遠落在 [0, n) 這個有限範圍內（整數，不是任意大小的字串），可以改用基數排序（Radix Sort）把每輪壓到 O(n)，乘上 O(log n) 輪，就能把總複雜度進一步降到 O(n log n)。

LCP 陣列為什麼是 O(n)（Kasai's Algorithm）：關鍵在於換一個順序掃描——不是依照排序後的順序，而是依照原始字串裡「後缀起始位置」的順序去算每個後缀跟它在排序後的左邊鄰居的 LCP。可以證明：若後缀 i 跟它排序後的左鄰居的 LCP 是 h，那麼後缀 i+1（只是把後缀 i 去掉第一個字元）跟它排序後左鄰居的 LCP，至少是 h-1（最多掉 1，不會一次掉更多）。於是用一個變數 h 逐一處理原始順序的每個位置，每次處理完該位置就把 h 減 1 當作下一個位置的起點，若有需要再用 while 迴圈往上加回去——h 在 n 個位置裡最多總共被減少 n 次（每個位置最多減 1 次），所以 while 迴圈裡「加回去」的總次數也最多是 n + n = O(n)，不會是看起來的 O(n²)。

Ch.4　4.5.5 Pipeline Hazards

昨天（4.5.4 Next PC Prediction）解決的是「Fetch 階段要抓哪一條指令」這個問題——靠一組固定規則「猜」，而不是乾等。但光是猜對下一個位址還不夠：PIPE 五級管線裡，同一時刻有 5 條指令分別處於 Fetch／Decode／Execute／Memory／Write-back 五個不同階段，彼此的資料與控制流其實還是緊密相依的。今天這一節（4.5.5 Pipeline Hazards）要處理的是管線化之後必然冒出來的兩類根本問題：資料危障（Data Hazard）——後面的指令需要用到前面指令「還沒算完」的結果；以及控制危障（Control Hazard）——Fetch 猜的下一條指令根本是錯的。這兩類危障如果不處理，管線化帶來的平行度完全沒有意義。

資料危障的典型場景：考慮 irmovq $10, %rdx 緊接著 addq %rdx, %rax。在單週期（SEQ）設計裡，每條指令跑完整個流程才換下一條，所以 %rdx 的值一定早就寫回暫存器檔案了；但在 5 級管線裡，當 addq 進入 Decode 階段要讀取 %rdx 時，irmovq 可能才剛走到 Execute 甚至還沒走到 Write-back，暫存器檔案裡的 %rdx 根本還是舊值。最原始、最保守的解法是暫停（Stalling）：讓 addq 在 Decode 卡住不動（同時讓它後面的指令也在 Fetch 卡住），插入一個什麼都不做的「泡泡（bubble）」，一直卡到 irmovq 真正寫回暫存器檔案為止。問題是：像這樣「前一條指令的結果馬上被下一條用到」的情況在真實程式裡非常常見，若每次都靠暫停硬撐，CPI（每指令所需週期數）會嚴重劣化，管線化幾乎等於白做。

Bubble（管線泡泡）　管線裡某一級被插入的「什麼都不做」佔位狀態，等效於動態插入一條 nop；用來讓某個階段暫停一個 cycle，同時不讓後面階段跟著亂動。

真正解決大部分資料危障的手段是轉送（Forwarding，有些版本譯作 Bypassing）：既然 irmovq 算出來的值其實已經「存在」於某個管線暫存器裡（例如還停留在 Execute 階段輸出、或正準備寫進 Memory／Write-back 階段），根本不需要等它真正寫回暫存器檔案才能用——直接從那個還在管線裡流動的暫存器把值「轉送」回 Decode 階段，餵給正在等待 %rdx 的 addq 當作運算元輸入。PIPE 的 Decode 階段為此設了一整組轉送來源（來自 Execute 階段剛算出的 e_valE、來自 Memory 階段的 m_valM、甚至是 Write-back 階段的值），並依照「最新產生的值優先」的規則去選擇，確保拿到的是最接近正確、最新鮮的那一份。有了轉送網路，前面 irmovq／addq 這組最常見的資料危障幾乎可以完全不用停管線。

但轉送不是萬能藥：有一種資料危障轉送救不回來，就是載入後立即使用（Load/Use Hazard）。考慮 mrmovq (%rbx), %rdx 緊接著 addq %rdx, %rax——mrmovq 真正從記憶體讀出值的時間點是在它自己的 Memory 階段結束時；如果 addq 緊跟在後面進入 Decode 想讀 %rdx，那一刻 mrmovq 還停留在 Execute 階段，連 Memory 都還沒走到，記憶體裡的值根本還不存在、無從轉送。這是整個 PIPE 轉送網路唯一「補不了」的缺口，解法只能退回最原始手段：讓 addq 在 Decode 多停一個 cycle，等 mrmovq 走完 Memory 階段、把讀出來的值透過轉送路徑送回來，才放 addq 繼續往前走。

控制危障則完全是另一條故事線，跟昨天的 predPC 直接相關：昨天教的規則是「條件跳躍一律預測會跳」。等到這條 jXX 真正走到 Execute 階段、ALU 把條件碼算出來之後，才能確認預測對不對。如果猜錯了（實際上沒跳），代表 Fetch 在這之前已經連續抓了兩條「跳躍發生後緊接著的那兩條指令」進管線——這兩條指令此刻正好停在 Decode 與 Fetch 階段——它們全部都是走錯路徑的垃圾指令，必須被清空（Squash）成等效 nop，然後讓 Fetch 從正確的下一條位址重新開始抓取。

Squash（清空）　把已經被誤抓進管線、屬於錯誤執行路徑的指令，強制改寫成等效 nop，讓它流過管線但不產生任何實際效果，藉此取消一次錯誤預測造成的後果。

ret 指令是控制危障裡最極端的個案：Fetch 階段完全沒有任何規則可以預測 ret 要跳到哪裡（返回位址藏在堆疊的記憶體內容裡，Fetch 根本看不到），所以在 ret 真正把返回位址算出來之前，Fetch 唯一能做的就是持續插入泡泡，什麼指令都不抓。這個返回位址要等到 ret 自己走到 Memory 階段把堆疊頂端讀出來（也就是 valM），再經過 Write-back 階段把這個值透過回授路徑送回 Fetch 的 PC 選擇邏輯，才真正可用——下方數學推導區塊會把「ret 需要幾個泡泡」「分支誤判需要幾個泡泡」「load/use 需要幾個泡泡」這三個具體數字，從管線各階段之間的距離精確推出來。

這一節講的其實就是現代超純量處理器裡「暫存器重命名（Register Renaming）」與「推測執行（Speculative Execution）」要解決的同一類問題的最原始版本：真實 CPU 用暫存器重命名讓資料危障幾乎不用停管線（原理上類似更徹底的轉送），用分支預測器＋推測執行＋管線清空機制處理控制危障，只是規模與精密度遠超 Y86 PIPE 的簡單規則。這也是為什麼 Spectre／Meltdown 這類側道攻擊會被拿來當系統組安全面試題：它們正是利用「推測執行後若猜錯會被清空」這個機制，在清空之前的短暫窗口裡，透過快取的存取時間差把本不該洩漏的資料側漏出去——理解今天這節課「猜錯了要怎麼清空、要花幾個 cycle」的基本機制，是理解那類攻擊原理的起點。

🔢 數學推導

三個具體的「需要幾個泡泡」數字，都可以直接從管線各階段之間的距離算出來：(1) Load/Use 危障：1 個泡泡——mrmovq 讀出記憶體值的時間點落在它自己的 Memory 階段結束；若下一條指令緊接在後，原本會在 mrmovq 進入 Execute 的那個 cycle，同時進入 Decode 想讀取這個值，兩者只差 1 級管線的距離，所以讓它多等 1 個 cycle，剛好等到 mrmovq 的 Memory 階段結束、值可以被轉送出來即可，差距正好是 1。(2) 分支誤判：2 個泡泡——條件碼要等到 jXX 進入 Execute 階段（它是 Fetch 之後的第 3 級）才能算出來，而這期間 Fetch 已經多抓了 2 條指令（此刻正停在 Decode 與 Fetch 這兩級），所以要清空的就是這 2 條，誤判確認的那一級（Execute）與 Fetch 之間恰好差 2 級。(3) ret：3 個泡泡——ret 的正確返回位址要等到它本身走到 Write-back 階段（Fetch 之後的第 5 級）才透過回授路徑送回 Fetch，而 Fetch 階段與「值真正可用」的那一級（Write-back）之間，扣掉 Fetch 自己，恰好差 4 級（Decode、Execute、Memory、Write-back），但因為 Write-back 當下那個 cycle 回授的新 PC 立刻可以被同一週期的 Fetch 使用，實際需要墊的泡泡數是 3——也就是 ret 在 Decode、Execute、Memory 這三個階段推進的同時，Fetch 持續插入 3 個泡泡，直到 ret 走到 Write-back 那一刻才抓到正確的下一條指令。這三個數字的共通規律是：泡泡數＝「正確答案真正出現的那一級」與「Fetch 需要這個答案的那一級」之間相差的管線級數，級數差越多，付出的停滯代價就越高，這正是為什麼 ret 比一般分支誤判代價更高、而 load/use 危障代價最低的根本原因。

§01
Debugging Embedded Devices using GDB（嵌入式系統的 GDB 除錯：gdbserver 遠端除錯與事後 Core Dump 分析）

昨天教的 UIO（Userspace I/O）把裝置驅動邏輯搬到使用者空間執行，理由之一正是「使用者空間程式壞掉只會死一個行程，不會讓整台機器當機」；但壞掉之後呢？嵌入式系統通常沒有桌面環境、沒辦法隨手插上螢幕跑圖形化除錯器，程式崩潰時能用的工具非常有限。今天的主題——Chris Simmonds 在 Embedded Linux Conference Europe 2020 的教學場次〈Debugging Embedded Devices using GDB〉——正好補上這塊：如何在資源受限的嵌入式目標機上，有效地用 GDB 找出問題。

嵌入式除錯最根本的限制是：目標機（target）的運算與儲存資源通常太有限，無法直接在上面跑一份完整的、帶齊符號資訊與原始碼的 GDB。解法是把 GDB 拆成兩半——在目標機上只跑一個極輕量的「除錯代理程式」gdbserver，它負責實際控制被除錯的程式（設定中斷點、單步執行、讀寫記憶體），但完全不理解符號名稱或原始碼；真正「有智慧」的那份 GDB（knows the symbol table、原始碼、變數型別）留在開發用的主機（host）上執行，兩端透過一套叫做遠端序列協定（Remote Serial Protocol, RSP）的文字封包協定，經由 TCP/IP 網路或序列埠通訊。

Remote Serial Protocol（RSP）　GDB 與 gdbserver（或硬體除錯探針）之間溝通用的文字封包協定，host 端送出像「讀取某個暫存器」「在某位址設中斷點」之類的請求，target 端的代理程式執行後回傳結果，兩端不需要共用同一份執行檔或符號資訊。

這套「host 端完整 GDB＋target 端輕量 gdbserver」架構，主要用來除錯已經在跑作業系統的使用者空間程式（像昨天教的 UIO 使用者空間驅動）。但如果要除錯的對象是 bootloader、核心本身、或是系統還沒跑起來之前的階段，target 上根本沒有 Linux 可以執行 gdbserver，這時改用JTAG這類硬體除錯介面：透過晶片上專用的除錯接腳，直接用外部硬體探針（如 OpenOCD 搭配的除錯轉接器）控制處理器的暫存器與記憶體，再讓 host 端 GDB 透過同一套 RSP 協定跟這個硬體探針溝通，概念上跟 gdbserver 一致，只是「target 端的代理程式」換成了硬體加韌體，而不是跑在 Linux 使用者空間裡的程式。

JTAG　晶片上標準化的硬體除錯／測試介面，外部除錯探針透過它可以直接控制處理器核心、暫停時脈、讀寫暫存器與記憶體，不需要晶片上已經有作業系統在跑，常用於 bootloader 或核心層級的除錯。

以使用者空間程式為例，實際操作流程是：先在 target 上啟動 gdbserver 監聽某個 port（例如 gdbserver :9999 myprogram），接著在 host 上啟動對應同一份原始碼、同一份符號資訊的 GDB（gdb myprogram），再用 target remote host:9999 連過去，之後設定中斷點、單步執行、檢視變數的操作體驗跟本機除錯幾乎一樣。這裡有個容易忽略的前提：嵌入式映像檔為了省空間，執行檔通常會被 strip 掉除錯符號，所以 host 端的 GDB 必須額外指向交叉編譯工具鏈對應的 sysroot，或是保留一份沒 strip 過、帶著除錯資訊（DWARF 格式）的對應版本執行檔，才能正確把位址對回原始碼的函式名稱與行號。

DWARF　編譯器產生的除錯資訊格式標準，把執行檔裡每個位址對應回原始碼的檔名、行號、變數型別與作用範圍，GDB 靠讀取這份資訊才能把組語位址翻譯成人看得懂的原始碼上下文；這跟我們很早以前教過的 ELF 執行檔格式是互補關係——ELF 定義檔案結構，DWARF 是放在裡面的除錯資料。

除了「程式還在跑、可以即時連上去」的即時除錯（live debugging），嵌入式現場還有另一種更常見但更棘手的情境：裝置部署在客戶端，程式崩潰了，但你人不在現場、也無法重現。這時要靠事後除錯（Post-mortem Debugging）：事先在 target 上設定好 ulimit -c unlimited（允許產生 core dump）與核心的 core_pattern 設定，程式崩潰時系統會把當時的記憶體狀態整個寫成一個 core 檔；只要把這個（通常不大的）core 檔傳回 host，就能用 gdb myprogram core 把當時的完整呼叫堆疊、各層區域變數、記憶體內容重建回來檢視，等於是把「崩潰那一瞬間」完整保存下來慢慢分析，不需要程式還活著、也不需要能重現問題。

GDB 提供的檢查手段不只中斷點（breakpoint，程式執行到某個位置就停下來）這一種：監看點（watchpoint）是當某塊記憶體的值被改寫時才停下來，這在嵌入式 C 程式常見的記憶體踩壞（buffer overflow、野指標寫入）場景特別有用——你不知道「哪一行」寫壞了某個變數，但只要對那個變數設 watchpoint，GDB 會在真正寫入的那一刻停下來，直接抓到兇手；backtrace（呼叫堆疊回溯）則是在崩潰發生時，列出從 main 一路呼叫下來到出事那一行的完整函式呼叫鏈，這對嵌入式系統裡常見「崩潰點其實發生在中斷處理程式或驅動 callback 深處」的情況特別關鍵，能快速定位問題源頭而不是只看到最後一層的症狀。

Edge case 與實務陷阱：多執行緒程式的除錯需要 GDB 搭配與目標 libc／pthread 版本相符的 libthread_db，才能正確列出每個執行緒各自的呼叫堆疊，版本不合時常常只看得到主執行緒、或整個除錯工作階段直接失敗；最佳化編譯（-O2 等）會讓編譯器重新排序指令、甚至直接消掉某些區域變數，導致單步執行時行號跳動詭異、想檢視的變數顯示「已被最佳化掉」，實務上常見做法是保留一份用 -Og（為除錯設計的最佳化等級，兼顧效能與可除錯性）編譯的除錯版映像檔，跟上線的 release 版本分開維護。

這個主題直接銜接到面試裡常被考察的系統理解深度：真正能看懂一支陌生程式在嵌入式裝置上「為什麼壞掉」，需要同時具備我們這幾週教過的 ELF／連結器（符號表哪裡來）、虛擬記憶體（為什麼某個位址讀不到）、以及今天這套交叉除錯架構（為什麼要分 host／target 兩端）的綜合知識——這正是系統組（systems）面試偏好用「給你一支會crash的程式，debug 它」這類題目，測試的不是背誦語法，而是對整條工具鏈與底層機制的理解深度。
