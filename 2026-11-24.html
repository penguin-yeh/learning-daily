二維樹狀陣列 2D Binary Indexed Tree／2D Fenwick Tree：矩陣區域和的查詢與更新，全新分類（304/308/1314/1292）

過去我們教過一維的 Fenwick Tree（樹狀陣列，9/9）、Segment Tree（線段樹，10/3）、Difference Array（差分陣列，11/20）——這些都是處理「一條線」上的動態區間問題。今天要做的是把 Fenwick Tree 的核心想法從一維推廣到二維，處理「一個矩陣上的某個矩形區域的總和」這種查詢，並且矩陣的值還可能隨時被更新。這正是 LeetCode 308「Range Sum Query 2D - Mutable」的核心考點，也是許多實務場景（例如即時更新的熱力圖、影像積分圖的動態版本）背後真正在用的結構。

先把問題講清楚：給一個 rows × cols 的矩陣，要支援兩種操作——(1) update(r, c, val)：把某一格的值改掉；(2) sumRegion(r1, c1, r2, c2)：查詢從 (r1,c1) 到 (r2,c2) 這個矩形區域裡所有元素的總和。如果只需要查詢、矩陣內容完全不會變（LeetCode 304、1314、1292 都是這種「靜態」情境），最簡單的做法是預先算好一份二維前綴和（2D Prefix Sum）表：pre[i][j] 存「從左上角到 (i,j)」這塊矩形的總和，查詢時用容斥原理 pre[r2][c2] - pre[r1-1][c2] - pre[r2][c1-1] + pre[r1-1][c1-1] 一次 O(1) 算出，預處理 O(rows×cols)。但只要矩陣會被動態更新，這張表就整個失效了——改動一格，理論上下游所有 pre[i][j]（i≥r, j≥c）都要跟著變，若每次更新都整張表重算，單次更新要付出 O(rows×cols) 的代價，這就是我們今天要打敗的基準。

暴力解法（完全不預處理）則是另一個極端：每次查詢都對矩形範圍內每一格做雙層迴圈加總，單次查詢 O(rows×cols)，但更新是 O(1)。三種做法擺在一起比較：暴力法（查詢 O(rows×cols)、更新 O(1)）、靜態前綴和（查詢 O(1)、更新 O(rows×cols)）、以及今天的 2D BIT（查詢與更新都是 O(log rows · log cols)）——2D BIT 正是在「兩者都要快」這個需求下，用一棵同時支援動態更新又能快速查詢前綴和的樹狀結構，取代了「查詢快但更新慢」或「更新快但查詢慢」這兩個極端。

要看懂二維版本，得先複習一維 Fenwick Tree 的精神：一維 BIT 的每個節點 tree[i] 並不是存第 i 格的原始值，而是存「以 i 為右端點、長度剛好等於 lowbit(i)（i 的二進位表示法中最低位的 1 所代表的值，例如 lowbit(6)=lowbit(0b110)=2）的一段區間和」。

lowbit(x)　取出整數 x 的二進位表示法中「最低位的 1」所代表的數值，運算式是 x & (-x)（在二補數系統裡，-x 等於 ~x+1，跟 x 做 AND 恰好只留下最低的那個 1 位元）。Fenwick Tree 的每一步移動都是加上或減去 lowbit，這也是為什麼它常被稱為「二進位索引樹」。
更新第 i 格時，只需要沿著 i += lowbit(i) 一路往上走，把沿途經過的所有節點都加上同一個差值；查詢「前 i 格的總和」時，則沿著 i -= lowbit(i) 一路往下走，把沿途節點的值加總。因為 i 的二進位表示法最多有 O(log n) 個 1，兩種操作都只需要 O(log n) 步。

二維 BIT 就是把這套「沿 lowbit 跳躍」的邏輯，同時套用在列（row）與行（col）兩個維度上：tree2d[i][j] 存的是「一個右下角在 (i,j)、高度為 lowbit(i)、寬度為 lowbit(j) 的矩形區塊」的總和。更新 (r,c) 時，外層沿 i = r; i += lowbit(i) 跳列，內層對每個 i 都沿 j = c; j += lowbit(j) 跳行，把 tree2d[i][j] 都加上差值；查詢「左上角到 (r,c) 的前綴和」時，外層沿 i = r; i -= lowbit(i)、內層沿 j = c; j -= lowbit(j)，把沿途節點加總。因為外層跑 O(log rows) 步、每一步內層又跑 O(log cols) 步，單次更新或查詢的總代價是 O(log rows · log cols)。要查任意矩形 (r1,c1)~(r2,c2) 的和，一樣用容斥原理，呼叫四次「前綴和查詢」再加減組合即可，額外代價只是常數倍。

走一次具體例子：一個 4×4、初始全為 0 的矩陣（BIT 陣列用 1-indexed，大小開 5×5）。執行 update(2, 3, +5)（把列 2、行 3 這格加 5）：列方向 i=2 → 2+lowbit(2)=4 → 4+lowbit(4)=8（超出範圍停止），行方向對 i=2 時 j=3 → 3+lowbit(3)=4 → 4+lowbit(4)=8（停止），對 i=4 時同樣 j=3→4。所以這次更新總共碰到 tree2d[2][3]、tree2d[2][4]、tree2d[4][3]、tree2d[4][4] 四個節點，各加 5。接著查詢「左上角到 (3,4) 的前綴和」：列方向 i=3 → 3-lowbit(3)=2 → 2-lowbit(2)=0（停止）；在 i=3 時 j=4→4-lowbit(4)=0，貢獻 tree2d[3][4]=0；在 i=2 時 j=4→0，貢獻 tree2d[2][4]=5。總和為 5——這正確反映了 (2,3) 這個更新落在 (1,1) 到 (3,4) 這個矩形範圍內，應該被算進去。

邊界情形值得特別注意：(1) 2D BIT 必須用 1-indexed，因為 lowbit(0)=0 會讓迴圈條件 i += lowbit(i) 永遠卡在 0、無法前進，所以索引 0 被保留當作「空」的哨兵值，實作時記得把原始矩陣座標 (row, col) 轉成 (row+1, col+1)；(2) update 傳入的是差值（delta）而非絕對值——如果某一格原本是 old、要改成 new，呼叫時要傳 new - old，這是初學者最常忘記的地方；(3) 矩陣退化成一列或一行時，二維 BIT 自動退化回一維 BIT，邏輯完全相容，不需要特別處理；(4) 如果矩陣的列數或行數極大（例如座標範圍到 10&sup9;）又稀疏，直接開 rows×cols 的陣列會爆記憶體，這時需要搭配座標壓縮或改用以雜湊表／字典模擬的「稀疏 BIT」，只替實際出現過的座標建節點。

變形模式一（靜態矩陣，退化用法）：LeetCode 304「Range Sum Query 2D - Immutable」、1314「Matrix Block Sum」、1292「Maximum Side Length of a Square with Sum Less than or Equal to Threshold」這三題的矩陣都不會被更新，完全不需要 2D BIT 這麼「重」的結構——直接用前面提到的靜態二維前綴和表即可，查詢一樣 O(1)、但程式碼簡單得多，沒有 lowbit 跳躍的心智負擔。1314 是對每一格算以它為中心、邊長 2k+1 的區塊和，直接套用前綴和公式；1292 則是在前綴和之上，額外對「正方形邊長」做二分搜尋答案（因為邊長越大、和越大，具單調性，可以二分找最大可行邊長），是「前綴和 + 二分搜尋答案」兩個技巧的疊加應用。这提醒我們一個重要的設計原則：先問清楚題目會不會更新，再決定要不要上 2D BIT，不要看到「矩陣區域和」就反射性地想上樹狀結構。

變形模式二（區間更新＋區間查詢）：如果需求升級成「把整個矩形範圍的所有格子都加上某個值」（區間更新），而不只是單點更新，一維世界裡的標準解法是改用差分陣列搭配 BIT：對差分陣列做一次區間更新只需要兩個點修改。二維版本是同樣想法的推廣——對差分矩陣 diff，一次「把 (r1,c1)~(r2,c2) 整塊都加上 delta」，只需要對 diff 做四次單點更新：diff[r1][c1] += delta、diff[r1][c2+1] -= delta、diff[r2+1][c1] -= delta、diff[r2+1][c2+1] += delta，而查詢任一點 (r,c) 的「目前值」就等於對 diff 做一次二維前綴和查詢。如果同時還要支援「區間查詢總和」（而不只是單點查詢），則需要再多維護一到兩棵輔助 BIT（跟一維「區間加、區間查」需要兩棵 BIT 搭配係數項是同一套數學推導，只是每一步都從一維的加減乘法換成二維的四點展開），複雜度仍是 O(log rows · log cols)，只是常數因子變大。

面試官常見的追問：「為什麼不乾脆用 2D Segment Tree？」——2D Segment Tree 確實也能做到類似功能，但它的節點數與常數因子都明顯更大（本質上是「線段樹的線段樹」），實作複雜度在白板面試的時間壓力下通常不划算，2D BIT 用迴圈加 lowbit 運算就能寫完，是更實際的選擇；「矩陣很大但大部分是 0（稀疏矩陣），要怎麼省空間？」——答案就是前面提到的座標壓縮或雜湊表版 BIT；「能不能把 2D BIT 换成兩個獨立的一維 BIT（先對列、再對行各做一次）？」——不行，因為二維區域和不能簡單拆解成「列方向一維和」乘上「行方向一維和」，矩形區域和的容斥結構本質上需要同時處理兩個維度的巢狀跳躍，這也是這個資料結構「二維」兩個字真正的含義所在。

🔢 數學推導

先複習一維 Fenwick Tree 為什麼是 O(log n)：從索引 i 開始，每做一次 i ± lowbit(i)，至少會把 i 二進位表示法裡最低的那個 1 位元清掉或進位，而一個 n 以內的整數最多只有 O(log&sub2; n) 個二進位位元，所以這個跳躍過程最多執行 O(log&sub2; n) 次就會停止——這就是一維版本單次操作 O(log n) 的來源。

二維版本是「外層跑列方向、內層對每個列座標都跑一次行方向」的巢狀迴圈，外層迴圈次數是 O(log&sub2; rows)，內層每次都要重新跑一次完整的 O(log&sub2; cols)，兩者是乘積關係，所以總複雜度是 O(log&sub2; rows · log&sub2; cols)，而不是相加。拿一個典型規模來算：若 rows = cols = 1000，log&sub2; 1000 ≈ 9.97，單次更新或查詢大約只需要 10 × 10 = 100 次基本加法運算；相較之下，靜態前綴和表在矩陣被更新後要整表重算，代價是 rows × cols = 1,000,000 次——兩者差了約一萬倍。這個數量級差距正是「只要有任何更新操作，就必須放棄 O(1) 查詢的靜態前綴和表，改用 2D BIT」這個設計取捨的量化理由。

📄 原始碼
自製 Python 參考實作（通用二維樹狀陣列邏輯，附逐步複雜度註解，非特定來源引用）
class BIT2D:
    # 1-indexed；rows, cols 為矩陣實際大小
    def __init__(self, rows, cols):
        self.rows, self.cols = rows, cols
        self.tree = [[0] * (cols + 1) for _ in range(rows + 1)]

    def update(self, r, c, delta):
        # 單點更新：把 (r, c)（1-indexed）這格加上 delta，O(log rows * log cols)
        i = r
        while i <= self.rows:
            j = c
            while j <= self.cols:
                self.tree[i][j] += delta
                j += j & (-j)
            i += i & (-i)

    def _prefix_sum(self, r, c):
        # 查詢「左上角到 (r, c)」矩形的總和，O(log rows * log cols)
        s = 0
        i = r
        while i > 0:
            j = c
            while j > 0:
                s += self.tree[i][j]
                j -= j & (-j)
            i -= i & (-i)
        return s

    def region_sum(self, r1, c1, r2, c2):
        # 容斥原理：矩形 (r1,c1)~(r2,c2)（1-indexed，含端點）的總和
        return (self._prefix_sum(r2, c2)
                - self._prefix_sum(r1 - 1, c2)
                - self._prefix_sum(r2, c1 - 1)
                + self._prefix_sum(r1 - 1, c1 - 1))


# 範例：4x4 全零矩陣，update(2,3,5) 後 region_sum(1,1,3,4) == 5
NOTE · 補充

判斷要不要上 2D BIT，先問一個問題就好：「矩陣的內容會不會被更新？」不會更新（304/1314/1292）就用更簡單的靜態二維前綴和，O(1) 查詢已經是最優；只有像 308 這種「資料會變動，又要頻繁查詢範圍和」的情境，才值得付出 2D BIT 的實作複雜度去換取 O(log rows · log cols) 的更新代價。這跟之前教過的「差分陣列只負責區間加值」一樣，都是「先看清楚操作組合，再選對應的資料結構」這個原則的具體案例。

Ch.4　4.5.7 Load/Use Data Hazards

昨天（§4.5.6）教完 Forwarding：只要一個暫存器的新值已經在管線裡的某個階段算出來，即使還沒真正走到 Write-back 正式寫回，也可以靠一條額外線路「轉送」給正在 Decode 階段、急著要讀這個值的後續指令。但昨天的內容結尾特別留了一個伏筆：如果 producer 是一條 load 指令（mrmovq 或 popq），而緊接著下一條指令立刻就要用它 load 回來的值，forwarding 這招會失效。今天這一節（§4.5.7）要正式處理這個被留白的特例——Load/Use Data Hazard（載入使用資料危障），以及為什麼它需要跟 forwarding 不一樣的解法。

先精確定義這個情境：當一條 load 指令（目的地暫存器欄位在 PIPE 裡稱為 dstM，因為它的值來自 Memory 階段）剛好走到 Execute 階段的同一個 cycle，緊接著下一條指令（中間完全沒有其他指令間隔）剛好走到 Decode 階段，而且這條指令要讀的 srcA 或 srcB 正好就是前一條 load 指令要寫入的那個暫存器——這個組合就叫做 load/use hazard。

dstM（Memory 目的暫存器）　PIPE 用來特別標記「這條指令的目的暫存器，其值要等到 Memory 階段讀取記憶體後才會產生」的欄位，只有 load 類指令（mrmovq、popq）會設定它；跟 ALU 運算指令的目的暫存器欄位 dstE 是分開追蹤的。

關鍵問題是：為什麼昨天教的 forwarding 清單解決不了這個特例？回想昨天整理的優先順序清單，第一條就是 e_valE——「此刻正在 Execute 階段、剛算出來的 ALU 結果」。但 load 指令在 Execute 階段根本沒有 ALU 結果可以轉送：它在 Execute 階段只是計算要去記憶體讀取的「有效位址（effective address）」，真正從記憶體讀出來的 valM，要等到下一個 cycle、它走到 Memory 階段才會真的存在。換句話說，這不是「forwarding 線路沒接對」的問題，而是「consumer 需要的那個值，在 producer 目前所在的那個 cycle，根本還沒被算出來」——任何轉送機制都沒辦法轉送一個尚未存在的值，這是純粹的時序問題，不是資料路徑的問題。

解法是把 forwarding 跟插入一個 cycle 的 stall（停頓）結合起來：管線控制邏輯偵測到 load/use hazard 時，讓 Fetch 與 Decode 階段都多停留一個 cycle（重複處理同一條指令，不往前推進），同時在 Execute 階段插入一個 bubble（空泡，等效於插入一條 nop），讓這個 cycle 不會有任何指令真正進入 Execute 做計算。等到下一個 cycle，producer（load 指令）已經走到 Memory 階段、valM 真正被算出來了，consumer 也剛好還停在 Decode——這時候再靠昨天清單裡的第二條 m_valM（「此刻正在 Memory 階段、剛從記憶體讀出來的 load 結果」）把值轉送過去，consumer 才真正往前走進 Execute。整個解法的本質是：先用 1 個 cycle 的 stall「爭取時間」，讓 producer 多往前走一步，直到它進入一個 forwarding 清單裡本來就涵蓋得到的狀態，再套用原本就有的 forwarding 機制。

PIPE 的真實控制邏輯用 HCL 寫成一個訊號，叫 F_stall，用來判斷是否要讓 Fetch／Decode 停住。真實條件（見下方「原始碼」區塊）是：E_icode in { IMRMOVQ, IPOPQ } && E_dstM in { d_srcA, d_srcB }——白話翻譯：「此刻正在 Execute 階段的指令是不是 load 類（mrmovq 或 popq），而且它要寫入的暫存器，剛好就是此刻正在 Decode 階段的指令要讀的 srcA 或 srcB」。值得注意的是，真實的 F_stall 其實是用 ||（或）連接兩個條件，第二個條件（IRET in { D_icode, E_icode, M_icode }）跟 load/use 完全無關，是處理 ret 指令還在管線裡流動時、必須讓 Fetch 暫停抓取下一條指令的另一個獨立理由（這是控制危障，不是資料危障）——兩個邏輯上不相關的 stall 原因，剛好共用同一個訊號名稱，這也是閱讀真實硬體控制邏輯時常見的「一個訊號身兼多職」的情況，不能看到訊號名稱就假設它只對應單一原因。

用一個具體例子走一遍時序：mrmovq 0(%rbx), %rax 緊接著 addq %rax, %rdx。在某個 cycle，mrmovq 剛好在 Execute（此刻它只算出有效位址，%rax 的值還不存在），addq 剛好在 Decode、正要讀 %rax。此時 F_stall 條件成立：Fetch 停住（不抓新指令）、Decode 停住（addq 原地多留一個 cycle）、Execute 被插入一個 bubble（這個 cycle 不會有指令真正執行 ALU 運算）。下一個 cycle，mrmovq 推進到 Memory，valM 被算出來；addq 仍停在 Decode，但現在可以透過 m_valM 這個轉送來源正確拿到剛讀出來的值；再下一個 cycle，addq 才正式進入 Execute，用剛剛轉送到的值做加法。整個過程比起「完全沒有 forwarding、死等 write-back」要快得多，但仍然比「無 hazard、完全不停頓」的情況多付出剛好 1 個 cycle 的代價。

邊界情形：如果 consumer 不是緊接在 load 後面、而是中間隔了至少一條其他指令（例如 mrmovq %rax, ... 之後先執行一條跟 %rax 無關的指令，第三條才用 %rax），這時候當 consumer 走到 Decode，producer 早就已經推進到 Memory 甚至 Write-back 階段了，直接落在昨天教的 forwarding 清單正常涵蓋的範圍內，完全不需要額外停頓——這也再次印證昨天的推導：load/use hazard 之所以特殊，純粹是因為它剛好對應到「0 條指令間隔、但 producer 是 load」這個在轉送清單裡原本不存在對應來源的組合，只要間隔拉開到 1 條指令，問題就自動消失。

這一節在面試／實務上呼應的，是真實處理器裡非常知名的 load-use latency（載入使用延遲）：現代 CPU 的 L1 Cache 命中延遲通常是好幾個 cycle（遠多於 PIPE 這個教學模型的 1 個 cycle），這也是為什麼編譯器的指令排程（instruction scheduling）會刻意把跟 load 結果無關、但本來就要執行的其他指令，插在 load 跟它的使用者中間——只要插入的獨立指令數量夠蓋過這段延遲，CPU 就完全不需要真的停頓，等於把這個「必然的等待」隱藏進「反正都要做的其他工作」裡，不浪費任何一個 cycle。常見的面試追問包括：「為什麼不能用分支預測那種『先猜後驗證』的技巧來消除這個 stall？」（值預測確實是真實研究與部分商用處理器探索過的方向，但需要額外的驗證與回滾機制，成本遠高於簡單插入 1 個 bubble，PIPE 這種教學管線並未採用）、「如果完全不做這個 stall 會發生什麼？」（consumer 會落回 forwarding 清單的最後一條預設選項，直接從暫存器檔案讀到過期的舊值，造成程式邏輯錯誤且難以察覺，因為它不會讓程式當掉，只會算出錯誤答案）、以及「這個 stall 跟分支預測失敗要清空管線比起來，代價差在哪？」（load/use 只需要 1 個 bubble、浪費 1 個 cycle，分支預測失敗則要整條清空已經錯誤抓進來的所有指令，代價通常是好幾個 cycle，這也是為什麼兩者在真實處理器設計裡會用完全不同等級的硬體資源去優化）。

🔢 數學推導

回顧昨天的推導：PIPE 是 F/D/E/M/W 五級管線，producer 跟 consumer 之間的「指令間隔」只可能是 0、1、2 三種，分別對應 producer 在 consumer 做 Decode 的那個 cycle，落在 Execute（e_valE，但只對 ALU 指令有效）、Memory（m_valM / M_valE）、或 Write-back（W_valE / W_valM）。load/use hazard 正是「0 條間隔、但 producer 是 load」這個組合——在這個組合裡，e_valE 這個本來對應 0 間隔的轉送來源，對 load 指令完全不適用（load 在 Execute 階段沒有 ALU 結果），所以 0 間隔這一格，對 load 類指令來說是轉送清單裡的「空格」。

插入剛好 1 個 cycle 的 bubble，效果等同於讓 consumer 在 Decode 多停留一輪，而 producer 照常往前推進一步——這個動作把「0 條間隔」的組合，轉換成「1 條間隔」的組合，而 1 條間隔對 load 指令剛好對應到 m_valM（load 在 Memory 階段讀出來的值），這正是清單裡存在、合法的轉送來源。所以 stall 的 cycle 數不是憑經驗取的，而是直接由「0 間隔到 1 間隔，中間剛好差 1」這個組合推導出來：差距是多少，就要停多少個 cycle，兩者完全對應，不多也不少。

換成量化的效能語言：假設管線沒有任何危障時的理想 CPI（每指令平均週期數）是 1.0，而程式裡有比例 p 的指令屬於「緊接在 load 後面、且直接使用其結果」的 load/use 情況，每次觸發固定多付出 1 個 cycle，則實際 CPI 會變成 CPI = 1 + p × 1 = 1 + p。這也是為什麼編譯器的指令排程要盡量把 p 壓低——排程排得越好、load 跟 use 之間能塞進越多其他有用的指令，p 就越接近 0，CPI 就越逼近理想值 1；排得越差（例如完全不排程、原始碼寫法剛好 load 完就立刻用），p 就越高，管線因為這一種危障造成的效能損失就越大。

§01
Linux Kernel Timer 機制：jiffies 計數、HZ 設定與 timer_list 的到期回呼管理

接續上週的 Device Tree（核心怎麼「知道」板子上有哪些硬體）與再往前的 GDB 除錯、UIO——這些主題解決的都是「硬體已經被認出來、驅動程式已經接管之後」的問題。今天要處理另一個幾乎每個驅動、每個子系統都離不開的基礎建設：核心怎麼追蹤時間的流逝，並且在未來某個時間點，自動執行一段程式碼？這正是成大進度表第 13 週緊接在 Device Tree 之後的下一個主題——Linux Timer 機制。

核心追蹤時間的最底層單位是 jiffies：一個從開機那一刻起、只會往上加的全域整數計數器，每次「計時器中斷（timer interrupt，也就是一次 tick）」發生時就加 1。

jiffies　核心從開機算起的全域 tick 計數器，每次計時器中斷遞增 1；它不是「現在幾點幾分」這種牆上時間，而是純粹的硬體中斷次數累計，要換算成人類看得懂的時間，需要另外配合 timekeeping 子系統與開機時刻校正。
每秒鐘發生幾次 tick，由編譯期常數 HZ 決定——例如 HZ=250 代表每 4 毫秒一次 tick，HZ=1000 代表每 1 毫秒一次；HZ 設得越高，核心能偵測到的時間精度越細，但處理 tick 中斷本身的 CPU 開銷也越高，這是嵌入式與伺服器環境常常要依實際需求去調整的一個經典 trade-off。

要讓核心「在未來某個時間點執行一段程式碼」，用的是 struct timer_list 這個結構（見下方「原始碼」區塊）：最關鍵的兩個欄位是 expires——一個絕對的 jiffies 數值，代表「到了這個 tick 數就該觸發」；以及 function——到期時要呼叫的回呼函式，而且從 Linux 4.15 左右開始，這個函式的簽章統一改成只傳入 struct timer_list * 自己這個指標，驅動程式若想拿回自己真正的裝置結構，要靠 container_of 這個巨集從 timer_list 指標反推回外層結構的位址。

container_of　已經在更早之前教過的核心慣用手法：已知一個內嵌欄位（這裡是 struct timer_list）的位址，加上它在外層結構中的 offset，反推回外層結構本體的位址，讓同一個回呼函式簽章可以服務任何「內嵌了 timer_list」的裝置結構，不需要額外傳遞不透明的 void * context。
初始化靠 timer_setup() 巨集，真正把它掛進核心排程、或是「改期重新掛」則靠 add_timer() / mod_timer()。

核心不會笨到每次 tick 都對「所有已掛起的 timer」做一次線性掃描——那在同時有成千上萬個 timer（例如繁忙伺服器上每條 TCP 連線各自的重傳計時器）的場景下，光是逐一檢查「到期了沒」的開銷就會壓垮系統。真實作法是用一種稱為 timer wheel（計時器輪）的分層雜湊結構：把 timer 按照「還剩多少 tick 到期」分門別類放進不同的桶子裡，越快到期的 timer 被放在精度越細的層級，越晚到期的則先放在粗略的層級、等快到期時再逐步「降級」搬到精確層級。

Timer Wheel（計時器輪）　把大量 timer 依照到期時間遠近分桶存放的分層雜湊結構，讓「插入一個新 timer」與「檢查這個 tick 有沒有 timer 到期」都接近 O(1) 攤銷成本，而不必對全部 timer 做線性掃描。
這讓插入與到期檢查都接近 O(1) 攤銷成本，是能同時服務大量計時器的關鍵設計。

來看一個真實、完整的使用範例：核心原始碼 drivers/watchdog/mtx-1_wdt.c 裡，裝置結構內嵌了一個 struct timer_list timer;（第 52 行），初始化時呼叫 timer_setup(&mtx1_wdt_device.timer, mtx1_wdt_trigger, 0)（第 210 行）；而在回呼函式 mtx1_wdt_trigger() 本身裡面，又呼叫了一次 mod_timer(&mtx1_wdt_device.timer, jiffies + MTX1_WDT_INTERVAL)（第 71 行）——也就是「每次 timer 一觸發，第一件事就是把自己重新掛回未來」。這正是核心裡處理「週期性」行為的標準慣例：struct timer_list 本質上永遠是一次性（one-shot）的，核心並不提供一個「每隔 N 個 tick 自動重複觸發」的內建原語，所有看起來「週期性」的 timer，都是靠回呼函式自己在執行到一半時手動呼叫 mod_timer() 重新排程，才「模擬」出週期行為。

邊界情形值得特別留意：(1) timer 回呼函式執行在 softirq context（而不是一般的 process context），這代表它不能睡眠——不能呼叫可能阻塞的函式、不能用一般的 mutex，只能用專為中斷情境設計的鎖；(2) jiffies 是固定寬度的整數，一定會溢位繞回（wraparound）——這一點在「數學推導」區塊用數字具體算給你看；(3) 正因為會溢位繞回，比較兩個 jiffies 值的先後，絕對不能直接寫 if (jiffies > timeout)，必須呼叫核心提供的 time_after() / time_before() 之類的巨集，它們用訊號運算的方式正確處理繞回後的比較，這是撰寫驅動程式時最容易忘記、也最容易造成「系統執行很久之後才突然出現的詭異 bug」的經典陷阱。

這個主題也呼應了我們 8 月底教過的另一個 Linux 定點數主題（Load Average 的 EWMA 定點數實作）：jiffies 本身從頭到尾都只是一個普通的 unsigned long 整數，核心追蹤時間流逝這件最基礎的工作，完全不涉及任何浮點數運算——這跟核心在效能關鍵路徑上一貫「能用整數運算就絕不用浮點數」的設計哲學完全一致。

面試／實務上的常見追問：「jiffies 為什麼不能直接當作牆上時間（wall clock）用？」——答案是 jiffies 只反映「開機以來經過幾次 tick」，要換算成真正的日曆時間，需要另一個獨立的 timekeeping 子系統配合開機時刻與 NTP 校正，兩者是分開維護、服務不同需求的子系統；「這裡教的低精度 jiffies-based timer，跟核心另一套 hrtimer（高精度計時器）差在哪？」——hrtimer 用紅黑樹依絕對到期時間排序，精度可以做到遠低於一個 tick 間隔（次微秒級），用於 POSIX timers、高精度 sleep 等場景；jiffies-based timer 的精度被綁死在 HZ 的 tick 間隔上，兩者是核心裡並存、服務不同精度需求的兩套系統；「為什麼 timer 回呼不能呼叫會睡眠的函式？」——因為 softirq context 底下沒有一個「正常的 process」可以被排程器切換走再換回來，在這裡睡眠沒有對應的喚醒機制，輕則行為不可預期，重則直接讓核心整個卡死或 panic，這是新手撰寫核心驅動最常踩的其中一個坑。

🔢 數學推導

jiffies 本質是一個固定寬度的整數計數器（常見是 32 或 64 位元），一定會在某個時間點溢位、從最大值繞回 0，這是推導「多久會繞回」最直接的數學問題：繞回週期 = 2³² ÷ HZ 秒。以常見的 HZ = 250 來算：2³² = 4,294,967,296，除以 250 約等於 17,179,869 秒，再除以 86,400（一天的秒數），大約是 198.8 天；如果 HZ = 1000（tick 更密集），同樣的位元數撐不了那麼久，繞回週期縮短成約 49.7 天——這也是為什麼教材裡常提到「32 位元 jiffies 大約 50 天左右就會繞一圈」這個數字的真正來源：HZ 設得越高，同樣的計數空間被更快地用完。

既然一定會繞回，比較「現在是不是已經超過某個 timeout」就不能直接用 a > b，核心的作法是 time_after(a, b) 定義成類似 (long)(b) - (long)(a) < 0——也就是先做一次無號整數相減（相減本身在繞回時也會自動「繞」出正確的差值，這是無號整數運算的模運算特性），再把結果重新詮釋成有號數去看正負號。這個技巧之所以正確，有一個關鍵前提：只要 a 與 b 之間「實際」的時間差距小於計數範圍的一半（對 32 位元來說是 2³¹ 個 tick），把差值重新詮釋成有號數得到的正負號，就一定跟「實際先後順序」一致；換算成時間，在 HZ=1000 時大約是 24.8 天以內的時間差都能正確比較。實務上沒有任何一個 timeout 會被排程到以「超過十幾天」為單位去跟目前時間比較，所以這個條件在真實系統裡永遠成立——這正是一個用「只檢查高位元的正負號」這個簡單整數技巧，正確解決「模運算計數器比較大小」這個看似棘手問題的經典範例。
