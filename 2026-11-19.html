回文分割動態規劃 Palindrome Partitioning DP（全新分類）

給定一個字串，要求把它切成幾段，使每一段都是回文（正讀反讀相同），這一整個題目家族統稱「回文分割」。LeetCode 131、132、1278、1745 是這個家族由淺到深的四個代表：131 要求列出所有合法切法、132 要求最少切幾刀即可讓每段都是回文、1278 放寬成「允許改一些字元」再求最少修改數、1745 則只問「能不能剛好切成 3 段回文」。這四題看似各自獨立，但都建立在同一個基礎工具上：快速判斷任意子字串 s[i..j] 是不是回文。

131 Palindrome Partitioning
列出所有合法回文切法：在 isPal 表上做 DFS/backtracking 枚舉切點，時間 O(n·2^n)（輸出本身就是指數量級），isPal 預處理 O(n^2)。
132 Palindrome Partitioning II
最少切幾刀：一維 DP，minCut[i] = s[0..i] 切成全回文段所需最少刀數，時間 O(n^2)，空間 O(n^2)（isPal 表）+O(n)（minCut 陣列）。
1278 Palindrome Partitioning III
允許改字元、切成剛好 k 段，求最少修改數：先用 O(n^2) DP 算出 cost[i][j]（把 s[i..j] 改成回文所需最少改動），再用 O(n^2·k) 的第二層 DP 選切點。
1745 Palindrome Partitioning IV
判斷能否剛好切成 3 段回文：固定 isPal 表後，對兩個切點 i<j 做 O(n^2) 枚舉（或雙指標收斂），時間 O(n^2)。
🔢 數學推導

先看暴力解法的代價：長度 n 的字串在相鄰字元之間一共有 n-1 個「縫」，每個縫可以選擇切或不切，所以總共有 2^(n-1) 種切法；每種切法還要花 O(n) 檢查每段是否回文，暴力枚舉的總時間是 O(n·2^n)，字串長度一到 30 左右就幾乎跑不完。

關鍵的省錢技巧是：把「某段是不是回文」獨立拆成一張二維表 isPal[i][j] 事先算好，而不是每次切法都重新檢查。回文有一個遞迴結構：s[i..j] 是回文，當且僅當頭尾字元相同（s[i]==s[j]）且中間那一段 s[i+1..j-1] 也是回文（或根本不存在，即 j-i<2 的邊界情形）。這代表 isPal[i][j] 可以只由「更短、範圍包含在 [i,j] 內部」的子問題推出，因此只要讓 j-i 由小到大遞推（或等價地讓 i 由大到小、j 由小到大），就能在 O(n^2) 個子問題、每個 O(1) 轉移的情況下，把整張表填滿——總共 O(n^2) 時間、O(n^2) 空間，查一次是否回文從攤還 O(n) 直接降到 O(1)。這張表填好之後，131/132/1278/1745 全部都只是在這張表之上做不同的第二層決策。

NOTE · 補充

面試官常見追問：

  • 「如果不是求最少刀數，而是要求列出『刀數最少的所有切法』怎麼辦？」——這題等於把 132 的最佳值 DP 與 131 的枚舉結合：先用 132 的 DP 算出每個前綴的最小刀數，再從後往前只沿著「真的能達到最小值」的轉移邊做 131 式的 DFS 還原路徑。
  • 「字串長度到 10^5、10^6 時 O(n^2) 還跑得動嗎？」——跑不動。這時需要換成 O(n) 求所有回文子結構的 Manacher's Algorithm（本頻道 09-20 教過，用「已知的對稱資訊」線性時間求出每個中心的最長回文半徑），或是維護一棵 Eertree（回文自動機），兩者都能把「這段是不是回文」的判斷壓到 O(1) 或攤還 O(1)，但要額外處理切分 DP 怎麼跟這些結構對接，是更進階的追問。
  • 「132 的 DP 轉移要枚舉所有 j，是 O(n) 的，能不能更快？」——如果把內層「找出所有以 i 結尾、且 [j..i] 是回文」的 j 集合，用 Manacher 或 PAM 先攤還列出來，轉移可以降到攤還 O(1)，使 132 整體逼近 O(n)。

邊界陷阱：isPal 遞迴式裡 j-i<2 這個邊界條件最容易寫錯——單字元（j==i）與長度 2 的子字串（j==i+1，只需頭尾相等）都不能真的去存取 isPal[i+1][j-1]，否則會讀到尚未初始化或範圍錯誤的格子。

Ch.4　4.5.2 Inserting Pipeline Registers

上一次（11/18）教到 4.5.1 SEQ+：把 SEQ 單週期處理器的邏輯重新排列，把「決定下一個 PC」這件事從一個週期的尾端概念上搬到開頭，但完全不改變處理器的行為——這只是為了方便後續插入管線暫存器所做的鋪路工作。4.5.2 才是真正動手「管線化」的第一步：在 SEQ+ 原本五個邏輯階段（Fetch 取指、Decode 解碼、Execute 執行、Memory 存取記憶體、Write-back 寫回）的邊界上，各插入一個時脈控制的暫存器，把一條很長的組合邏輯路徑切成五段較短的路徑。

PIPE-　書中對「剛插入暫存器、但尚未處理資料/控制相依性」這個中間版本的硬體設計取的名字，之所以加一個負號，是提醒讀者這個版本的行為還不正確，要到 4.5.5 節處理危障（hazard）之後才會變成真正可用的 PIPE。

具體做法是：在 Fetch 與 Decode 之間、Decode 與 Execute 之間、Execute 與 Memory 之間、Memory 與 Write-back 之間，各放一個暫存器，依慣例分別命名為 F、D、E、M、W。每個暫存器在每個時脈上升緣，把左邊那一階段算出來、右邊那一階段會用到的所有訊號都鎖存起來，直到下一個時脈週期才釋放給右邊的階段使用。這個改動帶來一個關鍵的質變：SEQ 裡只有一個 PC 暫存器，代表任何時刻只有一條指令在被處理；而 PIPE 裡同時有五個暫存器，意味著同一時刻最多可以有五條指令分別處於五個不同階段、同時被處理——這正是管線化能提高吞吐量的根本原因。

用一個具體例子說明：假設 irmovq 指令在時脈週期 1 進入 Fetch 階段，週期 2 進入 Decode、週期 3 進入 Execute、週期 4 進入 Memory、週期 5 進入 Write-back；而緊接著的下一條指令會在週期 2（也就是第一條指令離開 Fetch、進入 Decode 的同一個週期）就進入 Fetch 階段開始被處理，不必等第一條指令整個跑完五個階段才開始。把「指令」畫在縱軸、「時間（週期）」畫在橫軸，可以看到每條指令畫出一條往右下方斜的對角線——這張圖在教材與各校投影片裡通常稱為 管線時空圖（Pipeline Diagram / Space-Time Diagram），是理解管線化吞吐量提升最直觀的工具。

書中同時引入一套訊號命名慣例：凡是跨過某個管線暫存器之後的訊號，會在名稱前加上代表「目前所在階段」的字母當作字首（例如某個值在 Decode 階段叫一個名字，被 D 暫存器鎖存、傳到 Execute 階段後會換成帶 E 字首的名字），這套命名法讓後面幾節（4.5.3 重新排列訊號、4.5.4 下一個 PC 的預測、4.5.5 管線危障）在討論「某個值現在在哪個階段、下一步要傳到哪裡」時，可以一眼從名稱判斷，不必每次回頭查硬體圖。

4.5.2 刻意只處理「怎麼機械式地插入暫存器」，先假設所有指令之間彼此沒有相依性、分支與返回指令的結果總是能被正確預測——這個假設其實是錯的。例如：一條指令要讀的暫存器，如果剛好是前一條還沒寫回的指令要寫的同一個暫存器，PIPE- 這個中間版本會讀到舊值而出錯（資料危障）；又例如一條還在管線中、尚未真正執行完的 jmp 或 ret，PIPE- 必須「猜」下一個要抓取的指令位址，猜錯了就會抓進錯誤的指令（控制危障）。資料危障／控制危障（Data Hazard / Control Hazard）　正是接下來 4.5.4、4.5.5 節要解決的核心問題，4.5.2 只負責把舞台（五個暫存器、五個階段）搭好。

另一個容易被忽略的細節是：每個管線暫存器的「寬度」必須夠大，足以容納右側所有階段未來可能需要用到的每一個訊號，而不只是這一階段「看起來重要」的輸出——漏存任何一個訊號，後面的階段就會永久失去那個資訊，沒有辦法回頭去問前一階段，因為前一階段這時已經在處理別的指令了。這也是教材圖裡每個管線暫存器旁都畫著一長串訊號線的原因。

管線化是處理器與系統設計面試裡最常被問到的主題之一：為什麼管線化能提升「吞吐量」（單位時間完成的指令數）卻不能縮短、甚至會略微拉長「單一指令的延遲」（因為多了暫存器的建立/保持時間 overhead）？為什麼單純插入暫存器還不夠、還需要資料前送（forwarding）、暫停（stall/bubble）與分支預測？這些問題的答案，骨架都在 4.5.2 這一節先立好——之後軟體層面（編譯器指令排程、GPU warp 排程）、甚至系統層面（HTTP/2 的 pipelining、資料庫連線的 pipelining）會重複用到同一個原理：用「緩衝（暫存器／佇列）＋重疊處理」把吞吐量和單次操作延遲解耦。

🔢 數學推導

管線化理想加速比的推導：在 SEQ 裡，整個時脈週期長度 T_SEQ 必須長到足以讓訊號跑完「取指→解碼→執行→存取記憶體→寫回」這一整條組合邏輯路徑並穩定下來，所以 T_SEQ ≥ d_F + d_D + d_E + d_M + d_W（五個階段各自的邏輯延遲之和）。在 PIPE 裡，因為每個階段之間都用暫存器隔開，時脈週期只需要長到讓「最慢的那一個階段」算完即可，再加上暫存器本身的建立/保持時間（setup/hold）開銷 Δreg：T_PIPE ≈ max(d_F, d_D, d_E, d_M, d_W) + Δreg。

如果五個階段的延遲剛好被設計得很平均，各約為 T_SEQ / 5，則 T_PIPE ≈ T_SEQ/5 + Δreg，吞吐量（每秒完成的指令數）在忽略 Δreg 時理想上逼近 5 倍——也就是「加速比 ≈ 管線的階段數」這個經典結論。但要特別注意，這個 5 倍講的是「吞吐量」，不是「單一指令從頭跑到尾的延遲」：每條指令還是要依序經過 5 個週期才算完成，而且因為多了 Δreg 的 overhead，單一指令的絕對延遲其實還比在 SEQ 裡略高一點。等到 4.5.5 節開始處理資料與控制危障後，實際可達的加速比會因為 stall/bubble 而低於這個理想值 5 倍——這正是之後幾節要量化討論的重點。

CS:APP 第 10 章重點提示：Unix I/O 與「一切皆為檔案描述字」

成大 Linux 核心課程進度表 Week 13 在教完「C 語言的物件導向設計」「Stream I/O、EOF 與例外處理」（11/17、11/18 已教過）之後，緊接著的下一個條目是「CS:APP 第 10 章重點提示」——把焦點從 C 標準函式庫的 stream I/O 往下拉一層，看作業系統核心實際提供的 Unix I/O 介面，以及這個介面背後「everything is a file」這句話更精確的講法：「everything is a file descriptor」。

核心概念是：Linux 核心把裝置（終端機、磁碟分割）、管線（pipe）、網路 socket，甚至 /proc、/sys 底下的虛擬檔案，全部統一抽象成一組很小的非負整數——檔案描述字（file descriptor，簡稱 fd）。不管你背後實際存取的是真實磁碟上的檔案、一條匿名管線，還是一條 TCP 連線，使用者空間程式一律用同樣的四個系統呼叫 open/read/write/close（socket 則用 socket() 取得 fd 後同樣可以 read/write）去操作它，完全不需要知道背後的實作細節。這是一種經典的「插入一層間接」的設計：fd 這個小整數本身不是資料，而是核心內部一張表的索引，指向真正描述這個檔案狀態（讀寫位置、旗標、底層 inode 或 socket 結構）的資料結構。

檔案描述字（File Descriptor）　使用者空間看到的只是一個小整數；核心內部每個行程都有一張 fd 表（fd table），表裡每一格存著一個指向 struct file 的指標，而 struct file 又指向真正的 inode／socket／管線緩衝區等底層物件——這一層間接，讓同一個 fd 數字在不同行程裡可以指向完全不同的實體，也讓 dup2()、重新導向（redirection）這類操作只需要改表裡的指標，不必搬動任何實際資料。

依照慣例（但核心並不強制），每個行程啟動時 fd 0、1、2 分別對應標準輸入、標準輸出、標準錯誤輸出，這也是為什麼 shell 做 2>&1 這種重新導向語法時操作的就是這三個固定編號。更重要的是 POSIX 規定的 fd 配置規則：每次 open() 成功時，核心一定會回傳「目前這個行程尚未使用的、數值最小的非負整數」。這個規則本身是今天內容裡少見但很值得講清楚的「數字規則」，詳見下方數學推導區塊。

CS:APP 第 10 章也介紹了 RIO 套件（Robust I/O）——課本作者自己包的一層薄 wrapper，用來正確處理 read/write 系統呼叫常見的「short count」問題：這兩個系統呼叫並不保證一次呼叫就能讀/寫滿你要求的位元組數（可能被訊號中斷、管線緩衝區暫時滿了等），正確的程式必須用迴圈不斷重試、累加已經完成的位元組數，直到湊滿或遇到真正的錯誤／EOF 為止；RIO 把這個迴圈包好成 rio_readn／rio_writen，並額外提供帶內部緩衝區的 rio_readlineb（逐行讀取），是日後寫網路程式（第 11 章 Network Programming）時每個範例程式都會用到的基礎工具。

今天的筆記也特別點出一個常被忽略的作業系統面觀念：Reentrant（可重進入）與 Thread-safe（執行緒安全）　是兩個經常被混用、但定義並不相同的性質——一個函式是 reentrant，通常代表它不依賴任何共享的可變狀態（沒有靜態變數、沒有修改全域狀態），因此同一個函式可以被同一個執行緒在訊號處理器裡「重新進入」而不出錯；thread-safe 則是指多個執行緒同時呼叫這個函式仍能得到正確結果，可能是透過加鎖做到，但加鎖的函式通常反而不是 reentrant（因為訊號處理器裡再次呼叫同一把鎖會死鎖）。這組區分在之後的訊號處理（signal handler 只能呼叫 async-signal-safe 函式）與並行程式設計裡都會再用到。

另一個系統面的細節是跨平台的換行字元（EOL）差異：Linux／macOS 用單一字元 LF（\n，0x0a）代表換行，而 Windows 與大多數網際網路協定（HTTP、SMTP 等）用 CR+LF（\r\n，0x0d 0x0a）兩個字元。這個差異直接影響「跨平台讀文字檔」與「寫網路程式時手動組 HTTP 標頭」兩個場景，若把 Linux 下產生的純 LF 檔案直接丟給某些嚴格遵守協定的網路服務解析，可能因為行尾格式不符而解析失敗。

Unix I/O／檔案描述字這套抽象的優點是介面極其一致、簡單，缺點是「事件通知」天生偏向同步阻塞：一個 read() 在沒有資料時預設會讓呼叫的執行緒整個卡住，這正是後續 11/06 筆記提到的「Linux 核心設計：針對事件驅動的 I/O 模型演化」（select/poll/epoll/io_uring）要解決的問題，也是這個主題在系統設計面試裡反覆出現的原因：理解「fd 是什麼、為什麼要這樣設計」是理解 epoll、io_uring、甚至是資料庫連線池、網路程式 I/O 多工模型的共同起點。

🔢 數學推導

為什麼 POSIX 規定 open() 一定要回傳「目前未使用、數值最小的非負整數」fd，而不是隨便給一個空位？推導如下：如果允許核心任意分配 fd，那麼像 dup2(oldfd, 1)（把 fd 1，也就是標準輸出，重新指向 oldfd 所指的檔案）這類「把某個特定編號的 fd 換成另一個檔案」的操作就無法保證語意一致——很多程式（尤其是 shell 的重新導向、posix_spawn 的 file actions）依賴的正是「關掉 fd 1 再開一個新檔案，新檔案一定會拿到 fd 1」這個確定性。數值最小優先的規則，保證了「關閉某個 fd 後，下一次 open 極大機率會重用那個剛釋放的號碼」，這在 fork/exec 模式下組合出標準輸出、輸入重新導向時是不可或缺的前提：子行程只要先 close(1) 再 open(file)，不需要知道任何額外資訊，就能確定新檔案一定頂替到 fd 1 的位置。這也解釋了一個常見陷阱：如果程式不小心把 fd 0/1/2 其中之一關掉卻忘了重新開，之後任何一次不指定 fd 的 open() 都可能意外拿到 0、1 或 2 這三個「保留」編號，導致後續對 stdin/stdout/stderr 的操作實際上讀寫到完全不相關的檔案——這類 bug 在正式程式碼審查中屬於經典的資安／正確性地雷。
