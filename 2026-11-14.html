加權區間排程 Weighted Interval Scheduling（DP ＋ 二分搜尋）

上次（11/08）練的滑動視窗，本質上是貪心式地維護一個「當下合法」的窗口。今天要換一個表面相似、 但核心完全不同的類別：加權區間排程（Weighted Interval Scheduling）。最經典的「區間排程」問題 （Activity Selection）只問「最多能排幾個互不重疊的活動」，貪心策略（每次挑結束時間最早的）保證最優； 但只要每個區間多了一個權重（profit），貪心就會立刻失效——想像三個互相重疊的工作，利潤分別是 1、1、100， 結束時間最早的那個利潤只有 1，貪心會優先選它，但正確答案顯然是只選利潤 100 的那個。這正是今天要處理的 「加權」版本，必須換成動態規劃。

先把問題講精確：給定 n 個工作，每個工作有 start、end、profit 三個屬性，兩個工作「相容」代表它們的時間區間不重疊（即一個的 end 不晚於另一個的 start），目標是從中選出 一組兩兩相容的工作子集合，使 profit 加總最大。第一步永遠是把所有工作依 end 時間由小到大排序， 這一步排序正是後面能用二分搜尋的前提。

二分搜尋的單調前提 Monotonic Precondition　二分搜尋能用的必要條件不是「資料已排序」這麼單純，而是「搜尋目標函式在排序後的陣列上具有單調性」。本題把工作依結束時間排序後，結束時間本身單調不減，所以能對「結束時間 ≤ 某個開始時間」這個條件做二分搜尋。

排序完之後定義狀態：dp[i] 表示「只考慮排序後前 i 個工作時，能拿到的最大利潤」。 轉移方程式是 dp[i] = max(dp[i-1], profit[i] + dp[p(i)])，其中 p(i) 是「結束時間 不晚於第 i 個工作開始時間」的最大索引（找不到就當作 0）。這個 max 裡的兩項分別對應「不選第 i 個工作」與 「選第 i 個工作，並接上它能相容的最後一段最優解」。

最適子結構 Optimal Substructure　問題的最優解可以由子問題的最優解組合而成，是所有動態規劃解法成立的前提；本題中「前 i 個工作（依結束時間排序後）的最大利潤」確實只取決於「前 i-1 個工作的最大利潤」與「選第 i 個工作後、跳回最後一個相容工作的最大利潤」這兩個子問題。

找 p(i) 的方式就是對「已經排好序的 end 時間陣列」做二分搜尋，找「end ≤ start[i]」的最大索引。 這裡要特別澄清一個常見的混淆：真正支撐二分搜尋合法性的，是排序後的 end 時間陣列本身單調不減，而不是 dp[] 陣列單調——雖然 dp[] 碰巧也會是不減的（因為 dp[i]≥dp[i-1] 恆成立），但這只是附帶結果，二分搜尋從來不是對 dp[] 做的。

複雜度比較：純暴力窮舉每個工作「選／不選」是 O(2ⁿ)，連中等規模（n=30）都跑不完； 加上記憶化但找相容前一個工作用線性掃描，變成 O(n²)；排序後用二分搜尋找 p(i)， 整體降到 O(n log n)（排序 O(n log n) + n 次二分搜尋，每次 O(log n)）。空間複雜度都是 O(n) 存 dp 陣列。這組「指數 → 多項式 → n log n」的遞進，是面試裡示範「為什麼要用 DP」 最乾淨的例子之一。

Edge case 要注意幾種：多個工作結束時間相同時，排序的次序不影響正確性（因為轉移只看數值不看原始順序）， 但實作上要確保 tie-break 一致；區間「剛好相接」（例如工作 A 在 10 結束、工作 B 在 10 開始）通常視為相容 （不重疊），這點要跟題目的定義核對，二分搜尋條件要寫成 end ≤ start而不是 end < start； 如果所有工作兩兩都衝突（形成一條鏈），dp 會退化成逐一比較「選或不選」的線性掃描，仍然正確但失去了二分搜尋的優勢。

這個模式有幾種常見變形。第一種是像 1751 一樣多加一個維度 k：最多只能選 k 個工作， dp 狀態要多一維記錄「目前已經選了幾個」，變成 dp[i][j]，複雜度上升到 O(n·k·log n)。第二種是像 2008 一樣把問題包裝成完全不同的場景（計程車載客）， 但拆開表面敘述後本質跟 1235 一模一樣，是面試官很愛用來測試「你能不能看穿包裝」的手法。第三種更進階的變形是 「串流到達、無法事先排序」的線上版本，這時就要把陣列換成能動態插入並維護前綴最大值的資料結構 （例如以 end 時間為 key 的平衡樹或線段樹），二分搜尋會被線段樹上的區間查詢取代。

面試官常見的追問方向：（1）不只要最大利潤，還要還原出具體選了哪些工作——需要額外一個陣列記錄每個 dp[i] 是從「選」還是「不選」轉移過來，再從 n 往回走；（2）如果資料是即時串流進來、每來一個 新工作就要馬上回答目前最大利潤，要怎麼設計；（3）如果允許工作有「資源需求」而不是單純的 0/1 （例如會議室排程要考慮房間容量），該怎麼把這套框架擴充成多維背包式的 DP。這些追問都是從今天的核心 「排序＋二分搜尋找相容前驅」自然長出來的，值得在練習時主動想一遍。

為什麼整體是 O(n log n) 而不是更快或更慢？拆開看兩個步驟：排序 n 個工作依 end 時間， 不管用什麼排序演算法，下界就是 O(n log n)（比較排序的資訊論下界）；排序完之後，對每一個工作 各做一次二分搜尋找 p(i)，單次二分搜尋是 O(log n)，n 個工作總共 O(n log n)。兩步相加仍是 O(n log n)，不會因為「排序 + n 次 log n」而變成 O(n log n · log n)——因為這兩項是相加而非相乘的關係（先排序一次，再對已排序的結果重複查詢）。

另外值得推導的是：為什麼不能跳過排序、直接在原始順序上二分搜尋？因為二分搜尋的正確性要求陣列具備單調性， 原始輸入的 end 時間完全可能是任意順序；排序這一步正是「用 O(n log n) 的代價，換取之後 n 次查詢各只要 O(log n)」的攤銷設計——如果每次查詢都線性掃描（不排序、不二分），總代價會回到 O(n²)，排序的投資在 n 次查詢之後就回本了。

Ch.4　4.1 The Y86-64 Instruction Set Architecture

上週把第 3 章（x86-64 機器碼）教完了，第 4 章要帶我們從「讀懂機器碼」進一步到「動手設計一顆會執行 機器碼的處理器」。但真正的 x86-64 指令集太龐大、太多歷史遺留的特例，一學期內不可能完整實作出硬體電路。 作者 Bryant 和 O'Hallaron 因此設計了一套教學用的簡化指令集 Y86-64：指令數量大幅精簡、拿掉大量 x86-64 的複雜定址模式與特例，但保留足夠的真實感，讓接下來 4.3 節的單週期處理器（SEQ）與 4.5 節的管線化 處理器（PIPE）都能實際用邏輯閘電路語言 HCL 實作出來並模擬執行。

ISA（指令集架構，Instruction Set Architecture）　軟體與硬體之間的一份固定契約：它規定處理器支援哪些指令、每個指令的語意與編碼格式，但完全不規定底層電路要怎麼實作這些行為——同一份 ISA 可以對應到很慢的單週期電路，也可以對應到很快的管線化電路。
本節要講的「Y86-64 指令集架構」，具體內容分成三塊：處理器對程式設計師可見的狀態 （programmer-visible state）、指令集本身有哪些指令、以及這些指令怎麼編碼成位元組。這三塊合起來，就是 一份完整定義好、不含糊的契約。

先看程式設計師可見狀態：15 個 64-bit 通用暫存器（%rax、%rcx、%rdx、%rbx、%rsp、%rbp、%rsi、%rdi、 %r8 到 %r14，刻意沒有 %r15——因為暫存器欄位用 4 bit 編碼，4 bit 能表示 16 個值，Y86-64 把第 16 個值 0xF 保留當作「沒有暫存器」的 sentinel，而不是真的拿來當第 15 個通用暫存器）、一個程式計數器 PC、 一塊從位址 0 開始、位元組編址的記憶體，以及 3 個條件碼 ZF（零旗標）、SF（符號旗標）、OF（溢位旗標）， 由算術或邏輯指令執行後更新。

Stat（程式狀態欄位）　Y86-64 處理器除了暫存器、PC、記憶體、條件碼之外，還多維護一個 Stat 欄位記錄目前的執行狀態：1 = AOK（正常執行）、2 = HLT（執行了 halt）、3 = ADR（存取不合法位址）、4 = INS（遇到不合法的指令編碼），一旦不是 AOK，處理器就必須停止繼續執行。

指令集本身可以分成幾類：halt（停機）、nop（不做事）、 rrmovq 與六種條件搬移 cmovXX（共用同一個 icode，只靠 ifun 區分是不是加上條件， 這跟上週才教過的「同一大類指令、用功能碼區分變形」的設計思路一致）、irmovq（立即數存進暫存器）、 rmmovq（暫存器存進記憶體）、mrmovq（記憶體讀進暫存器）、四種算術邏輯運算 OPq（addq/subq/andq/xorq）、jmp 與六種條件跳躍 jXX、 call／ret（函式呼叫與返回）、以及 pushq／popq （堆疊操作）。

指令編碼是本節最值得細讀的部分：每條指令的第一個 byte 固定拆成兩個 nibble（各 4 bit）——高 4 位是 icode（指令大類，例如 rmmovq 這整類），低 4 位是 ifun（同一大類底下的具體變形，例如 OPq 底下 addq=0、subq=1、andq=2、xorq=3）。如果這條指令需要暫存器運算元，接著會有第二個 byte，高 4 位放 rA、低 4 位放 rB，不需要的那個欄位一律填 0xF。如果還需要常數（立即數或位移量）， 最後會接上完整 8 bytes，

little-endian（小端序）　多位元組的數值在記憶體中由低位元組先放、高位元組後放。Y86-64 的 8 bytes 常數（立即數或位移量）一律用小端序排列，這跟第 2 章學過、x86-64 在記憶體中擺位元組順序的規則完全一致。
。舉一個完整例子：rmmovq %rbx, 0x18(%rax) （把 %rbx 存到 %rax+0x18 這個記憶體位址）的編碼是 
40 30 18 00 00 00 00 00 00 00
其中第 1 byte 40 是 rmmovq 的 icode:ifun；第 2 byte 30 是 rA=%rbx(3)、 rB=%rax(0)；後面 8 bytes 是位移量 0x18，補成 8 bytes 後以小端序排列（最低位元組 0x18 放在最前面）。

正因為「要不要暫存器 byte」「要不要 8-byte 常數」是依指令類別決定的，整條指令的長度並不固定， 會是 1、2、9 或 10 bytes 其中一種：halt／nop／ret 只有 1 byte （只有 icode:ifun，沒有運算元）；OPq／rrmovq／cmovXX／ pushq／popq 是 2 bytes（多一個暫存器 byte，没有常數）； jXX／call 是 9 bytes（1 byte icode:ifun + 8 byte 絕對目標位址， 注意這裡沒有暫存器 byte，因為跳躍目標是直接給位址不是暫存器）；irmovq／rmmovq／ mrmovq 是 10 bytes（1+1+8）。

Y86-64 處理器還定義了程式狀態欄位 Stat，對應三種非正常狀態：執行到不存在的 icode:ifun 組合會進入 INS（不合法指令）；存取超出範圍的記憶體位址會進入 ADR（不合法位址）； 執行到 halt 會進入 HLT。這幾種異常處理故意做得非常粗糙——一旦不是 AOK，處理器就整個停下來，完全不像真正 x86-64 有特權層級、分頁保護、中斷向量表那樣精緻的 例外處理機制，這是刻意的簡化：Y86-64 的目標是讓讀者看清楚「ISA 定義行為、microarchitecture 決定怎麼 實作這個行為」的分離，不是做出一顆能跑真實作業系統的 CPU。

雖然 Y86-64 本身不會出現在任何求職面試題裡，但這裡建立的「ISA／microarchitecture 分離」概念， 是後面理解「同一套 x86-64 指令集，Intel 和 AMD 的晶片可以用完全不同的管線深度與執行單元去實作」 這類問題的基礎，也直接銜接下週會接續讀到的 4.3 單週期實作（SEQ）與 4.5 管線化實作（PIPE）——同一份 今天定義好的指令集，會先用最笨但最容易懂的單週期方式跑一次，再重新設計成管線化、大幅提升吞吐量。

🔢 數學推導

為什麼暫存器欄位固定用 4 bit？因為 2⁴=16，剛好是「15 個真實暫存器 + 1 個 sentinel」這個需求的最小 位元寬度——用 3 bit 只能表示 8 個值不夠用，用 5 bit 可以表示 32 個值但浪費一半以上的編碼空間，4 bit 正好卡在「夠用」與「不浪費」的邊界上。

為什麼第一個 byte 要拆成 4+4 的兩個 nibble，而不是用一整個 byte 表示「指令種類」？因為 Y86-64 的指令 分類天生有「大類＋變形」兩層結構（例如 OPq 底下有 4 種運算、jXX 底下有 7 種條件），用 4 bit icode 分出 最多 16 個大類、每個大類底下再用 4 bit ifun 分出最多 16 種變形，剛好用 1 個 byte 同時表達兩層資訊， 不需要額外多一個 byte 專門存「變形種類」。

為什麼最長的指令剛好是 10 bytes？因為編碼規則是「1 byte icode:ifun ＋（可選）1 byte 暫存器 ＋ （可選）8 bytes 常數」，8 bytes 是因為 Y86-64 是 64-bit 的 ISA，暫存器與記憶體位址都是 64-bit 寛， 常數必須完整容納一個 64-bit 數值；1+1+8=10 就是三個欄位都出現時的上限，這也是為什麼 irmovq／rmmovq／mrmovq（同時需要暫存器與常數的三種指令） 會是最長的指令。

Linux 共享記憶體機制全景：System V shm、POSIX shm、memfd_create 與 dma_buf

承接 11/08 教過的 POSIX Shared Memory（shm_open／mmap／ftruncate）， 今天把視角拉高，完整看一遍 Linux 歷史上為了「讓兩個以上互不相關的行程直接存取同一塊實體記憶體」這個同一個 目標，陸續長出哪些彼此並不相容、甚至彼此競爭的機制：System V 共享記憶體、POSIX 共享記憶體、 memfd_create，以及跨裝置驅動用的 dma_buf。它們共通的目的都是達成

zero-copy（零拷貝）　讓同一份資料只在實體記憶體存在一份，透過分頁表映射讓多個行程或裝置都能直接存取，而不是像 read()/write() 那樣每次都要在使用者空間與核心空間之間 memcpy 搬一次。
， 省掉 read()／write() 來回在使用者空間與核心空間之間搬資料的開銷。

最早出現的是 System V 共享記憶體：shmget(key, size, shmflg) 用一個全域的 key（或 IPC_PRIVATE）向核心要一塊共享記憶體段，拿到 shmid 之後， 每個想用的行程各自呼叫 shmat(shmid, ...) 把它掛進自己的虛擬位址空間，用完呼叫 shmdt 卸載，整個段最後要靠 shmctl(shmid, IPC_RMID, ...) 明確刪除。 真實核心原始碼（今天附在下面原始碼區）顯示，shmget 系統呼叫背後的 ksys_shmget 把 key／size／flag 包成 struct ipc_params，再呼叫共用的 ipcget()——這個 ipcget 正是整個 System V IPC（shm、semaphore、message queue 共用的那一套）的核心： 先用 key 在目前 IPC namespace 的 id table 裡查有沒有既存的段，查不到才呼叫 newseg() 建立新的。

這裡要特別強調 System V shm 的生命週期陷阱：這個核心物件綁定的是「這個 key／id」，不是任何單一行程， 所有行程都 shmdt 離開後，這塊記憶體依然健在，沒有人主動 ipcrm 或 shmctl(IPC_RMID) 就會一直佔用實體記憶體——這是教科書等級的資源洩漏來源，也是為什麼實務上 ipcs -m 這個指令幾乎是每個資深 Linux 工程師都會的除錯反射動作。

POSIX 共享記憶體（shm_open + mmap）設計上明顯比 SysV 進步： shm_open() 回傳的是一個普通的檔案描述符（fd），底層實際上是掛在

tmpfs　一種把資料直接放在記憶體（必要時可被交換到 swap）而非實體磁碟的檔案系統；POSIX 共享記憶體的 /dev/shm 底層就是一個 tmpfs 掛載點，這也是為什麼 shm_open() 建出來的物件重開機後就會消失。
的 /dev/shm 上。因為是普通 fd，所以可以直接用一般 UNIX 檔案 API 操作它——fstat 看大小、chmod／chown 控權限、甚至可以丟進 poll／select 的監控集合；這些都是 SysV shm 的不透明 shmid 做不到的。也正因為底層是 tmpfs 檔案， 忘記呼叫 shm_unlink() 一樣會讓 /dev/shm 殘留檔案，是另一種形式的同一類洩漏。

memfd_create()（Linux 3.17 引入）更進一步：回傳的 fd 完全匿名，不綁定任何 /dev/shm 路徑名稱，也不需要先 unlink 掉名字來做到「匿名」。它真正強大的地方在於可以搭配 UNIX domain socket 的

SCM_RIGHTS　UNIX domain socket 的一種輔助訊息（ancillary message）類型，讓行程可以把一個開啟的檔案描述符（fd）透過 socket 傳給另一個完全沒有親緣關係（非 fork 出來）的行程，是 memfd_create 配合匿名記憶體跨行程分享的關鍵機制。
，把這個 fd 直接傳給一個完全沒有親緣關係（不是用 fork() 衍生出來） 的行程。更進一步，memfd_create 支援 file sealing（fcntl(fd, F_ADD_SEALS, ...)）， 讓接收端可以放心這塊記憶體事後不會被對方偷改大小或內容——這在 Android 的 zygote fork 模型、 Chromium 的沙箱架構裡都是關鍵的安全邊界機制。

dma_buf 處理的是完全不同層次的「共享」：不是行程之間，而是裝置驅動之間共享一塊 DMA buffer——例如相機驅動把拍到的一張影格匯出（export）成一個 dma_buf fd，GPU 驅動把它匯入（import） 進去直接做影像處理，整段資料完全不經過 CPU 複製。它的介面不是像前三者那樣對應到具體系統呼叫，而是 核心內部的 struct dma_buf_ops 這組 callback（attach／map_dma_buf／ release／mmap），由各裝置驅動自己實作，再透過 dma_buf_fd() 包裝成使用者空間看得到的 fd。

有一個貫穿四種機制都要留意的陷阱：共享記憶體本身只解決「資料怎麼讓兩邊都看得到」，完全不解決 「誰先寫、誰先讀」的同步問題——兩個行程同時寫同一塊共享記憶體，一樣會有資料競爭（data race）， 仍然需要額外搭配 POSIX semaphore、futex 或 atomic 操作來保護，這點常常被剛接觸共享記憶體的人誤會成 「用了 shm 就自動安全」。

與系統設計面試的關聯：這幾種機制最終都繞不開 mmap 把實體記憶體映射進 virtual address space 這個核心概念，直接呼應 CS:APP 虛擬記憶體章節、也是上週（11/07）記憶體管理主題的延伸。系統設計 面試裡常見的「兩個 process 之間要交換大量資料，你會怎麼設計」這類問題，比較 SysV／POSIX／memfd 的 trade-off（相容性 vs. 介面乾淨度 vs. 匿名傳遞能力）正是一個很扎實的切入角度；選用準則大致是： 舊程式碼相容或嵌入式環境→SysV；一般新應用→POSIX shm；需要匿名傳給無親緣關係行程或做沙箱隔離→ memfd_create；跨裝置驅動的 zero-copy pipeline→dma_buf。

🔢 數學推導

memfd_create 的 file sealing 用的是位元旗標（bitmask）設計：F_SEAL_SEAL=0x0001、 F_SEAL_SHRINK=0x0002、F_SEAL_GROW=0x0004、F_SEAL_WRITE=0x0008。 用 OR 把多個旗標組合起來一次設定（例如同時封印「不能縮小」與「不能寫入」），核心內部再用 AND 去檢查 某個旗標有沒有被設定，這跟幾週前才教過的 C 語言 bit-field／bitwise 操作是同一套思路：每個獨立的 「能不能做某件事」用一個 bit 表示，組合狀態用 OR，查詢狀態用 AND，4 個旗標剛好只需要 1 byte 就能表達 全部 16 種組合（其中 F_SEAL_SEAL 本身是「封印這組旗標，不准再加新旗標」的 meta-旗標， 一旦設定就讓剩下三個旗標的狀態從此凍結）。

long ksys_shmget(key_t key, size_t size, int shmflg)
{
	struct ipc_namespace *ns;
	static const struct ipc_ops shm_ops = {
		.getnew = newseg,
		.associate = security_shm_associate,
		.more_checks = shm_more_checks,
	};
	struct ipc_params shm_params;

	ns = current->nsproxy->ipc_ns;

	shm_params.key = key;
	shm_params.flg = shmflg;
	shm_params.u.size = size;

	return ipcget(ns, &shm_ids(ns), &shm_ops, &shm_params);
}

SYSCALL_DEFINE3(shmget, key_t, key, size_t, size, int, shmflg)
{
	return ksys_shmget(key, size, shmflg);
}
