歐拉路徑與 Hierholzer's Algorithm（Eulerian Path／Circuit）

今天的子主題是歐拉路徑／歐拉迴路（Eulerian Path／Eulerian Circuit）與求解它的標準演算法 Hierholzer's Algorithm。這是圖論裡少見的「以邊為中心」的遍歷問題：目標不是走訪每個頂點恰好一次（那是 Hamiltonian Path，屬於 NP-hard），而是走訪圖中每一條邊恰好一次（頂點可以重複經過）。歐拉迴路（circuit）額外要求起點與終點相同；歐拉路徑（path）則允許起點、終點不同。這個區分很重要，因為它決定了圖必須滿足的前提條件，也決定了演算法要從哪個頂點開始走。

Eulerian Path vs. Hamiltonian Path　歐拉路徑關心「邊」是否都被走過恰好一次，可以在 O(V+E) 判定存在性並在線性時間內求出；Hamiltonian Path 關心「頂點」是否都被走過恰好一次，判定存在性是 NP-complete。面試中很容易把兩者搞混，務必先說清楚問題問的是邊還是頂點。

存在性條件是第一個該掌握的重點。無向圖：歐拉迴路存在的充要條件是圖（忽略零邊的孤立點）連通，且每個頂點的 degree 都是偶數；歐拉路徑（非迴路）存在的充要條件是圖連通，且恰好有 0 個或 2 個奇數 degree 的頂點——若有 2 個，路徑必須以這兩個頂點為起訖點。有向圖的條件則是看每個頂點的 outdegree - indegree：歐拉迴路要求每個頂點都平衡（差值為 0）；歐拉路徑則最多允許一個頂點差值為 +1（作為起點）、一個頂點差值為 -1（作為終點），其餘必須平衡，且圖必須是弱連通的。這些條件可以在線性時間內直接算出，不需要真的跑一遍演算法。

Hierholzer's Algorithm 的運作原理可以拆成幾步：(1) 選一個合法的起點（有向圖選 outdegree−indegree=1 的頂點，若不存在則任選一個有邊的頂點）；(2) 用一個顯式的 stack 模擬 DFS，每走一步就把剛剛用掉的邊「消耗掉」（從鄰接表移除，或移動該頂點的邊游標）；(3) 當目前頂點已經沒有未使用的邊（走到死路）時，把這個頂點 pop 出來、記錄進結果序列；(4) 回退到呼叫它的上一個頂點，繼續嘗試該頂點剩下的邊；(5) 重複直到 stack 清空，最後把記錄下來的結果序列反轉，就是一條合法的歐拉路徑。直覺上，這其實是後序（postorder）記錄：一個頂點只有在「它所有邊都已經走完」之後才會被記錄，所以整條記錄序列反過來看，剛好是「先走的邊在前面」。

用 332. Reconstruct Itinerary 具體示範：題目給一堆機票 [from, to]，要從 JFK 出發，用光所有機票、且在有多種合法走法時回傳字典序最小的那一條。做法是把每個機場的目的地清單排序（或用 min-heap），對 JFK 跑 Hierholzer's DFS，每用掉一張票就從該機場的待選清單移除，卡住時把機場名稱 push 進結果堆疊，最後整個堆疊反轉就是答案。因為每一步都優先挑字典序最小的目的地，保證得到的是字典序最小的合法路徑。

Edge case 是這類題目最容易出錯的地方：(a) 重邊（parallel edges）——同一對 [from, to] 可能出現多次，必須用可以計數的結構（例如每個機場對應一個 multiset 或 Counter）而不是用 set 去重，否則會漏掉合法的邊；(b) 自環（self-loop）——在有向圖中會同時貢獻 outdegree 與 indegree 各 +1，通常不影響平衡性判斷，但要記得它也要被走過恰好一次；(c) 孤立無邊的頂點——只要圖中「有邊相連的部分」整體連通即可，跟邊無關的孤立頂點不影響歐拉路徑是否存在；(d) 若題目強制指定起點（像 332 題一定要從 JFK 出發），但這個起點不滿足 outdegree−indegree=1 的條件，就代表這組機票本身不可能用光，要先用存在性條件快速判斷再動手，而不是寫到一半才發現無解。

複雜度比較是面試官最愛追問的地方。暴力解法大致有兩種：①把所有邊的排列當作候選路徑，逐一檢查是否合法，時間複雜度 O(E!)，完全不可行；②用 backtracking，每一步都重新掃描整份邊列表找「還沒被標記為用過」的邊，時間複雜度退化成 O(E²)（詳細推導見下方「數學推導」區塊）。Hierholzer's Algorithm 的關鍵優化是讓每個頂點保留一個「指向下一條未使用邊」的游標（而不是每次重新掃描），使得整條邊只會被存取、消耗一次，總時間壓到 O(V+E)、空間 O(V+E)（鄰接表＋結果堆疊）。如果像 332 題那樣還要求字典序最小，改用 heap 維護每個頂點的鄰居，時間變成 O(E log E)（每條邊進出 heap 各一次）。

常見的變形模式至少有兩種值得記住：①De Bruijn Sequence（如 753. Cracking the Safe）——把每個長度 n-1 的字串當作頂點、每個長度 n 的字串當作一條邊，求遍歷所有邊恰好一次的歐拉迴路，等價於求出涵蓋所有可能密碼組合的最短覆蓋序列，頂點數 k^(n-1)、邊數 k^n；②任意起訖點的有向圖歐拉路徑（如 2097. Valid Arrangement of Pairs）——把每個 pairs[i] = [u, v] 當作一條邊 u→v，求一條用掉所有邊恰好一次的路徑，起點不固定，只需先用 outdegree/indegree 找出合法起點（若全部平衡則任選有邊的頂點作為起點，結果會是一個迴路）。另外還有無向圖版本的延伸——「中國郵遞員問題」（Chinese Postman Problem）：當圖不滿足歐拉迴路條件時，先用最小權重完美匹配把奇數 degree 的頂點兩兩配對、加上額外邊讓圖重新滿足條件，再套用 Hierholzer's 求解。

面試官常見追問：①「如何保證結果字典序最小？」——答案是鄰接表要排序或用 min-heap，每次優先走最小的未用邊；②「如果圖有多個互不相連的部分，但只有一部分含有全部的邊，怎麼辦？」——答案是只要「有邊的部分」整體連通即可，忽略完全沒有邊的孤立頂點；③「只需要判斷『圖是否存在歐拉路徑』，不需要真的求出路徑，怎麼優化？」——答案是只需要 O(V+E) 算出每個頂點的 degree／outdegree−indegree 並檢查連通性，完全不需要真的跑一次 Hierholzer's；④「遞迴版的 Hierholzer's 在邊數很多時會不會 stack overflow？」——答案是會，實務上要改寫成顯式 stack 模擬遞迴，搭配每個頂點的邊游標，才能處理邊數上萬甚至上百萬的圖。

為什麼「每次重新掃描邊列表找未用邊」的 backtracking 會退化成 O(E²)？設圖中共有 E 條邊。若每個頂點不保留游標，而是每走一步都要從頭掃描該頂點的鄰接表，跳過前面已經被標記為「用過」的邊，才找到第一條未用邊——那麼對某個頂點而言，它被訪問第 i 次時，平均要跳過 O(i) 條已用邊才找到可用邊。把這個成本加總到整個演算法（總共恰好執行 E 次「消耗一條邊」的操作），最壞情況（例如所有邊集中在同一個頂點的星狀多重圖）會變成 1 + 2 + 3 + ... + E = E(E+1)/2 = O(E²)。舉具體數字：若 E = 10⁵（十萬條邊，一張中等規模的圖），O(E²) 就是 10¹⁰ 次操作，在一般競程 1 秒時限（約 10⁸～10⁹ 次操作）內必定超時；而改用「每個頂點保留一個只會前進、不會回頭的邊游標」後，游標總共只會被推進 E 次（每條邊恰好讓某個游標往前移動一次），總時間變成 O(E) = 10⁵，快了五個數量級。這正是 Hierholzer's Algorithm 在實作上「必須用游標／index 而不是每次重新掃描」的理論依據——它不是風格選擇，而是決定演算法是 O(E) 還是 O(E²) 的關鍵。

Ch.4　4.4 General Principles of Pipelining

今天接續 11/16 的 Ch.4 §4.3 Sequential Y86-64 Implementations，進入全書第四章的轉折點：§4.4 General Principles of Pipelining。§4.3 介紹的 SEQ（sequential）處理器把一條指令的 fetch、decode、execute、memory、write-back 五個階段全部塞進同一個 clock cycle，一條指令完全走完才能開始下一條；本節要解決的問題是：這種做法的 clock rate 被整條組合邏輯的「關鍵路徑」（critical path）長度卡死，而且每個 cycle 裡大部分硬體其實是閒置的（fetch 單元在做 decode 時完全沒事做）。Pipelining 就是為了同時解決這兩個問題而生的設計原則。

throughput（生產量）　單位時間內完成的指令數，常用 GIPS（Giga Instructions Per Second，每秒十億條指令）衡量，是 pipelining 主要想拉高的指標。

運作原理逐步拆解：把一個大任務拆成一系列更小的階段（stage），不要求一個任務走完全部階段才讓下一個任務開始，而是讓多個任務同時在系統裡、分別處於不同階段。具體到硬體實作，就是在每個 stage 之間插入pipeline register：這些暫存器在每個 clock edge 把上一個 stage 算好的結果鎖存下來，這樣下一條指令的第一個 stage 就可以在上一條指令還在後面 stage 進行時提前開始，不用等整條指令跑完。書中用自助餐排隊與自動洗車的流程類比：不是一位客人走完全程才讓下一位進場，而是讓多位客人同時分散在不同環節上，整體出餐／出車的速率（throughput）因而提升。

critical path（關鍵路徑）　一個組合邏輯電路中，從輸入訊號穩定到輸出訊號穩定所需時間最長的那條訊號路徑，它直接決定了 clock period 的下限：clock 跑得比這條路徑的延遲還快，電路就會讀到還沒算完的錯誤訊號。

具體數字例子（教材的標準範例）：假設一條指令所需的全部組合邏輯共需 300ps，加上一次暫存器鎖存延遲 20ps。未管線化時，一條指令的 latency（從開始到結束的總時間）是 300 + 20 = 320ps，throughput 約為 1/320ps ≈ 3.1 GIPS。若把這 300ps 的邏輯平均拆成 3 個各 100ps 的stage，每個 stage 後面都接一個 20ps 的 pipeline register，clock period 就縮短為 100 + 20 = 120ps，throughput 提升到約 1/120ps ≈ 8.33 GIPS——但一條指令仍要走完 3 個 clock cycle 才算完成，latency 反而變成 3 × 120ps = 360ps，比未管線化的 320ps 還長。這正是 pipelining 的本質取捨：throughput 上升，但單條指令的 latency 可能略微增加，因為多付出的暫存器延遲被重複計算了 k 次（k 是 stage 數）。

Edge case／限制有兩個：①Nonuniform Partitioning（不均勻切分）——整條 pipeline 的 clock rate 由最慢的那個 stage 決定（木桶的短板），但像 ALU 運算或記憶體存取這類單元很難再被切得更細、更均勻，所以實務上很難讓每個 stage 的延遲完全一致；②Diminishing Returns（收益遞減）——stage 切得越細，每個 stage 本身的邏輯延遲越小，但固定的暫存器開銷 20ps 占比卻越來越高，throughput 的提升幅度會隨著 stage 數增加而趨緩，最終被暫存器延遲本身卡住上限（見下方數學推導）。現代真實 CPU 常見 15 級以上的深管線（deep pipeline），正是在這個 trade-off 下，靠非常精細的電路設計與 clock distribution network 把暫存器開銷壓到最小才做到的。

§4.4.4 Pipelining a System with Feedback 則是為下一節（§4.5 真正實作 PIPE，也就是管線化版的 Y86-64 處理器）鋪路，引入兩種「相依性」：data dependency（資料相依）——後面的指令需要用到前面指令算出來的結果（例如暫存器值）；control dependency（控制相依）——條件分支指令（如 jne）的結果決定接下來該抓哪一條指令執行。如果直接把 SEQ 的邏輯硬塞進管線化的硬體，這些相依性會被破壞：例如還沒等分支指令 decode 完就已經先把「猜測」的下一條指令抓進管線fetch stage，一旦猜錯，就要把已經進入管線、但實際上不該被執行的指令作廢（squash），這就是之後章節要處理的 data hazard／control hazard 的根源。

與面試／實務的關聯：理解「throughput 與 latency 的取捨」「clock rate 受限於最慢 stage」這兩件事，是回答「為什麼現代 CPU clock rate 不能無限往上拉」「為什麼分支預測（branch prediction）與分支誤判代價（misprediction penalty）這麼重要」這類系統設計面試題的基礎。寫程式時常被建議的「避免難以預測的分支」「減少長依賴鏈」「warm up CPU pipeline」等經驗法則，背後的物理原因正是本節描述的管線限制——分支預測錯誤代表整個已經進入管線的指令序列要被丟棄重來，深管線的 CPU 代價更高。

🔢 數學推導

用教材給的基準數字可以推導出 pipelining 的理論上限。設一條指令所需的組合邏輯總延遲為 C = 300ps，每個 pipeline register 的延遲為 R = 20ps，把 C 平均拆成 k 個 stage（假設可以無限細分，忽略不均勻切分的現實限制）。那麼：

clock period：T(k) = C/k + R　　throughput（單位 GIPS，1 GIPS = 每 1000ps 完成 1 條指令）：Throughput(k) = 1000 / T(k) = 1000 / (300/k + 20)　　latency：Latency(k) = k × T(k) = C + k×R = 300 + 20k

代入幾個 k 值可以看出趨勢：k=1 時 T=320ps、throughput≈3.1 GIPS、latency=320ps；k=3 時 T=120ps、throughput≈8.33 GIPS、latency=360ps；k=10 時 T=50ps、throughput=20 GIPS、latency=500ps；k=30 時 T≈30ps、throughput≈33.3 GIPS、latency=900ps。當 k → ∞，C/k → 0，所以 T(k) → R = 20ps，throughput 的理論上限趨近 1000/20 = 50 GIPS——這個上限完全由暫存器延遲 R 決定，跟原本的邏輯延遲 C 無關；而 latency 卻是 300 + 20k，隨 k 線性成長、沒有上限。這就是「收益遞減」的數學根源：切得越細，throughput 的邊際提升越來越小（因為已經快要碰到 1/R 這個天花板），但付出的 latency 代價卻持續線性增加，完全沒有回頭的空間——這也解釋了為什麼真實處理器的管線深度會停在某個甜蜜點（如 10～20 級），而不是切成成千上萬個 stage。

§01
Linux Kernel 的物件導向設計模式：Method Dispatch 與 Data Inheritance

今天延續 11/16 教過的「struct + 函式指標模擬 vtable、container_of」這個起點，深入 Neil Brown 在 LWN 發表的經典兩篇文章《Object-oriented design patterns in the kernel》（2011 年），這兩篇系統性地把 Linux kernel 裡用 C 語言模擬物件導向的各種手法歸納成固定的模式分類，分成兩大主題：method dispatch（方法／行為的派發）與data inheritance（資料的擴充／繼承）。今天的重點是把這兩篇文章的分類法整理清楚，並用真實的 kernel 結構對照，補上昨天只講了「vtable 基本概念」沒有展開的細節。

vtable（虛擬函式表）　在 C++ 裡由編譯器自動產生、藏在物件背後的函式指標表，用來實現動態多型；Linux kernel 沒有這個語言機制，所以直接用一個全是函式指標的 struct（如 file_operations）手動模擬同樣效果。

Part 1 把 kernel 裡的 method dispatch 歸納成 7 種具體模式：①純 vtable——struct 裡只有函式指標，物件內嵌一個指向 vtable 的指標，第一個參數通常是物件本身，kernel 裡約有 200 個這類結構，多數命名為 *_operations 或 *_ops；②vtable 裡的 NULL 函式指標——Brown 歸納出至少 4 種成因：漸進式開發新增欄位但舊的初始化沒跟上、方法對該物件無意義所以呼叫端要檢查 NULL、介面過渡期（如 ioctl() 逐步換成 unlocked_ioctl()）、長期並存（如同步 read() 與非同步 aio_read() 並存）；③非函式指標成員——像 owner（模組指標，防止模組在使用中被卸載）、name、list 這類跟「註冊」與「生命週期管理」相關的欄位；④非典型的第一參數——多數 *_ops 把物件自身放在第一參數，但也有例外（如部分 fb_ops 把 fb_info 放最後，或單例物件如 platform_suspend_ops 乾脆不傳物件參數）。

剩下三種 method dispatch 模式：⑤mixin——一組跟主要 vtable 分開、可以獨立選配的函式集合，例如 quota_format_ops、tcp_congestion_ops，物件不一定要實作這整組功能；⑥操作放在父物件上——例如 struct page 自己沒有 vtable 指標，它的操作反而放在 address_space_operations 上，super_operations 裡也包含部分本來該屬於 inode 的操作；⑦直接把函式指標嵌進物件本體（不另外包一層 *_ops struct）——適用於物件數量少、函式數量少、或每個物件都需要個別微調函式實作的情況，例如 request_queue、sock 裡都直接嵌了少量函式指標。VFS 的 file_operations／inode_operations／dentry_operations 這條鏈就是①③⑥的綜合運用：read() 若為 NULL，VFS 會改走 aio_read() 搭配 do_sync_read() 模擬同步讀取——這正是②的「介面過渡期」情境。

container_of　從一個「內嵌在外層 struct 裡的成員」的指標，反推回外層 struct 本身的指標。實作上靠 offsetof 算出成員在 struct 裡的位移量，再用成員指標減掉這個位移量；這個功能最早由 list_entry() 提供，2.5.28 版後才拆出更通用、名稱更清楚的 container_of。

Part 2 談的 data inheritance（資料繼承／擴充）以 struct inode 的演進史為主線，歸納出三種做法：①union 擴充——早期 struct inode 裡放一個 union，每種檔案系統（minix_inode_info、ext_inode_info、msdos_inode_info……）都把自己的擴充欄位塞進同一個 union，缺點是新增一種檔案系統就要去改這個共用的 union，而且每個 inode 配置時都要預留能放下「所有檔案系統裡最大那個」member 的空間，相當浪費；②內嵌結構（embedded structure）——方向反過來，讓各檔案系統自己的 ext3_inode_info 之類的結構內嵌 struct inode（成員名稱常叫 vfs_inode），這樣新增檔案系統完全不用動共用結構，但換來的代價是每個檔案系統都要自己實作 alloc_inode()／destroy_inode() 來配置與釋放記憶體；③void 指標——用一個 void * 指向另外配置的擴充資料，例如早期 struct inode 的 u.generic_ip（後改名 i_private）、struct super_block 的 s_fs_info、struct file 的 private_data，缺點是多一次記憶體配置、而且完全沒有型別安全（拿到的是裸的 void *）。

②的「內嵌結構」正是昨天教的 container_of 真正派上用場的地方：VFS 層只認得 struct inode *，但各檔案系統內部要做事時，需要從這個指標反推回自己的 ext3_inode_info *，這就是 container_of(inode_ptr, struct ext3_inode_info, vfs_inode) 的典型用法。文章也指出一個實用的判斷法則：如果一個 struct 的設計裡，最內層含有參考計數器（atomic_t 或 struct kref），由最底層的 driver 自己負責配置記憶體，且有對應的 *_init() 初始化函式，那它大概就是「內嵌結構」模式的多層疊加——例如 struct usb_device 內嵌 struct device，struct device 再內嵌 struct kobject，最底層才是真正的 struct kref 參考計數器，一層包一層，正好對應物件導向裡「繼承鏈越往基礎類別走，共用的基礎設施越多」的直覺。

Edge case：三種 data inheritance 不是互斥選擇而是會混用——同一個 struct inode 身上，檔案系統私有資料用②內嵌結構，但同時 i_private 這個 void 指標欄位仍保留給少數不想（或不需要）走內嵌結構的驅動程式使用；判斷「這個欄位該用哪種做法」本身就是真實 kernel 程式碼審查裡常討論的設計取捨，沒有單一正確答案，要看物件數量、記憶體精細度要求與型別安全的優先順序。

與面試／實務的關聯：「如何在不支援物件導向的語言裡模擬物件導向」是嵌入式 C 與系統程式設計面試中很常見的追問（有時直接問「C 語言怎麼做 polymorphism」），今天整理的 7 種 method dispatch 模式加上 3 種 data inheritance 模式，幾乎可以涵蓋所有常見答案；讀懂 VFS、網路子系統、區塊裝置層的原始碼時，一旦認出「這是純 vtable」「這是內嵌結構＋container_of」，就能很快抓到程式碼背後的設計意圖，而不會被一堆函式指標跳轉弄得暈頭轉向。

📄 原始碼
torvalds/linux v6.12 · include/linux/container_of.h#L18-L23
#define container_of(ptr, type, member) ({				\
	void *__mptr = (void *)(ptr);					\
	static_assert(__same_type(*(ptr), ((type *)0)->member) ||	\
		      __same_type(*(ptr), void),			\
		      "pointer type mismatch in container_of()");	\
	((type *)(__mptr - offsetof(type, member))); })
NOTE · 補充

這兩篇文章雖然寫於 2011 年，但描述的 7+3 種模式至今（2026）仍廣泛存在於 kernel 原始碼中，只是後續又長出了更多變體（例如 struct_group() 巨集、各種 notifier chain 機制），基礎框架並沒有過時。另外，内嵌結構與 void 指標兩種做法的取捨本質上是「型別安全與編譯期檢查」對「記憶體配置彈性與子系統解耦」的 trade-off——這跟軟體工程裡「組合優於繼承」「依賴反轉」等設計原則討論的其實是同一類問題，只是換了語言與場景。
